## 2. 根因分析

### 🔴 P0-A｜治理与 Web 服务抢同一个进程（**「卡顿」的根因**）

**证据**：`tools/productlib/routes/govern.py:51-54`
```python
t = threading.Thread(target=_run_govern, ...)
t.start()
```

**机理**：治理跑在 Web 服务**进程内的线程**上。本地 OCR 走 onnxruntime + OpenCV，是重 CPU 任务；按 ~2.8 s/张算，2738 张约 2.1 小时。这段时间内进程 CPU/GIL 被持续占用，而所有页面请求（列表、缩略图、治理进度轮询）都在这同一个进程里排队 → **用户体感就是「整个系统在治理期间卡死」**。

这也解释了为什么单看接口都很快、用户却说慢：**慢的是治理期间的并发争抢，不是单接口**。

**改法（推荐）**：治理移出 Web 进程，改为独立 worker 进程（`multiprocessing.Process` 或子进程），状态经 DB / 状态文件交换，Web 侧只轮询状态并支持「取消」。OS 会在两个进程间做公平调度，OCR 吃满 CPU 也不影响页面响应。

**改法（轻量兜底，治标）**：给治理进程降优先级（Windows 用 `psutil.Process.nice(BELOW_NORMAL_PRIORITY_CLASS)`）+ 每 N 张 `time.sleep(0.01)` 主动让出 GIL。改动小，但不如进程隔离彻底。

**验证方法**：治理跑起来后，另开浏览器反复翻照片页，记录 P95 响应时间；对比改造前后的 P95。

> ⚠️ 我没能在真实环境复跑治理来验证：那会写老板的真实库并消耗视觉 API 额度。此项为**架构级推断 + 代码证据**，建议先在测试库上验证。

### 🔴 P0-B｜`photos(taken_at)` 缺索引（**实测 32.9x，建索引只要 8 ms**）

**证据**：列表 SQL 在每个请求的 `ORDER BY p.taken_at`（`routes/photos.py:220`），而 photos 表现有 7 个索引**没有任何一个包含 `taken_at`**：

```
现有索引：govern_state / photo_kind / batch_id / photo_usage / carton_no / supervision_tag / sup_tag_ai
```

执行计划证实了后果：

```
【建索引前】SCAN p · CORRELATED SCALAR SUBQUERY · USE TEMP B-TREE FOR ORDER BY
           首页 0.9 ms   末页 17.1 ms
【建索引后】SCAN p USING INDEX idx_photos_taken（不再需要临时排序树）
           首页 0.4 ms   末页 0.5 ms        → 末页提速 32.9x
CREATE INDEX 耗时：8 ms
```

`taken_at` 空值行数 = **0 / 2738**，索引干净无副作用。

**改法**：在 `schema.py` 的迁移里加（注意按既有幂等铁律，用 `sqlite_master` 探测后再建）：
```sql
CREATE INDEX IF NOT EXISTS idx_photos_taken ON photos(taken_at);
```

**收益**：不仅现在快 33 倍，更重要的是**去掉了随照片数线性劣化的全表排序**。照片量再涨 10 倍时，这条索引的价值会成倍显现。

**风险**：极低。索引约几十 KB，写入开销可忽略。

---

### 🟡 P0-C｜`synchronous = FULL`，应改为 `NORMAL`

**实测**：同上那条 UPDATE+COMMIT，200 次提交取平均：

| synchronous | 单次提交 | 相对现状 |
|---|---|---|
| FULL（现状） | 1.30 ms | — |
| **NORMAL** | **0.04 ms** | **37.1x** |
| OFF | 0.03 ms | 37.8x（相对 NORMAL 无额外收益） |

WAL + `NORMAL` 是 SQLite 官方推荐的组合：`NORMAL` 下 WAL 在**检查点**才 fsync，正常提交不必等磁盘，同时仍能保证崩溃后的一致性（只可能丢掉最后极短窗口内的事务）。

**改法**：`store.py:53-54` 的 `connect()` 里加一行：
```python
con.execute('PRAGMA synchronous=NORMAL')
```

**收益说明（务实口径）**：这条**不会**显著缩短治理总时长——2738 张省下约 3.5 秒，相对 2.1 小时是 0.05%。它的真正价值是**降低写 IO 抖动与锁竞争、减少查看照片时的偶发卡顿**。请不要按「治理提速」宣传它。

**风险**：断电/硬崩溃可能丢失最近少量事务。本产品是本地单机工具，数据可重建（照片在别处、治理可重跑），风险可接受；若不能接受则保持 FULL。

### 🔥 P1-A｜视觉分类结果没有缓存（**性价比最高的一条**）

**证据**：`pipeline.py:138-139`，`govern_one` 对**每一张照片无条件**调用：
```python
(kind, conf, reason, model, usage,
 sup_tag, sup_conf, sup_reason) = classify(con, photo, use_vision)
```
→ `classify`（`pipeline.py:104-109`）→ `vision.classify(path)` → `_call()` → **一次完整的多模态 HTTP 请求**。

而 OCR 那一侧，他们已经做得很好：`_OCR_CACHE` + `_ocr_cache.json`，注释里写明了动机（`pipeline.py:50-52`）：

> 实测：249 张照片全量 OCR ≈ 700s；有缓存二次运行 ≈ 5s。
> **治理是必然要反复调的（阈值、分路规则、纠偏表），不缓存等于每次付 12 分钟。**

问题就在这里：**这条正确的判断只覆盖了 OCR，没覆盖视觉**。而 `use_vision` 默认为 `True`（`govern.py:46`）。于是每轮重复治理，都要为全部照片重付一次网络时间与 API 费用——哪怕用户只是调了一下 `conf >= 0.5` 这种阈值（`pipeline.py:148`）。

而且缓存**天然安全**：`_call` 里设了 `temperature=0`（`vision.py:152`），输出是稳定的，重跑也是同样的结果。

**改法**：按 `file + 模型名 + prompt 版本（hash）` 做 key 缓存 `kind/conf/reason/usage/sup_tag*`。可先沿用 `_ocr_cache.json` 的机制（最简单），长期建议和 OCR 缓存一起迁进 SQLite 表（见 P1-B）。

**收益**：重复治理从「每张一次网络请求」降到 0 次。调阈值、改纠偏表时几乎瞬时完成，且**省下真金白银的 API 额度**。总之，这是一条**同时省时间与省钱**的改动。

**注意**：缓存 key 必须带上模型名与 prompt 版本，否则换了模型还用旧结果，是静默错误。

### 🟠 P1-B｜OCR 缓存每 25 张就全量 pretty-dump 一次

**证据**：`pipeline.py:598-604`
```python
con.commit()
if done % 25 == 0:
    save_ocr_cache()      # 每 25 张
```

而 `save_ocr_cache`（`pipeline.py:84-95`）做的是**对整个缓存字典**：
```python
for k, v in sorted(_OCR_CACHE.items()):     # 全量排序
    dump.append(d)
json.dump(dump, f, ensure_ascii=False, indent=1)   # 全量 pretty-print 重写
```

这是一次 **O(缓存总量)** 的完整重序列化，每 25 张执行一次。缓存现在 1.5 MB，未来会持续增长；2738 张照片 ≈ 触发 110 次全量重写，且 `indent=1` 的格式化输出比紧凑 JSON 慢得多。

**改法（按推荐度排序）**：
1. **迁进 SQLite 表**：`ocr_cache(file PRIMARY KEY, texts_json, ...)`，`INSERT OR REPLACE` 增量写入，彻底告别全量重写（与 P1-A 一起做最划算）。
2. **最低改动**：只在治理结束时写一次 + 异常兜底路径写一次；并去掉 `indent=1`（性能立即改善，代价是可读性下降——这是缓存文件，本就不需要人读）。

**收益**：消除一块随缓存规模增长的隐性开销。

### 🟡 P1-C｜每张照片一次 COMMIT + 一次冗余 UPDATE

**证据**：`pipeline.py:576` 和 `:598`
```python
con.execute("UPDATE photos SET govern_state='running' WHERE id=?", (ph['id'],))
...
done += 1
con.commit()      # 每张一次
```

`govern_state='running'` 这个中间态**没有任何消费者**（进度走的是 `progress()` 回调），是一次纯浪费的写。

**改法**：每 25 张提交一次（与缓存落盘节奏一致），并去掉或批量化那条 `running` UPDATE。异常时回退到逐张提交以保证不丢进度。

**收益说明（诚实）**：相对 OCR 的 2.8 s/张，这块的绝对值很小。**它的意义主要是减少磁盘 IO 抖动和写锁竞争**，真正解决卡顿的是 P0-A。请把它当收拾杂物，不要当性能杀手看待。

### 🟢 P2-A｜缩略图：`Image.draft()` + 预热缺失的 382 张

**证据**：`routes/photos.py:465-471`
```python
im = Image.open(r['path'])
im.thumbnail((360, 360))
```
缺了 `Image.draft()` —— 等于先**完整解码整张原图**（样本为 2.7–4.3 MB），再缩小。

**实测**（真实照片，只读，输出到临时目录）：

| 样本 | 体积 | 现写法 | 加 draft | 提速 |
|---|---|---|---|---|
| IMG_20250405_083614.jpg | 4.3 MB | 64 ms | 49 ms | 1.3x |
| IMG_20250405_083621.jpg | 3.8 MB | 59 ms | 47 ms | 1.3x |
| IMG_20250405_083631.jpg | 3.8 MB | 65 ms | 51 ms | 1.3x |
| IMG_20250405_083645.jpg | 2.7 MB | 54 ms | 39 ms | 1.4x |
| IMG_20250405_083701.jpg | 4.2 MB | 72 ms | 55 ms | 1.3x |
| IMG_20250405_083708.jpg | 3.5 MB | 64 ms | 46 ms | 1.4x |

**结论必须说实话**：`draft()` 只带来 **1.3–1.4 倍**，不是数量级。而且目前 2356/2738 张已预热，只有 382 张是冷的。所以**这条不是主因**，属于顺手捡的便宜。

**改法**：加 `im.draft('RGB', (360, 360))`；再提供一个「预热缺失缩略图」的后台任务一次性补齐那 382 张。

### 🟢 P2-B｜`/thumb/` 没有 HTTP 缓存头

**证据**：`routes/photos.py:452-474` 直接 `FileResponse(tp)`，未设 `Cache-Control` / `ETag`。而 `server.py:78-85` 的 no-store 中间件**只作用于 `/static/`**。

后果：用户翻到第 2 页再翻回第 1 页，60 张缩略图会被重新下载一遍。缩略图以 photo id 命名且内容稳定，完全可以缓存。

**改法**：给 `/thumb/{pid}` 加 `Cache-Control: max-age=...` + `ETag`（基于文件 mtime/size）。

**收益**：来回翻页、重复查看同一个柜的照片时明显更顺，且几乎零成本。

## 4. 明确建议：**不要换数据库**

（呼应此前关于 SQLite 替代方案的讨论。）

| 理由 | 数据 |
|---|---|
| 数据库极小 | 4.9 MB |
| 查询极快 | 0.4–0.9 ms |
| 瓶颈不在 IO/查询 | 而在 **CPU 的 OCR 推理**与**网络的视觉 API** |
| 换库收益 | ≈ 0 |
| 换库成本 | 极高（重构全部数据访问层、迁移、打包体积、部署形态全变） |

之前讨论过的 DuckDB 只读副本 / LibSQL / 服务端 DB，在**当前这个量级**都用不上。真正的优化空间全在「治理链路怎么少干活」。

> 什么时候才该重新考虑：**多柜多人同时写**、或照片量级到十万以上。现在（2738 张 / 4 个柜 / 单机）远没到那一步。

## 6. 验证与量化方法

**可安全复跑的基准**（只读，不碰真实库——本次脚本即为此写法）：

```python
# 用 backup API 从真实库做只读副本，一切读写都发生在临时副本上
s = sqlite3.connect('file:<真实库>?mode=ro', uri=True)
d = sqlite3.connect('<临时>/bench.db'); s.backup(d)
```
