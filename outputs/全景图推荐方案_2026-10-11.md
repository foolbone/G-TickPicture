# 「由标签近景找可能的全景图」实现方案

日期：2026-10-11 · 状态：方案（未实现）· 数据来源：真实库实测 + 样本人工核对

---

## 一、结论先行

**能做到"给出少数几张、让人一眼确认"，做不到"自动关联"。**

推荐做法：**导入序号相邻（前后各 3 张）∪ 微信文件名序号相邻 ∪ 同组 → 分类过滤 → 最多给 3 张候选 → 人工一键确认**。

- 覆盖率 **36% → 49%**，同时**候选数从平均 9.9 张降到约 2 张**（现在是"要么给 29 张没法看、要么给 0 张没得看"）；
- 🔴 **主信号必须避开时间**：照片有**三种来源**（相机原图 / 手机相册 / 微信转来），只有相机原图的时间可信；现有「同组」按时间分组，在微信数据上分成 23~29 张的超大组、在手机相册数据上 100% 是单张组，两头不讨好。可靠的顺序在**文件名的连续序号**和**导入顺序**里；
- 界面上展示"**相隔几张**"而不是"间隔几秒"——秒差在微信场景下是假数字；
- **不引入 pHash**：实测证明它在这个场景没有区分度（正/负样本中位数都是 32）；
- 绝不自动写关联 —— 全景图只能证明"同一托盘/同一批发送"，不能证明"同一件货"。

## 二、场景拆解（含真实样本）

### 2.1 采集动作
作业时对一件货通常拍两张：
1. **标签近景**：怼着物料标签拍，OCR / 大模型能读到编码 → 自动关联的产品就是它；
2. **产品全景**：退后拍整件/整托盘，**图上没有编码** → 自动关联完全无从下手。

### 2.2 真实样本观察（人工看图核对）
| 样本 | 近景（有标签） | 候选全景 | 判断 |
|---|---|---|---|
| 105050103010H | 贴标签的黄色包装袋（标签写明该编码） | 白色保护膜卷材特写 | 同一托盘时段（11:48 / 11:49），近景左缘可见同款膜 → **相关**，但全景看不出是哪一件 |
| 103013100020A | 标签近景 | 金属线材托盘全景 | 该全景**同时**是 203150003112 的候选 → **一张全景对应多个产品** |

### 2.3 关键特性（决定方案形态）
1. **一图多产品是常态**：一个托盘上堆着多种货，一张全景天然属于多个产品 —— 不能做成"一张全景只能给一个产品"，否则会逼人瞎选。
2. **全景 ≠ 该产品的特写**：它证明的是"这批货在这",不是"这就是这件"。所以只能"建议"，必须人看图。
3. **上下文（同组/时间）才是主信号**，画面内容本身没有编码可依。

## 三、⚠️ 前提：三种来源混在一起，时间只有一种可信（这改变了信号选型）

> 以下实测基于老板真实库 `D://集刻产品库//data`（2737 张照片 / 1075 条标签关联）。

### 3.1 三种来源，时间可信度完全不同

| 来源 | 张数 | 文件名形态 | `time_src` | 时间可不可信 |
|---|---|---|---|---|
| **相机原图** | 236 | `IMG_20250405_083614.jpg` | `exif` | ✅ **可信**（真拍摄时间） |
| **手机相册** | 1284 | `20260915_204034_01066.jpg` | `filename` | ⚠️ 半可信（文件名带拍摄时刻，但照片常是挑出来的、不连续） |
| **微信转来** | 1166 | `微信图片_20260913075631_644_3035.jpg` | `mtime` | ❌ **不可信**（= 接收时间；35% 与他人同秒；与拍摄差约 2.67 天） |

### 3.2 这让现有「同组」机制两头不讨好

`group_idx` 是按 `taken_at` 间隔算的，于是组的质量完全取决于时间：

| 来源 | 每组张数 | 单张组占比 | 现有「同组待确认」一次给几张 |
|---|---|---|---|
| 相机（exif） | 4.5 张 | 19% | 中位 9.8 张（46% 的情况 ≥10 张） |
| 手机相册（filename） | **1.0 张** | **100%** | **0 张**（完全给不出候选） |
| 微信（mtime） | **22.9 张** | 4% | **中位 29 张**（98% 的情况 ≥10 张） |

**合计：只有 36% 的标签照片能拿到同组候选，平均一次给 9.9 张。** —— 要么一次甩 29 张没法看，要么一张都没有。这才是现在「同组待确认」不好用的真正原因，不只是覆盖率低。

### 3.3 各来源的召回率（窗口 = 前后各 3 张）

| 来源 | 标签关联数 | 按时间排序 | 按导入顺序排序 |
|---|---|---|---|
| 相机（exif） | 13 | 92% | 92% |
| 手机相册（filename） | 681 | 30% | 30% |
| 微信（mtime） | 381 | 80% | 82% |
| **合计** | **1075** | **48%** | **49%**（候选约 2.0 张） |

结论：**导入顺序在三种来源上都不劣于时间排序**（微信下还略好），且不依赖时间可信度 → 定为**统一主信号**。

### 3.4 好消息：三种来源的文件名都保留了顺序
- **微信**：`微信图片_<时间>_<序号>_<发送批>`，序号连续递增（838 批 22075→22080；3035 批 644→779，连续率 100%）；
- **相机**：`IMG_20250405_083614.jpg` 自带拍摄时刻，连拍文件名序号递增；
- **手机相册**：`20260915_204034_01066.jpg` 末段是序号；
- 而**导入顺序 = 文件名顺序**（库里 rowid 1~8 对应微信序号 755→762），因为导入时按文件名遍历。

所以「导入序号相邻」是一条**三种来源通吃**的信号。
## 四、信号实测（决定了方案取舍）

在真实库上统计 **1075 条**「标签类照片的关联」（三种来源混合）：

| 信号 | 覆盖率 | 命中时平均要看的候选数 | 结论 |
|---|---|---|---|
| 现有「同组」（batch + group_idx） | **36%** | **9.9 张**（微信下中位 29 张、手机相册下 0 张） | ⚠️ 两头不讨好，必须收敛 |
| **导入序号相邻 ±3（窗口 6）** | **49%**（526/1075） | **2.0 张** | ✅ **主信号**：三种来源通吃、与时间无关 |
| 导入序号相邻 ±5（窗口 10） | 54% | 2.7 张 | 可作"再多看几张" |
| 时间相邻 ±3（窗口 6） | 48%（520/1075） | 1.9 张 | 覆盖相同，但依赖时间可信度 → 只当兜底/加权 |
| 时间窗 ±90 秒 | 100% | **约 69 张** | ❌ 噪音太大，没法确认 |
| **pHash 视觉相似** | — | — | ❌ **无效**（见下） |

### pHash 为什么不能用（实测负面结论）
40 对"同组近景↔全景"（正样本）与 30 对"同批次但间隔 >10 分钟"（负样本）：

| | 中位数 | 范围 |
|---|---|---|
| 正样本距离 | 32 | 20 ~ 38 |
| 负样本距离 | 32 | 26 ~ 42 |

**分布几乎完全重叠 = 没有区分度。** 原因：pHash 是整图低频结构，近景（标签特写）和全景（整堆货）构图天生不同；反过来，同一仓库里不同的货堆（木箱、托盘、塑料膜）低频结构反而很像。所以这条路直接排除，别再试。

## 五、推荐方案

### 5.1 触发条件（避免打扰）
只对**缺全景的产品**给出建议：
- 该产品**已有** label 类关联照片（说明是"有标签的货"）；
- 且**没有** product / packaging 类照片（说明缺全景）。

> 已有全景的产品不提示 —— 老板不需要"你已经有的东西"的提醒。

### 5.2 候选来源与过滤（主信号 = 导入序号，三种来源通吃）
```
候选 = （同批次「导入顺序」前后各 3 张）        ← 通用主信号，不依赖时间/命名
     ∪ （文件名序号相邻 ±3：微信/相机/相册都解析）
     ∪ （同组 group_idx，但**组内再按导入顺序取相邻 ±3**）
       过滤：kind ∈ {product, packaging, unknown}     ← 排除 label/packing_list/scene
             未关联到本产品
             非副本（is_dup=0）
             未被人标记「无关联」（cand_reject）
       排序：序号相邻优先 → 同组 → 时间近的（仅 exif 时时间才参与）
       截断：最多 3 张（超出折叠成"还有 N 张"）
```

🔴 **同组必须收敛，不能整组给**：实测微信来源的组平均 22.9 张、一次能给 29 张 —— 那就是"没法看"。所以同组只用于**确认与加权**，候选本身一律按导入顺序收敛到 ±3 张。这一条同时修掉了现有「同组待确认」一次甩几十张的老问题。

- **导入顺序怎么取**：导入时按文件名遍历入库，库里 `rowid` 即导入序；更稳的是导入时落 `import_seq`（本次导入内序号），别依赖 SQLite rowid 语义。
- **序号解析（按来源）**：
  - 微信 `微信图片_<14位时间>_<序号>_<发送批>` → 同发送批内 `|Δ序号| ≤ 3`；
  - 相机 `IMG_20250405_083614.jpg` → 时间可信，可用秒差辅助；
  - 手机相册 `20260915_204034_01066.jpg` → 末段序号；
  - 解析不出就退回导入顺序（不失败、不空转）。
- **时间只当加权，不当依据**：仅 `time_src='exif'` 时把"秒差小"作为排序加分。
- **必须复用现成口径**：过滤走 `store._cand_filter_sql()`，排除走 `rejected_pairs(con)`（铁律：同源）。
- 窗口限定在**同一 batch_id** 内 —— 跨批次比较会张冠李戴。

### 5.3 呈现（产品详情页）
在现有「待确认」并排区新增一列 **"可能的全景图"**：

```
┌ 可能的全景图 · 3 张待确认 ──────────────┐
│ [缩略图] 后 1 张    [关联] [不是]        │
│ [缩略图] 前 2 张    [关联] [不是]        │
│ [缩略图] 同组       [关联] [不是]        │
└──────────────────────────────────────┘
```
- 🔴 **显示什么，取决于这张图的时间可不可信**（按 `time_src` 自适应）：
  - `exif`（相机原图）→ 可以写"**间隔 8 秒**"，时间是真的；
  - `filename` / `mtime`（相册、微信）→ **只写"后 1 张 / 前 2 张"**，绝不写秒数（实测与拍摄差 2.67 天、35% 同秒，写秒数就是给假数字）。
- 「关联」= 走现有 `/api/links`；「不是」= 走现有 `candidates/reject`（可撤销）。
- 已给别的产品用过的全景，加角标 `已用于 N 个产品`（一图多产品是常态，但要让人知道）。

### 5.4 明确不做的事
- ❌ 不自动关联（哪怕置信度很高）—— 错关联会被报告当成证据用出去；
- ❌ 不上 pHash（实测无效）、不上模板匹配/特征点（成本高、收益未知）；
- ❌ 不做"±90 秒全收"（69 张候选等于没有建议）；
- ❌ 不在时间不可信的来源上展示秒差；
- ❌ 不把"整组"直接当候选（微信下 29 张）。

### 5.5 从源头改善（采集侧建议，成本最低）
1. **微信发「原图」** → 保住 EXIF，时间变可信（现在 1166 张微信图里 EXIF 全丢）；
2. **边拍边发、别攒着挑着发** → 序号顺序才等于拍摄顺序；
3. **一件货连着拍完再发下一件** → 序号相邻才等于"同一件货"；
4. 手机相册导出的照片**别改名** → 文件名里的拍摄时刻和序号才在。
这四条不改代码，但直接决定推荐准不准 —— 值得写进作业规范。

| 层 | 位置 | 改动 |

| 后端 | `tools/productlib/store.py` | 新增 `product_panorama_candidates(con, code_norm, k=3)`：导入序号窗口 ∪ 文件名序号 ∪ 同组（组内再收敛），复用 `_cand_filter_sql` / `rejected_pairs` |

| 路由 | `tools/productlib/routes/products.py` | `/api/products/{code}/candidates` 返回体加 `panoramas`；或独立 `GET /api/products/{code}/panoramas`（需在 `checks/routes.py` 登记落点） |

| 测试 | `tests/panorama_cand.py` | 见第六节 |
| 实跑 | `checks/cdp_panorama.py` | 界面层验证（Edge + CDP，可选 `PL_EXT_URL` 复用打包版） |

**性能**：按 `(batch_id, taken_at)` 取前后各 K 行，是索引可覆盖的局部查询；单产品几十毫秒量级。**不要**全库扫或引入图像计算。

## 七、验证计划

`tests/panorama_cand.py` 至少要锁住：
1. 同组有全景 → 出现在候选，且标 `same_group=True`；
2. 同组没有、但导入顺序前后 3 张内有 product 类 → 出现在候选（**净新增能力**）；
3. 微信命名且序号相邻 ±3 → 命中；序号隔很远（>10）的不出现；
4. `packing_list` / `scene` 类**绝不进候选**（否则会把整箱清单关联到一件货）；
5. 已关联本产品的照片不重复出现；
6. 已标记「无关联」的不出现；撤销后回来；
7. 副本（is_dup=1）不出现；
8. **一张全景可同时是多个产品的候选**（一图多产品不被去重）；
9. 计数（角标）与列表条数一致（同源断言）;
10. 无 label 照片的产品返回空、不报错；
11. 🔴 **时间退化场景**：造一批 `taken_at` 全部相同、`time_src='mtime'` 的照片，
    候选仍要按导入顺序给出（不因时间撞车而返回空或乱序）；
12. **三种来源各自一组用例**：`IMG_*`+exif / `20260915_*`+filename / `微信图片_*`+mtime，
    都能给出候选且**不超过 3 张**；
13. **大组收敛**：造一个 29 张的组，候选必须 ≤3 张（防止重蹈"一次甩几十张"）。

`checks/cdp_panorama.py`：浏览器里确认那一列真的渲染、点「关联」真的写进去、「不是」真的消失且可撤销。

## 八、分期建议

| 期 | 内容 | 价值 |
|---|---|---|
| **一期（推荐先做）** | 导入序号相邻 ±3（+ 微信序号）∪ 同组 + 分类过滤 + 人工确认列 | 覆盖率 33%→46%，一次只看 ~2 张，改动集中在 store + products.js |
| 二期（可选） | "再多看几张"（K 可调 3/5）；角标显示"已用于 N 个产品"；导入时落 `import_seq` | 让老板按需放宽、顺序更稳 |
| 三期（不确定） | 「帮我判断」按钮 → 把近景+候选一起交给视觉大模型判断是否同货 | 只在人工点的时候调用（每次 1~2 张），成本可控；**结论仍只作建议** |
| 同步（零代码） | 作业规范要求对方**发原图、边拍边发、连着发** | 从源头让顺序和 EXIF 可用，比任何算法都值 |

## 九、风险

| 风险 | 说明 | 对策 |
|---|---|---|
| **时间只有相机原图可信** | exif 236 张可信，微信 1166 张不可信（35% 同秒、差 2.67 天） | 主信号换导入序号；展示按 `time_src` 自适应 |
| 来源混杂 | 同一批次可能既有相机图又有微信图 | 统一用导入序号，时间只作加权 |
| 顺序本身失真 | 对方攒着挑着发 → 序号顺序 ≠ 拍摄顺序 | 只能给弱建议；写明"可能"；靠采集规范改善 |
| 推荐错 | 同托盘 ≠ 同一件货 | 只建议不自动；「不是」可撤销 |
| 打扰过多 | 每个产品都给 3 张 | 触发条件限定"缺全景"，且最多 3 张 |
| 一图多产品被误当重复 | 老板可能以为系统重复推荐 | 角标写明"已用于 N 个产品" |
| 窗口内噪音 | K 取大时命中率涨得慢、候选变多 | 默认 K=3，实测甜点 |
| 微信压缩画质 | 转发默认压缩，OCR/大模型识别率会降 | 采集规范：发原图（顺带解决 EXIF） |
