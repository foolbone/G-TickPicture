00 v3.1 核心变更

v3.1 修订依据：现场真实规模（老板 09-23 确认）
货品件数几百件（不是 200 件）
照片数原则上每件 2 张 → 600~1600 张
作业时长预检 + 拍照持续 1 天（约 6~8 小时纯作业）
完整性要求⚠️ 原则上每件都拍，但实际能到 80% 覆盖率即可满足要求

这四条里，最后一条改变了本方案的核心目标口径——前三条只是把规模放大了 3~8 倍，工程上可解；最后一条改的是"什么叫做完"的定义。

一、三段式主路径（本版的骨架）

STAGE 1 · 现场
① 批量采集
走一圈，全部拍完。全程只按快门——不识别、不绑定、不弹窗、不做任何决策。照片进入项目的「待整理池」。
STAGE 2 · 现场随时 / 收工统一
② 对应货品
系统按拍摄时序自动分组，OCR 给出建议，人做决定。拍一段就顺手清一段，剩下的留到收工时一次过——进度随时落盘，两处接着做。
STAGE 3 · 交付
③ 打包输出
按清单生成交付包：ZIP（按货品分目录）+ PDF 联系表 + 清单对照表，微信分享或上传 WebDAV。
v3.1 最重要的变化：「100% 对应」不再是达标条件
v3.0 隐含了一个假设——清单里的每件货都必须有照片，缺口要一件件处理干净才能交付。按这个口径，几百件货里会有 40~100 件的缺口，逐件标记原因就是一项15~30 分钟的额外负担，而且必然做不完整。

v3.1 改成覆盖率达标制：
  • 达标线：清单覆盖率 ≥ 80%（有照片的货品数 / 清单货品数），且无未对应的已拍照片。
  • 达标后缺口不再阻塞交付——缺口清单自动汇总进交付包，不需要人工逐件标记原因。
  • 没达标的处理办法只有两条，且都必须由人显式选择：① 回去补拍（拍照时）② 强制导出并说明原因（收工后）。

为什么这个改动是对的：80% 本来就是业务上的验收线。让 APP 去追求一个业务上不需要的 100%，等于把成本转嫁给最忙的那个人。系统该做的是把缺口诚实地说出来，而不是假装它不存在、或者要求人消灭它。
v2.0 的定位错误：让机器当了决策者
v2.0 把 OCR 当作「主路径引擎」——快门按下后 300ms，由机器决定这张照片归到哪件货。它虽然加了五道防线（分组互证、多候选消歧、四态归属、待核对闭环、可追溯），但本质上还是在赌 OCR 的精度——只要有一张照片被静默归错，错误就顺着流程流进了交付物。

更隐蔽的问题是：它把「整理」这件事切碎、塞进了拍摄的那一刻。预检员在现场虽然没被打断，但系统一直在替他做决策、算分组、写状态。整个 APP 的复杂度、异常场景、解释成本，都压在了现场那一秒里——而那恰恰是最不该有复杂度的地方。
v3.0 的定位：机器只建议，人做决定
先批量整体拍照 → 然后统一对应货品 → 最后打包输出分享。

三个阶段物理隔离，各管各的，互不渗透：
  • 采集阶段，系统什么都不做。只有一个动作：把照片和时间戳写进本地库。零识别、零分组、零判定。预检员的动作从"掏手机→拍→塞回口袋"变成同样的事，但没有任何后台逻辑在替他决策。
  • 整理阶段，OCR 才登场——但只以"建议"的身份。它把识别结果、置信度、命中依据一并摆出来，人看一眼点一下。系统永远不替人写最终归属。
  • 交付阶段，只交付人确认过的。没被确认的照片不会出现在交付包的正片清单里——它们进「未使用」区并在对照表里列明。这是本版最强的一条保证。

三、那"统一对应"会不会变成一件苦差事？

这是本方案必须回答的问题——因为全部靠人确认，如果整理页不好用，就等于把 v2.0 的风险换成了一个更糟的体验。

答案是把整理的单位从「张」提升到「组」，并用七种手段把人的操作次数压到最低：

#手段效果
1时序自动分组利用"走一段、站定、连拍 2~3 张"的现场规律，把 1200 张照片聚成约 400~500 组。人按组决策，不按张决策。
2组代表图每组只看一张代表图，其余折叠。人眼的工作量 ÷3。
3建议置于组头卡片上直接显示 建议：ABC-1024 · 92%，人只需做「对 / 不对」二选一，不需要自己去找。
4相似建议合并成块建议相同的相邻组自动并成一个"待确认块"，一次点击确认整块（如 3 组都建议 ABC-1024 → 一次点掉）。
5一键确认全部高置信≥0.90 且组内一致的全部一次性确认。通常有 60~80% 的量能被这一下清掉。
6只显示未对应的整理页默认只显示还没对应上的——待确认的组、无建议的组、已拍未指派。已确定的收起来不占视线。
7候选前缀检索手动指派时，输入 2~3 个字符即出候选（Trie 前缀 + 编辑距离容错），扫码可直达。手动也不慢。
8连贯拍摄的批量预期v3.1 新增采集时按时间连续的一段（如 10 分钟内）自动归一个「批次」（Burst），整理按批推进。整理页只需显示"还差几批"，不必面对上千张的全局数字——这对心理负担是决定性的。
一句话总结这一版的调整
v2.0 问的是「怎么让机器不出错」——这是个没有确定答案的问题。
v3.0 问的是「怎么让人觉得对一遍很便宜」——这是个可以用工程解决的问题。
v3.1 补上了第三个问题：「付出多少才算够」——答案是 80% 覆盖率，不是 100%。把达标线定在业务真正的验收线上，而不是定在"理论上完美"上。

关键观察（本次修订的核心依据）：

  • 拍摄与整理在时间上是分离的，但不是"只能分离"。现场没有条件做完整整理，也不该在那时做——因为整理需要"停下来、看屏幕、做判断"，这三种行为在现场都不成立。但允许"顺手清一段"：趁换区、等车、午休的空档处理掉一段，能显著减轻收工后的负担。所以 v3.1 支持两条路径共用一套数据。
  • 整理的主场景仍是"坐下来过"：人坐着、双手空闲、视线在屏幕上、大概率有 WiFi。这意味着整理页的 UI 可以、也应该与采集页完全不同——一个要极简到什么都没有，一个要信息密集、操作高效。
  • 现场只需要一件事：按快门。任何在现场弹出的东西都是成本。
  • 整理需要四件事：看得清（大图缩略）、点得快（批量操作）、有对照（清单在旁边）、有退路（错了能改）。
  • 拍摄是成组发生的：站在一件货前会连拍 2~5 张（唛头、整体、侧面、破损处）。这是整理阶段最重要的可利用规律。
  • 清单顺序 ≠ 现场动线。清单按客户口径排，现场按仓库码放排。所以不能拿清单顺序当先验。
  • 存在清单外的货（临时加货、清单漏录），也存在找不到的货（压在垛底、已被提走）。整理阶段必须能表达"不存在的货"。
  • ⚠️ 规模是"一整天 + 几百件 + 上千张"：这意味着整理页不能只考虑"好不好用"，还要考虑连续作业几小时后人还有没有耐心（见 R1b），以及"面对上千张时的心理压力"——所以覆盖率仪表与批次分组是必需而非锦上添花。
  • ⚠️ 80% 覆盖率是业务验收线，不是失败线：现场本来就拍不满，方案设计必须把"缺口是常态"当成前提，而不是把缺口当成要清零的异常。

1.3 现场环境约束

🌐 网络
仓库深处/金属货架屏蔽，4G 信号弱甚至无信号。采集必须完全离线，OCR 与上传都放到有网络时（整理阶段）再做。
💡 光线
顶灯昏暗、逆光、外包装反光。闪光灯默认关闭，需曝光补偿与手动对焦。
🧤 操作
常戴手套、单手操作、手机挂腕带。采集页大按钮、零输入；整理页也需要大点击区。
📦 数量
单次预检几百件货，照片 600~1600 张。列表虚拟滚动，缩略图必须缓存；整理页要能扛住上千张的组织。
🔋 续航
连续作业一整天（6~8 小时）。采集期禁止跑 OCR、禁止预览帧分析、禁止轮询——这是采集期唯一的技术红线。
🏷️ 标签
编码多为印刷唛头/条码贴纸，会污损、褶皱、倾斜、被遮挡、手写。OCR 必然会失败一部分——所以它只能做建议。

02 设计原则与关键决策

2.1 十条铁律

#原则含义与验证方式
1三段式隔离 采集 / 整理 / 交付三阶段互不渗透。验证：采集页代码里不出现任何 OCR 调用；整理页里不出现相机预览。
2采集期零智能 采集时系统只做一件事——把照片和时间戳落盘。不识别、不分组、不判定、不联网。验证：飞行模式下采集全流程无阻碍。
3人做决定，机器给建议 任何进入交付包的归属，必须有一条"人确认"的记录（assignment.confirmed_at IS NOT NULL）。验证：交付包里不存在 confirmed_at 为空的归属。
4建议必须可解释 每条 OCR 建议都带置信度 + 命中依据（来自哪个 token、匹配方式）。禁止出现"系统认为是 X"这种无依据的建议。
5OCR 可完全关闭 设置里一个开关关掉 OCR，全流程照常可用（纯手动指派模式）。验证：关闭后整理页仍能完成 400 件货的全部指派（≤45 min）。
6整理单元是"组"不是"张" 人按组决策，机器负责把张聚成组。分组错了要能手动合并/拆分——分组是建议，不是约束。
7只显示缺口 整理页默认隐藏已确定的项，把注意力集中在未对应的照片和未拍照的货品上。
8离线优先 采集、整理、打包全部本地完成。网络只用于 WebDAV 上传与微信分享。
9文件名自带归属 交付时按 {项目}_{序号}_{编码}_{序号}.jpg 命名（生成在交付包内，不改动原始文件）。照片被单独拷走也丢不了归属。
10不申请"所有文件访问" 不用 MANAGE_EXTERNAL_STORAGE。用 App 私有外置目录 + 系统分享 / SAF 导出。

2.2 关键决策与取舍

决策点选定方案理由 / 放弃的方案
整理时机 拍完统一整理 放弃"边拍边整理"。现场不具备整理条件（站着、戴手套、看货）。统一整理时人坐着、有网、注意力在屏幕上，效率高一个数量级。
归属决策者 人 放弃"OCR 自动归档"。精度风险不可控，且错误静默流入交付物是业务不可接受的风险。
OCR 触发时机 采集结束后后台批量跑 放弃"整理页实时识别"（人等着，每一张都是延迟）。放弃"采集时实时识别"（耗电、发热、拖慢快门）。
最佳窗口：采集结束后、整理开始前的这段时间（人正在走路/换场/坐下，手机可以安静地跑 OCR）。
建议粒度 组级建议 组内多张 OCR 结果做加权投票，得到一个组级建议 + 组级置信度。张级建议只在"拆分组"后的单张指派里用到。
分组依据 拍摄时序（间隔 ≤ 45s 归同组）+ 可手动合并/拆分 放弃"清单顺序邻近"（现场动线与清单顺序无关）。分组结果必须可人工修正——因为人是最终决策者。
分组错误的兜底 合并 / 拆分 / 移出 三个操作 走神拍错一张、或一件货拍了两段（中间插了别的货），都能修正。
手动指派方式 候选列表（前缀检索）+ 搜索 + 扫码 + 新建货品 四种入口覆盖全部情况。候选列表基于清单做 Trie 索引，输入 2~3 字符即出。
相册导入 并入采集流程 相册照片直接进"待整理池"，与现场照片一视同仁。区别只在于：相册照片没有可靠的拍摄时序（可能全是同一时间戳），所以不参与时序分组，独立成组。用户可在整理页手动合并。
一张照片拍到多件货 主归属 + 附加关联 数据模型预留多对多关联表。UI 上先只做单选（P0），多选留到 P2。
落选照片 「未使用」区 + 对照表列明 没被指派或没被确认的照片不进正片，但也不删——放进交付包的 _未使用/ 目录并在对照表里列明。给报告员一个"这些我看到了但没用"的交代。
一条需要明确说清的红线
采集期绝对不能跑 OCR。连续 2~3 小时、数百次快门的现场作业，如果每张都跑识别，会带来：发热降频（相机变卡）、电量崩（续航从 4h 掉到 1.5h）、快门延迟（错失拍摄时机）。

这不是"优化"，是架构约束——所以采集页和 OCR 之间不能有任何代码路径。

  • 编码为空 → 跳过该行，计入"未导入 N 行"并展示行号（客户清单常有一个"合计"行）
  • 编码重复 → 默认保留首次出现，提示"第 37 行与第 12 行编码相同"。允许用户选"合并"或"重命名保留"
  • 编码含不可用于文件名的字符（/ \ : * ? " < > |）→ 自动替换为 _，并在交付命名时使用替换后的版本（数据库里保留原值，两者都要留）
  • 编码含全角字符 / 前后空格 → 归一化（trim + 全角转半角），并给出提示
  • 超过 5000 行 → 提示"清单异常大，是否确认？"（防误导入错文件）

5.3 分组与建议生成（后台 · 采集结束后）

这两个步骤都在采集结束之后、整理开始之前执行。它们是"整理页好不好用"的地基。

5.3.1 时序聚类（GroupingService）

输入：同一 capture_session 内、按 taken_at 升序的 photo 列表
规则：
  1. 相邻两张的时间间隔 ≤ 45 秒  → 归入同一组
  2. 单组张数上限 12 张（超出的开新组，防止"连续拍 40 张"糊成一组）
  3. 组张数下限 1 张（允许单张成组）
  4. 跨 capture_session 不合并
  5. source=album 的照片：若该 session 内 taken_at 全部相同或跨度 < 2 秒
     → 每张独立成组（时间戳不可信，不做聚类）
     否则沿用规则 1~3，但组标记 origin=album
输出：photo_group 记录（seq 按组内首张时间排序）
可修正：整理页提供 合并 / 拆分 / 移出 三个操作，改完即时重算

5.3.2 OCR 建议合成（SuggestService）

对每一组、组内每一张：
  1. 缩到长边 1600px 后送入 ML Kit（降分辨率以提速，仍足够识别印刷体）
  2. 得到 tokens：{ text, confidence, box(归一化), page }
  3. token 归一化
       · 全角→半角、去空白、去常见分隔符差异（连字符/下划线/点）
       · 仅在「数字段」内做形近纠偏：O→0  I/l→1  S→5  B→8  Z→2  G→6
  4. 与清单编码字典匹配，取最佳命中：
       完全相等            → base 0.98
       清单编码是 token 前缀 → base 0.86
       编辑距离 = 1        → base 0.88
       编辑距离 = 2        → base 0.72
       编辑距离 ≥ 3        → 丢弃
  5. 单张得分 = base × token_ocr_confidence × 位置权重(中心/大字号 1.0，边缘 0.85)
  6. 组级建议 = 组内按得分加权投票
       · 胜者 = 加权票最高者
       · 若第二名与胜者差值 < 0.15 → 组标记 conflict（提示人看一眼）
       · 若组内最高分 < 0.40 → 组标记 no_suggestion
输出：photo_group.suggested_item_id / suggestion_confidence / suggestion_evidence
关键：阈值不再决定"归不归"，只决定"标不标冲突"
这是 v3.0 与 v2.0 最本质的区别。v2.0 里 0.90 是"自动归档线"——跨过它就机器说了算。
v3.0 里，没有任何阈值能让机器直接写入归属。置信度只做两件事：① 排序（把最可能对的排在前面）② 标冲突（提醒人这里要留意）。

好处：OCR 精度的波动不再影响交付正确性。哪怕它今天整体偏保守（只敢给 0.5），人也不过是多看几眼；哪怕它今天整体偏激进（什么都给 0.95），人也还是每一条都看过。系统对 OCR 精度的依赖被彻底切断了。

5.3.3 预处理的可中断性

场景行为
用户直接进整理页若预处理未完成，页面顶部显示进度条「正在准备：识别 128/640」，已完成的组立即可操作，不做全屏阻塞
OCR 开关被关闭跳过 5.3.2，只做分组。整理页不显示任何建议，全部走手动指派。功能不缺失，只是变慢
ML Kit 初始化失败 / 机型不支持自动降级为"无建议模式"，顶部提示一次，不反复报错
用户在预处理中退出 APP任务持久化，下次进入继续；已完成的部分不重跑

5.4 对应货品流程 ★ 本方案核心

这是全案最重要的界面与流程。按真实规模（几百件 / 1200 张 / 持续一天），目标定为：覆盖率达标（≥80%）＋ 无未对应照片，全程 ≤ 30 分钟，可分多次完成。

v3.1 关键设计：两条路径，同一套数据（老板确认"两种都可能"）
路径 A · 现场随手清（拍一段就清一段）
  • 采集页有个不显眼的入口：「已拍 37 张 · 点此对应」。只在照片累积到一定数量（默认 20 张）后才出现，避免采集期被反复打扰。
  • 点进去只看这一批（最近这段连拍），几十张级别，几分钟清完。清完自动回到采集页。
  • 好处：记忆新鲜、认得出是哪件货；不用等到收工回顾上千张。
  • 代价：打断拍摄节奏。所以入口必须克制——绝不弹窗、绝不变红、绝不显示"待办 N 项"。
路径 B · 收工统一过
  • 白天只拍，收工后进整理工作台，按批次（Burst）从头到尾过一次。
  • 整理页支持断点续做：做到一半退出、第二天再来，进度一点不丢（每确认一组即时落盘）。

为什么两条路径不能各做一套界面：现场清的是一小段，收工过的是全部，但"看组 → 确认 → 落盘"的动作完全一样。共用同一套整理组件，只是数据范围（本批 / 全部）不同。这样 M3 只需实现一次。

v3.0 的 S5 是清清单缺口——列出所有没照片的货品，逐件标记「现场未见 / 补拍」。按真实规模，这意味着几百件里有 40~100 件要处理，光标记原因就要 15~30 分钟，而且必然做不完整。

v3.1 改成覆盖率闸门：
覆盖率判定界面行为
≥ 80% 达标 交付 Tab 亮起，缺口清单自动汇总进交付包，不需要任何人工标记。顶部只提示一句「清单 387 件 · 已拍 322 件 · 缺口 65 件（已写入对照表）」

< 60% 拦一下 红条提示，导出前必须显式勾选"我知道覆盖率不足"并填原因。这是防止"拍漏了一半还以为完事了"

S1 · 一键确认高置信

顶部按钮，点击后弹出一个可复核的列表（不是直接执行）：

「一键确认高置信」的执行条件
进入这个批次的组必须同时满足：
  • 组级置信度 ≥ 0.90
  • 组内所有照片的建议一致（没有 conflict）
  • 该货品当前还没有被其他组占用（一个货品只允许一个主组，冲突的会被排除）

弹层展示：「以下 74 组 · 213 张将被确认」+ 可横向滚动查看缩略图 + [全部确认] / [取消]。
这是整条链路里唯一的一次"批量信任"——但因为人看得到即将发生什么，它仍然是一个人类决策，只是批量的。

S2 · 逐块确认（相似建议合并）

剩余待确认的组，按建议货品聚合展示。3 个组都建议 GHI-3300 → 合成一张卡，标题「3 组 · 7 张 · 全部建议 GHI-3300」，一次点击确认全部。

为什么要把它们合并？因为预检员在现场对同一件货可能拍了两段（中间插了别的货），或者在两个位置拍了同一型号的不同箱。这些情况在清单一侧是同一个编码，合并展示能让人一次决策，而不是三次机械点击。

S3 · 处理冲突组

冲突组的卡片样式：
  [橙色左边框]  ⚠ 组内识别不一致 · 3 张
     ├ 第 1 张 → 建议 ABC-1024 (0.94)
     ├ 第 2 张 → 建议 ABC-1024 (0.91)
     └ 第 3 张 → 建议 XYZ-7788 (0.83)   ← 与组建议不同，高亮
  操作：[按多数确认 ABC-1024]  [逐张指派]  [拆分组]

设计意图：第 3 张很可能是"拍到了旁边那箱货"，或者是标签被遮挡后误识。
         不自动处理，而是把证据摊开让人 5 秒判断。

S4 · 处理无建议组

没有识别结果、或置信度过低的组。场景包括：标签反光/模糊/遮挡、手写标签、清单外的货、拍了空托盘或环境照。

人的动作结果
手动指派打开指派面板：候选列表（输入 2~3 字符即出）+ 搜索 + 扫码
创建为新货品清单外货品。只需填编码（可从照片 OCR 的原始文本里选一段预填）+ 名称，立即建立 item 并完成指派。这个新货品会出现在对照表里，标注"清单外"
标记为未使用环境照 / 废片。归入交付包的 _未使用/ 目录，不删
与相邻组合并拍照时走神，把一件货拍成了两段 → 选中相邻组，合并后重新指派

S5 · 看覆盖率是否达标 这是 v2.0 完全没有的能力

覆盖率仪表 + 缺口视图：从"清单"这一侧倒着看
前面的步骤都是"照片 → 找货品"。覆盖率视图反过来：看清单里的货，到底拍到了几成。 
清单 387 件 → 已对应 322 件 → 缺口 65 件 → 覆盖率 83.2%  [达标]

       DEF-2001 钢制法兰   ·  [补拍] → 跳采集页，拍完自动回来
       GHI-3300 塑料件     ·  [指派已有照片] → 从"未使用/无建议"照片里挑
       ...
  低于达标线时：
       [回去补拍]  或  [仍然导出]（需一句原因，如"部分货已被提走"）

为什么这个视图重要：它是唯一能回答「我是不是漏拍了哪件货」的地方。v2.0 完全依赖 OCR 成功识别才能知道某件货被拍了；只要 OCR 失败，系统就永远不知道那件货其实拍过、或者根本没拍。覆盖率视图把这个判断从"识别问题"变回了"清单比对问题"——100% 可靠。

⚠️ 与 v3.0 的区别：缺口不再是"必须逐件清理的待办"，而是一份如实交给报告员的信息——自动汇总进交付包的 _清单缺口.txt。原因由报告员与预检员线下确认，比在 APP 里挨个点选更准确。

S6 · 收尾

当顶部显示「覆盖率 ≥ 达标线 · 待处理 0」时，底部 Tab 的红色角标消失，交付 Tab 亮起引导。此时还剩一件事：池子里的"未使用"照片——它们不阻塞交付，会在打包时统一进 _未使用/。

整理流程的两条产品原则
  1. 随时可中断。每确认一组即时落盘。预检员可以整理到一半去接电话、退出 APP、第二天再来——进度一点不丢。这也是"现场随手清 + 收工统一过"两条路径能共用一套数据的前提。
  2. 无强制顺序。虽然默认引导 S1→S6，但任何一步都可以跳过。APP 不会"不让你走下一步"，只会在交付页汇总提示还剩什么。

为什么原始文件永不改名
交付包里的命名规范（{序号}_{编码}_{n}.jpg）是在打包时生成副本时应用的。本地原始文件保持不变，好处有三：

7.1 时序分组算法

lib/domain/grouping/grouping_service.dart
/// 把一次采集的照片按拍摄时序聚成组。纯函数，无副作用，可单测。
/// 分组只是"建议"——用户能在整理页手动合并/拆分，所以这里容错优先。
class GroupingService {
  static const gapThreshold = Duration(seconds: 45);
  static const maxPerGroup  = 12;

  List<List<Photo>> group(List<Photo> photos, {required String sessionSource}) {
    if (photos.isEmpty) return const [];

    // 相册导入且时间戳不可信（全部相同 / 跨度 < 2s）→ 每张独立成组
    if (sessionSource == 'album' && !_timestampsTrustworthy(photos)) {
      return photos.map((p) => [p]).toList();
    }

    final sorted = [...photos]..sort((a, b) => a.takenAt.compareTo(b.takenAt));
    final groups = <List<Photo>>[];
    var current = <Photo>[sorted.first];

    for (var i = 1; i < sorted.length; i++) {
      final prev = sorted[i - 1], next = sorted[i];
      final gap  = Duration(milliseconds: next.takenAt - prev.takenAt);
      final ok   = gap <= gapThreshold && current.length < maxPerGroup;
      if (ok) { current.add(next); } else { groups.add(current); current = [next]; }
    }
    groups.add(current);
    return groups;
  }

  bool _timestampsTrustworthy(List<Photo> ps) {
    final ts = ps.map((p) => p.takenAt).toSet();
    if (ts.length <= 1) return false;             // 全部同一时刻
    final span = ps.map((p) => p.takenAt).reduce((a, b) => a > b ? a : b)
                 - ps.map((p) => p.takenAt).reduce((a, b) => a < b ? a : b);
    return span > 2000;                            // 跨度 > 2 秒
  }
}

7.2 编码归一化与匹配

lib/domain/suggest/code_matcher.dart
/// 编码归一化 + 与清单字典匹配。这一步的产出是「建议」，不是「归属」。
class CodeMatcher {
  final List<ItemCode> _items;
  final Map<String, String> _normIndex;   // 归一化编码 → itemId

  CodeMatcher(this._items) : _normIndex = {
    for (final it in _items) normalize(it.code): it.id
  };

  /// 归一化：全角→半角、去空白、统一分隔符、数字段内形近纠偏
  static String normalize(String raw) {
    var s = raw.trim().toUpperCase()
      .replaceAll(RegExp(rr'[\s\-_·．。]'), '');          // 分隔符差异一律抹平
    s = s.replaceAllMapped(RegExp(r'[０-９Ａ-Ｚａ-ｚ]'),
        (m) => String.fromCharCode(m.group(0)!.codeUnitAt(0) - 0xFEE0)); // 全角转半角
    return _fixConfusables(s);
  }

  /// 形近纠偏：只在纯数字段内替换，避免把合法的 O/I/S 字母改坏
  static const _confuse = {'O': '0', 'D': '0', 'I': '1', 'L': '1',
                            'S': '5', 'B': '8', 'Z': '2', 'G': '6'};
  static String _fixConfusables(String s) {
    final buf = StringBuffer();
    var i = 0;
    while (i < s.length) {
      // 找出连续的数字段（含形近字符），整段一起纠偏
      final seg = RegExp(r'[0-9OODIILLSSBBZZGG]+').matchAsPrefix(s, i);
      if (seg != null && seg.group(0)!.length >= 2) {
        var t = seg.group(0)!;
        // 仅当段内数字占多数时才纠偏，否则认为是纯字母词（如 "BOX"）
        final digits = t.split('').where((c) => '0123456789'.contains(c)).length;
        if (digits * 2 >= t.length) {
          t = t.split('').map((c) => _confuse[c] ?? c).join();
        }
        buf.write(t); i += seg.group(0)!.length;
      } else { buf.write(s[i]); i++; }
    }
    return buf.toString();
  }

  /// 对一段 OCR 文本求最佳命中。返回 null 表示没找到像样的候选。
  MatchCandidate? best(String tokenText, double tokenConf) {
    final n = normalize(tokenText);
    if (n.length < 3) return null;

    // ① 完全相等
    if (_normIndex.containsKey(n)) {
      return MatchCandidate(_normIndex[n]!, 0.98 * tokenConf, 'exact');
    }
    // ② token 包含清单编码（照片上多识别出前后缀）
    for (final e in _normIndex.entries) {
      if (n.contains(e.key) && e.key.length >= 4) {
        return MatchCandidate(e.value, 0.86 * tokenConf, 'prefix');
      }
    }
    // ③ 编辑距离 1 / 2（用长度差预筛，避免全表算)
    MatchCandidate? bestCand;
    for (final e in _normIndex.entries) {
      final d = e.key.length - n.length;
      if (d.abs() > 2) continue;
      final dist = levenshtein(n, e.key, cap: 2);
      if (dist == 0) continue;
      if (dist <= 2) {
        final base = dist == 1 ? 0.88 : 0.72;
        final c = MatchCandidate(e.value, base * tokenConf, 'edit$dist');
        if (bestCand == null || c.score > bestCand.score) bestCand = c;
      }
    }
    return bestCand;
  }
}
形近纠偏的一个细节，值得单说
_fixConfusables 只在"数字占多数的连续段"里做替换。原因：如果无脑全局替换，BOX 会被改成 B0X、SL-100 会被改成 5L-100——反而制造错误。需要先判断这个 token 到底是"数字编号"还是"字母词"。

这也是 Q2（编码形态）必须问清的原因：纠偏表必须按真实编码规则来定，通用规则一定会在某个客户的编码体系上翻车。

7.3 组级建议合成

lib/domain/suggest/suggest_service.dart（节选）
/// 把组内每张照片的识别结果加权投票，得到组级建议。
/// 注意：产物写在 group.suggestedItemId / suggestionJson 上，
///       绝不写 group.itemId —— 那是人的领地（见 7.4）。
GroupSuggestion synthesize(List<PhotoOcrResult> results) {
  final votes = <String, double>{};
  final evidence = <String, List<String>>{};

  for (final r in results) {
    final cands = <MatchCandidate>[];
    for (final t in r.tokens) {
      final c = _matcher.best(t.text, t.confidence);
      if (c == null) continue;
      // 位置权重：位于画面中心区域 / 字号较大的 token 更可能是主唛头
      final pos = t.isCentral ? 1.0 : 0.85;
      final sz  = t.relativeHeight > 0.06 ? 1.0 : 0.9;
      cands.add(c.scaled(pos * sz));
    }
    if (cands.isEmpty) continue;
    cands.sort((a, b) => b.score.compareTo(a.score));
    final top = cands.first;
    votes[top.itemId] = (votes[top.itemId] ?? 0) + top.score;
    (evidence[top.itemId] ??= []).add('${r.photoIndex}:${top.mode}(${top.score.toStringAsFixed(2)})');
  }

  if (votes.isEmpty) {
    return GroupSuggestion.none();          // → group.suggestState = no_suggestion
  }

  final ranked = votes.entries.toList()..sort((a, b) => b.value.compareTo(a.value));
  final winner = ranked.first;
  final conf   = (winner.value / results.length).clamp(0.0, 1.0);
  // 组内分歧：第二名紧咬第一名 → 标 conflict，提醒人看一眼
  final conflict = ranked.length > 1
      && ranked[0].value - ranked[1].value < 0.15 * results.length;

  return GroupSuggestion(
    itemId: winner.key,
    confidence: conf,
    candidates: ranked.take(3).toList(),   // 交给 UI 做"改派"时的候选排序
    evidence: evidence[winner.key]!,
    state: conflict ? 'conflict' : (conf < 0.40 ? 'no_suggestion' : 'pending'),
  );
}

7.4 归属的唯一写入口

lib/domain/assign/assign_service.dart
/// 全应用唯一允许写 photo.itemId / group.itemId 的地方。
/// 每个方法都必须带 confirmedBy —— 这是"人做决定"原则的代码化。
class AssignService {
  final AppDatabase db;
  final String deviceName;   // 免登录下的最小身份标识

  /// 确认一个组的归属（用户点 ✓ 或 采纳建议）
  Future<void> confirmGroup(String groupId, {
    required String itemId,
    required String source,          // suggestion_confirmed / manual / bulk_confirm
    MatchCandidate? fromSuggestion,
  }) => db.transaction(() async {
    final now = DateTime.now().millisecondsSinceEpoch;

    // ① 吊销该组此前未吊销的决策记录
    await (db.update(db.assignments)..where((t) =>
        t.targetType.equals('group') & t.targetId.equals(groupId) & t.revokedAt.isNull()))
      .write(AssignmentsCompanion(revokedAt: Value(now)));

    // ② 写新的决策记录（必须先写记录，再改归属）
    await db.into(db.assignments).insert(AssignmentsCompanion.insert(
      id: _uuid(), projectId: _projectOf(groupId),
      targetType: 'group', targetId: groupId, itemId: itemId,
      source: source,
      suggestedItemId: Value(fromSuggestion?.itemId),
      suggestionConf: Value(fromSuggestion?.score),
      confirmedAt: now, confirmedBy: deviceName,
    ));

    // ③ 更新组与组内所有照片
    await (db.update(db.photoGroups)..where((t) => t.id.equals(groupId)))
      .write(PhotoGroupsCompanion(itemId: Value(itemId), confirmedAt: Value(now)));
    await (db.update(db.photos)..where((t) => t.groupId.equals(groupId)))
      .write(PhotosCompanion(itemId: Value(itemId), state: const Value('confirmed')));
  });

  /// 批量确认高置信组（"一键确认"）
  Future<int> bulkConfirmHighConfidence(String projectId, double threshold) async {
    // 一个货品只允许一个主组：已被占用的货品从候选里剔除
    final taken = await _assignedItemIds(projectId);
    final groups = await (db.select(db.photoGroups)
      ..where((t) => t.projectId.equals(projectId)
        & t.suggestState.equals('pending')
        & t.suggestionConf.isBiggerOrEqualValue(threshold))
      ..orderBy([(t) => OrderingTerm.desc(t.suggestionConf)])).get();

    var n = 0;
    for (final g in groups) {
      final iid = g.suggestedItemId;
      if (iid == null || taken.contains(iid)) continue;   // 冲突的跳过，交给人
      await confirmGroup(g.id, itemId: iid, source: 'bulk_confirm');
      taken.add(iid); n++;
    }
    return n;
  }

  /// 撤销（整理页可展开已确认列表撤销）
  Future<void> revoke(String groupId) => db.transaction(() async {
    final now = DateTime.now().millisecondsSinceEpoch;
    await (db.update(db.assignments)..where((t) =>
        t.targetType.equals('group') & t.targetId.equals(groupId) & t.revokedAt.isNull()))
      .write(AssignmentsCompanion(revokedAt: Value(now)));
    await (db.update(db.photoGroups)..where((t) => t.id.equals(groupId)))
      .write(const PhotoGroupsCompanion(itemId: Value.absent(), confirmedAt: Value.absent()));
    await (db.update(db.photos)..where((t) => t.groupId.equals(groupId)))
      .write(const PhotosCompanion(itemId: Value.absent(), state: Value('unassigned')));
  });
}
这段代码的注释就是设计文档
注意 confirmGroup 里的注释："必须先写记录，再改归属"。这个顺序保证了一个不变式——任何时刻都不存在"有归属但没有决策记录"的状态。如果反过来（先改归属、再写记录），中间崩溃就会留下一条无据可查的归属，而它可能流入交付包。

整个 v3.0 的正确性保证，就落在这一条顺序上。

7.7 WebDAV 上传队列

lib/data/webdav/upload_queue.dart
/// 上传是交付的旁路，不是必经步骤 —— 失败不影响分享。
class UploadQueue {
  static const backoff = [1, 5, 15, 60];   // 分钟
  static const maxAttempts = 5;
  static const maxParallel = 3;
  static const chunkSize   = 50 * 1024 * 1024;

  Future<void> pump() async {
    if (!_hasNetwork()) return;                    // 无网不消耗
    final batch = await _dueTasks(limit: maxParallel);
    await Future.wait(batch.map(_uploadOne));
  }

  Future<void> _uploadOne(UploadTask t) async {
    try {
      final size = File(t.localPath).lengthSync();
      if (size <= chunkSize) {
        await _client.writeFromFile(t.localPath, t.remotePath);
      } else {
        // 大文件分片：写 .part 后改名，兼容不支持 chunk 的服务器
        await _client.writeFromFile(t.localPath, '${t.remotePath}.part');
        await _client.move('${t.remotePath}.part', t.remotePath);
      }
      await _markDone(t);
    } catch (e) {
      final n = t.attempts + 1;
      if (n >= maxAttempts) {
        await _markFailed(t, e);                    // 转人工，不再重试
      } else {
        await _reschedule(t, n, backoff[n - 1]);
      }
    }
  }
}

指标 1 为什么可以做到 100%（这条不变，是本方案的地基）
因为架构上不存在"机器写归属"的路径。归属只能由 AssignService 写入，而它的每个方法都要求 confirmedBy。所以"交付包里有没有未确认的归属"不是一个统计概率问题，而是一个结构性问题——答案是恒定的"没有"。

这正是把 OCR 降级为"建议"带来的最大收益：正确性不再依赖 OCR 精度，只依赖代码结构。
指标 1 和指标 3 是两回事，不要混
指标管什么做不到会怎样
指标 1 · 归属完整性 照片和货品的对应关系有没有搞错 报告里张冠李戴 —— 致命，不可接受。所以是硬指标，且靠结构保证
指标 3 · 清单覆盖率 清单里的货拍到了几成 报告里少几件 —— 可接受（业务上 80% 就够），但要如实写进交付包

v3.0 把这两件事混在一起当成"都要 100%"，结果是把一个业务上可接受的缺口，做成了工程上不可承受的负担。v3.1 把它们拆开：对应关系必须绝对正确，覆盖率只要够用就行。

  ⚠️ 这一轮同时要拿到一个关键数字：真实覆盖率是多少？
     它决定「80% 达标线」是否要按客户/货种调整

第 2 轮（M4 后，接入 OCR 建议）
  目标：验证建议是否真的让人变快
  判据：建议采纳率 ≥ 80%、一键确认覆盖率 ≥ 60%、整理耗时降到 ≤ 20 min
  → 未达标则回到 M4 调优（改归一化规则 / 促精度），不动主干

第 3 轮（M6，上线前）
  目标：长时稳定性 + 真实环境覆盖
  判据：连续 5 次真实任务（含至少 2 次全天作业）无崩溃、
        WebDAV 上传成功率 ≥ 95%、微信分享成功率 ≥ 95%
  → 通过则正式分发
v3.1 新增一条灰度观测项：覆盖率分布
第 1 轮和第 3 轮都要记录每次任务的实际覆盖率，并观察：
观察结果说明什么
稳定在 80~95%正常。达标线 80% 定得合适，不必动
普遍 < 70%要么是业务本身就这样（那达标线要下调），要么是采集页有问题让人漏拍（那要改 APP 而不是改线）
普遍 > 95%业务实际能力比预期强，达标线可以上调，避免放行过于宽松
不同客户差异很大达标线需要按项目可配，不能写死在代码里

⚠️ 这也意味着：80% 这个数必须做成可配置项，写死在 constants.dart 里是一种偷懒。已按此调整 M3 的交付范围（见 §10）。
一条灰度纪律
第 1 轮必须先于第 2 轮完成，且第 1 轮不得开启 OCR。因为第 1 轮要验证的是"整理页到底好不好用"——如果同时开着 OCR，出了问题你分不清是"整理页设计不好"还是"OCR 建议不准"。先验证主干，再叠加增强，这是本方案排期的核心纪律。

最早可以灰度的时间点：第 5.5 周（M3 结束）
M3 结束时，APP 已经是一个完整可用的工具——采集、整理、交付三段全通，只是没有 OCR 建议（整理全手动）。这时候就可以让真实预检员用起来，而且用到的反馈能直接指导 M4 的 OCR 该往哪个方向做。

这是 v3.0 排期的最大好处：不必等 OCR 调好才能给人用。v2.0 因为 OCR 是主路径，不给 OCR 留出足够时间就不敢交付——整个周期被 OCR 的进度绑架。
v3.1 排期的一处风险提示
整体周期 不变（7.5 ~ 8 周），但判据的难度是显著上升的——M2 从 300 张变为 1200 张，M3 从 200 件/25 min 变为 400 件/45 min。

这不是把工期藏起来，而是把"通过"这两个字的含金量补齐：上一版的判据在真实规模下会轻易通过，但通过之后用户仍然不满意——那种"假通过"是排期里最危险的东西。

如果 M3 判定纯手动确实压不进 45 min，不要靠加班硬顶，直接按 R1 的第 ④ 条走：把 M4 的 OCR 投入加大。此时它是唯一剩下的杠杆。

11.1 风险登记

#风险等级影响缓解措施
R1整理页效率不达标头号高 这是本方案唯一的关键路径。按真实规模（几百件 / 上千张 / 持续一天），如果整理要 2 小时以上，用户会觉得"还不如自己拿文件夹归"——整个方案的价值就不成立了 ① M3 就灰度拿真实耗时数据，不留到最后 ② 八个提速手段逐个压测 ③ 批次（Burst）分组是这一版新增的主要杠杆——让整理按批推进，避免面对上千张的全局数字 ④ 若纯手动压不到 45 min，加大 M4 的 OCR 投入（此时它是唯一的杠杆） ⑤ 最后的退路：整理页拆成"只处理未对应"的极简模式
R1b长时作业下的资源与稳定性v3.1 新增高 一天连续作业、上千张照片累积，可能出现内存持续增长、缩略图缓存撑爆、SQLite 变慢、发热降频 —— 这些在 1 小时的测试里看不出来 ① 缩略图一律降采样落盘，不常驻内存 ② 整理页用分页查询，不一次性加载全部 ③ 列表虚拟化，只渲染可见项 ④ 必须做 8 小时连续作业实测（见指标 10），不能只做短时压测 ⑤ 感知到发热/低电时主动提示，并提供标清采集模式
R1c覆盖率达标线定错v3.1 新增中 80% 是我们从"通常能到 80% 以上"反推的。如果定太高，会逼着人为了凑数去拍无意义的照片；定太低，会放行明显不足的批次 ① 做成按项目可配，不写死 ② 灰度期收集实际覆盖率分布（见 §9.3） ③ 界面提示措辞用"低于常见达标线"而不是"不达标"——APP 不替业务下判断
R2分组算法不符合现场拍摄习惯中 45 秒阈值定错 → 组过碎（人要点很多次）或过粗（一组混了多件货） ① 分组结果只是建议，可手动修正，不会导致错误归属 ② 埋点统计人工修正率，超过 25% 就调参数 ③ 45 秒是初始值，灰度后用真实数据重定
R3OCR 建议质量差，形同虚设中 采纳率低 → 用户觉得建议是噪音，甚至要求关掉 ① 不影响交付正确性（这是架构保证的，不是缓解） ② 设置里可一键关闭，界面立即清爽 ③ 采纳率 < 60% 时主动建议用户关闭，别硬撑
R4Android 相机碎片化中 某些机型对焦慢、连拍卡、EXIF 时间缺失 ① 锁定 2~3 款配发机型优先适配，不追求全机型覆盖 ② 提供"兼容模式"（降分辨率、关连拍） ③ EXIF 缺失时退化用文件时间
R5PDF 联系表体积过大中v3.1 调级 按真实规模，1200 张照片的联系表可能 100~250 MB，微信传输基本不可用 ① 联系表用缩略图（长边 1200px），并提供"精简版"（长边 800px） ② 默认按批次/货品大类分册输出多份 PDF，避免单文件过大 ③ 超过 50MB 时明确提示改走网盘 ④ 实测体积后再定默认档位
R6微信分享大文件失败低 原始照片 ZIP 按真实规模可能 2 GB+ ① 主推 PDF 联系表（微信直传首选） ② ZIP 走 WebDAV ③ 分享前显示体积并给出建议
R7存储空间不足中 一次预检可能产生 1.5~3 GB 照片 ① 采集前预检空间 ② 提供"上传后清理原图" ③ 提供标清采集模式
R8用户绕过整理直接交付低 为赶时间，带着一堆未确认的照片就生成交付包 ① 交付页显性提示"未确认 N 张"，但不硬拦（尊重现场判断） ② 对照表和 PDF 上标注未确认项 ③ 宁可有标记的不完整，也不要无标记的错误
R9卸载导致数据丢失低 文件在私有目录，卸载即失去 ① 设置里提供"导出项目备份" ② 交付后引导用户立即上传 WebDAV 作为异地备份

11.2 开放问题

#问题影响为什么需要你拍板
Q1货品编码长什么样？（含不含中文、有无固定前缀/长度/校验位、是字母还是数字为主） 高 决定 §7.2 的归一化规则与形近纠偏表。通用规则一定会误伤某些客户的编码体系——比如给 BOX-001 做 O→0 纠偏就错了。这是 OCR 建议质量的分水岭。
Q2单次预检的典型规模 已答 ✅ 09-23 已确认：几百件货 · 每件原则上 2 张 · 预检+拍照持续 1 天 · 覆盖率 80% 以上即可满足要求。已据此把验收指标改为按真实规模分档（§9.1），并把达标口径从"100% 对应"改为"覆盖率 ≥80%"（§5.4）。
仍需补充：具体是 200~300 还是 600~800？这决定性能压测的档位，但不阻塞开工。
Q3后端报告员期望的交付格式，是否有固定的包结构模板？ 高 决定 §5.5 的目录命名与 PDF 联系表版式。如果报告员有现成模板，我们应该直接对齐，而不是自创一套让他再改一遍。
Q4清单里"有货但没拍照"的缺口，是否需要出现在正式报告里？ 中 我的判断是必须出现——它是报告里"未装/短装"结论的直接依据。但需要确认后端报告模板里有没有承接这个信息的位置。
⚠️ 注意 v3.1 已把措辞从「现场未见」改为「缺口」（见 §5.5）——因为"现场未见"替业务下了判断，而缺口的原因是多样的：货未到、已被提走、压在垛底、漏拍，性质完全不同。这个问题要问的其实是"缺口清单该以什么口径进报告"。
Q5每件货默认拍几张够用？（当前默认 2 张） 已答·采纳 ✅ 09-23 已确认：原则上每件 2 张——当前默认值即为 2，无需改动。但仍保留"张数少于 N 张"的提醒能力（按项目可配），用于发现个别货品拍漏了的情况。
Q6配发的手机型号？是否统一采购？ 中 决定相机适配的重点机型与"兼容模式"的必要性。统一机型能省掉大量适配成本。
Q7WebDAV 由公司提供（Nextcloud/群晖）还是用坚果云等第三方？ 低 影响限流适配与并发参数。私有云可控性高但需要配外网访问（域名 + HTTPS）。
Q8是否需要多人协作同一项目（如两人分区域拍）？ 低 若需要，采集批次要加"操作人"维度，WebDAV 上要做合并。当前设计是单机单项目，多人协作需要额外设计——建议第一期不做。
下一步建议
最需要你提供的东西（半天内就能给出结论）：
  1. 2~3 份真实货品清单 Excel（用于验证导入向导与列映射的健壮性——按几百件量级，最好有一份"列名不规范"的）
