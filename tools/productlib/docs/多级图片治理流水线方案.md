# 多级图片治理流水线・详细方案

> 版本：v1.0・2026-10-16
> 范围：产品库（productlib）图片治理子系统
> 目标：用「小模型分类铺底 + 检测裁剪提码 + 大模型兜底读手写码」替换当前「全图大模型分类 + 读码」，降低 API 成本、提高吞吐、保住手写码召回。



***

## 1. 背景与问题

### 1.1 现状

当前治理管线（`pipeline.py` → `govern_one`）对每张照片做：



```
整图 → 多模态大模型 classify() → 整图 PP-OCRv6 → 整图多模态 describe() → 关联
```

已落地的能力：



* 多模态大模型（Qwen-VL）一次调用同时返回 kind /usage/sup\_tag / 置信度

* PP-OCRv6 全量 OCR，token 落 `ocr_tokens` 表

* 多模态读码 + 描述 + 标签结构化 meta（name/spec/brand/material/unit/category）

* OCR 缓存 + 视觉缓存（`_ocr_cache.json` / `_vision_cache.json`）

* 自动关联阈值 `AUTO_LINK_THRESHOLD=0.70`，人工否决落 `cand_reject`

### 1.2 实测痛点



| 痛点                 | 数据                                     | 影响                          |
| ------------------ | -------------------------------------- | --------------------------- |
| 每张都付一次大模型分类钱       | 2737 张 × classify ()                   | 重跑治理成本高                     |
| 934 张 OCR 零 token  | 占 34%                                  | 其中大量是手写 / 反光标签，OCR 印刷体模型读不出 |
| 大模型读手写码成功率高但贵      | 抽样 12 张全部救回                            | 这是手写码**唯一**可靠路径             |
| 标签贴在产品上时整图送大模型     | token 浪费在背景上                           | 裁剪后可省 60%+ token            |
| 监装照片（209 张）也走大模型分类 | 没必要                                    | 小模型二分类即可                    |
| 标注有噪声              | packing\_list/packaging/label 三类系统性误分类 | 直接训会学错                      |

## 3. 分类体系设计

### 3.1 现有字段映射

保持现有 `photo_kind` / `photo_usage` / `supervision_tag` 三列不变，小模型预测值写入与大模型同列，但带 `model` 字段区分来源。



| 小模型输出                   | 写入字段                               | 说明              |
| ----------------------- | ---------------------------------- | --------------- |
| 监装 / 预检                 | `photo_usage`                      | 复用现有列           |
| kind（label/product/...） | `photo_kind`                       | 复用现有列           |
| kind\_conf              | `kind_conf`                        | 复用现有列           |
| 监装细分                    | `sup_tag_ai`（不写 `supervision_tag`） | 报告只认人工确认列，硬规则不变 |

### 3.2 新增子类：贴标产品照

**为什么要加**：实测大量照片是 "标签贴在金属件 / 软管 / 卡箍上" 的特写 —— 既不是纯标签卡（label），也不是纯产品外观（product）。现有数据里这类被混在 label 里。

**处理方式**：第一版不新增 `photo_kind` 枚举值（避免动 schema），而是在 `label` 类下用 `vision_meta` 里新增一个字段 `on_product: true/false` 标记。第二版数据足够时再考虑拆成独立类。

### 4.2 清洗规则

基于已完成的 contact sheet 目检，三类系统性误分类的修正规则：



1. **packing\_list → 其他类**：画面主体是物料 / 工件特写、不是打印的表格页 → 改为 `product` 或 `label`

2. **packaging → scene**：缠绕膜包裹的托盘 / 堆货远景，看不清产品 → 改为 `scene`

3. **label → product**：带白色铭牌标签的黑色零件本体特写，标签只是零件上一个贴条 → 保留 `label`（因为要读码），但 `vision_meta.on_product=true`

## 5. 模型训练

### 5.1 技术选型



* **框架**：PyTorch（已安装，需 `PYTHONPATH` 指向 user site-packages）

* **骨干**：MobileNetV2（迁移学习，ImageNet 预训练）

* **导出**：ONNX（推理时不依赖 PyTorch，用 onnxruntime）

* **输入尺寸**：224×224

* **增广**：水平翻转、随机裁剪 90%、色彩抖动、旋转 ±15°

### 5.2 训练脚本

复用已有的 `training/train_classifier.py`，改造点：



* 支持多任务头：同时输出 usage（2 类）+ kind（4 类）

* 数据从 `training/dataset/` 读取，目录结构 `train/{label}/xxx.jpg`

* 训练分两阶段：


  * Stage 1：冻结骨干，只训分类头（10 epoch）

  * Stage 2：解冻最后 3 层，微调（20 epoch，lr 降 10 倍）

### 5.3 模型文件位置



```
tools/productlib/models/
  usage_cls.onnx          # 二分类：监装/预检
  kind_cls.onnx          # 预检四分类
  supervision_cls.onnx   # 监装细分（第二阶段再训）
```

加载用 `onnxruntime`，懒加载（首次用到才加载，不阻塞启动）。

### 5.4 验收指标



| 模型    | 目标 val\_acc | 关键指标                        |
| ----- | ----------- | --------------------------- |
| 二分类   | ≥95%        | 监装召回 ≥90%（漏监装 = 报告少图）       |
| 预检四分类 | ≥85%        | label 召回 ≥90%（漏 label = 漏码） |
| 混淆矩阵  | 必出          | 重点看 label↔product 误判        |

## 6. 流水线改造细节

### 6.1 新增模块 `govern_classifier.py`

封装小模型推理：



```
# 接口设计
def classify_usage(image_path) -> (usage: str, conf: float) | None
    """二分类。模型未加载/未训练时返回 None，调用方降级到大模型。"""

def classify_kind(image_path) -> (kind: str, conf: float) | None
    """预检四分类。同上。"""

def detect_label_region(image_path) -> list[bbox]
    """PaddleOCR DB detector 框出文字区域。返回坐标列表。"""
```

### 6.2 改造 `pipeline.py:govern_one`



```
def govern_one(con, photo, index, use_vision=True, use_ocr=True):
    # ── ① 小模型二分类（新增）──
    usage_ai = govern_classifier.classify_usage(photo['path'])

    # ── ② 小模型预检四分类（新增），监装走大模型 sup_tag ──
    if usage_ai == '预检':
        kind_ai = govern_classifier.classify_kind(photo['path'])
    else:
        kind_ai = None  # 监装类不进预检四分类

    # ── 置信度降级链（核心）──
    # 小模型 conf < 0.80 → 走大模型 classify()
    # 小模型 conf ≥ 0.80 → 直接用，不调大模型（省 API）
    if kind_ai and kind_ai[1] >= 0.80:
        kind, conf = kind_ai
        model = 'onnx_kind'
    else:
        # 走原有大模型 classify() 路径
        kind, conf, ... = classify(con, photo, use_vision)

    # ── ③ 标签区域检测裁剪（新增，只对 label 类）──
    crops = []
    if kind == 'label':
        boxes = govern_classifier.detect_label_region(photo['path'])
        crops = [crop_image(photo['path'], b) for b in boxes]

    # ── ④ OCR：先整图跑（已有），再对裁剪小图跑（新增）──
    # 整图 OCR 结果保留（向后兼容）
    # 裁剪小图 OCR：印刷码命中率更高
    for crop in crops:
        texts = run_ocr_on_crop(crop)
        # 匹配码，命中则记 hit

    # ── ⑤ 多模态读码：降级触发 ──
    # 条件：(a) label 类且 OCR 没命中精确码  (b) 手写码样本
    # 此时送的是裁剪小图而非整图 → token 省 60%+
    if kind in ('label', 'unknown') and not hit_codes:
        for crop in crops or [photo['path']]:
            d = vision.describe(crop, expect_codes=True)
            # 读码 + meta

    # ── ⑥ 关联（原有逻辑不变）──
    ...
```

### 6.3 缓存策略

新增两个缓存表 / 文件：



| 缓存                 | key                           | value               | 失效条件         |
| ------------------ | ----------------------------- | ------------------- | ------------ |
| `_onnx_cache.json` | path + mtime + model\_version | (usage, kind, conf) | 换模型自动失效      |
| `_crop_cache.json` | path + bbox\_hash             | 裁剪小图 OCR 结果         | 不失效（裁剪是确定性的） |

## 7. 手写码专项处理

### 7.1 现状



* PP-OCRv6 是印刷体模型，手写码召回率极低（934 张零 token）

* 多模态大模型（Qwen-VL）能读手写码，抽样 12 张全部成功

* 现有 `DESCRIBE_PROMPT_CODES` 已设计为支持手写码读取

### 7.2 流水线中的位置



```
label 类照片
  ├─ 整图 OCR → 命中码？→ 是 → 直接关联（省 API）
  │                          → 否 → 继续
  ├─ 检测裁剪 → 裁剪小图 OCR → 命中码？→ 是 → 直接关联
  │                                      → 否 → 继续
  └─ 裁剪小图送多模态 → 读手写码 → 关联
```

### 7.3 Prompt 调整

`DESCRIBE_PROMPT_CODES` 已有 "手写编码也要尝试读" 的指令。新增一条：



```
- 标签可能贴在金属/塑料/纸箱表面，有反光、污渍、倾斜，请结合上下文猜测字符形状
- 如果数字之间有连笔或空格，按正常编码格式补全（如 10 50 47 05 00 01 → 105047050001）
- 末尾字母（A/B/C）可能是手写潦草的，仔细辨认
```

## 8. 降级策略（硬要求）

任何一级失败都不能阻断流水线：



| 故障点                         | 降级行为                            |
| --------------------------- | ------------------------------- |
| ONNX 模型文件不存在                | 小模型函数返回 None → 走大模型 classify () |
| ONNX 推理报错                   | 同上                              |
| PaddleOCR detector 没检测到文字区域 | crops 为空 → 整图 OCR               |
| PP-OCRv6 不可用（缺 cv2）         | 原有逻辑已有降级                        |
| 多模态 API 不可用                 | 只留 OCR 结果，多模态字段为空               |
| 裁剪小图送多模态超时                  | 重试一次，失败则退回整图送                   |

**原则**：小模型是加速器不是依赖。没有它系统照跑，只是变慢变贵。

## 9. 性能与成本预估



| 指标              | 现状              | 改造后                                 |
| --------------- | --------------- | ----------------------------------- |
| 每张分类成本          | 1 次大模型 API      | 小模型本地 0ms，conf≥0.8 时不调 API          |
| 大模型调用次数（2737 张） | 2737 次 classify | 估计 500\~800 次（只对低置信 + label 未命中码的图） |
| 多模态读码 token     | 整图 1024px       | 裁剪小图～400px，省 60%                    |
| OCR 时间          | 249 张 ≈700s     | 整图 OCR 不变，裁剪小图额外 +20%               |
| 重跑治理成本          | 全量重付 API        | 缓存命中 + 小模型本地，接近 0 成本                |

## 11. 风险与应对



| 风险               | 概率 | 应对                            |
| ---------------- | -- | ----------------------------- |
| 小模型在生产数据上分布偏移    | 中  | 保留大模型兜底，小模型 conf<0.8 就降级      |
| 清洗脚本误改正确标注       | 中  | 清洗前导出备份，清洗后人工抽检 10%           |
| 检测裁剪框错区域，漏掉真标签   | 低  | 没检测到 → 回退整图 OCR（不丢码）          |
| 手写码多模态读错（A/B 混淆） | 中  | 自动关联阈值不变 0.70，错码进人工候选不自动写     |
| 模型文件打包进 exe 后路径错 | 低  | 复用 paths.data\_dir () 模式，不硬编码 |

## 12. 验收标准
