## ①的另一半根因：逐张连拍「两两一组」（v0.17.1）

老板复测 v0.17.0：不点补充照片，直接连拍 4 张，分成两组（期望一组）。

### 机理（与 10-08 的补拍拆组是**两条不同路径**）
相机**每拍一张**触发一轮 regroup，旧口径「只回收单张组」追不上逐张节奏：
{1} → 回收成 {1,2} → 第 3 张的 regroup 不敢动 2 张组 → 新组 {3} → {3,4}
→ 最终「两两一组」。逐张推演与老板看到的完全吻合。

### 修法：回收口径收紧为「整批重聚」（这才是「一批一组」的正确展开）
活跃批次（本轮有游离照片落下的批次）内，未指派 + 未指定箱号 + 未保护的
**全部**组，连同游离照片整批重聚。三道边界：carton IS NULL（人工痕迹）/
itemId IS NULL（归属地盘）/ _protectedGroups（补拍）。且**只动活跃批次**
—— 整理阶段无游离照片 → regroup no-op → 手动成果天然安全。

### 关键推论：回收只作用于活跃批次
跨批次的老组不再被别的批次的 regroup 碰 —— 旧口径会跨批回收单张组，
反而违反「一批一组」。附带效应：「无保护单张组被任意批次回收」的旧行为
消失，补拍保护的真实战场收窄到**同批续拍**（5 分钟窗口内）。

### 测试口径修正（3 条旧断言守护的正是 bug 行为）
- 「同批续拍新照片只进新组」「同批可立第二组」—— 旧断言前提=拆组 bug 行为，
  改为断言整批重聚（同批=一组）。
- suggest_pipeline「rerunProject 跳过已归属」：第二组用 startSession 续接了
  同一批次 → 新口径下两组并成一组 → confirmGroup 把 4 张全归属 → n=0。
  修法：回拨 endedAt 造真两批（裸 SQL，该文件刻意不 import drift）。
- 新增 3 条：逐张连拍复现真机节奏 / 箱号组不重聚 / 归属组不重聚。
- **探针**：改回 photoCount<=1 旧口径 → 4 条红全是整批重聚用例，箱号/归属
  保护用例依旧绿 → 理由逐条正确。

## 「拍照时没有看到 0.6x 的焦距选项」（v0.17.2）

### 物理事实（先立住，别再去找"软件缩小"）
数码变焦**只能放大**；视野变宽**只能换镜头**。camera 插件 Android 端走
`camera_android_camerax 0.6.19`，minZoom = CameraX `ZoomState.minZoomRatio`：
超广角只有被**聚合进 logical 主摄**时才会 <1；否则系统只暴露一颗后置，
插件层拿不到 0.6x。（`CameraDescription.name` 是 `Camera N` 下标，不是
Android cameraId，所以自己按 cameraId 构造 description 无效。）

### 两条真因
1. **缩小档写死 0.6**：`zoomStepCandidates` 里的 0.6 在 `minZoom=1.0` 时被
   过滤，界面**什么都不说** → 人只看到"少了这个功能"。写死一个数字 =
   许诺一个按下去没反应的按钮。
2. **档位条只认"能放大"**：显示条件 `maxZoom > 1.05` → 只能缩小的机型
   （min<1、max≈1）整条档位都不出现。
3. 附带：能力同步三处各写一遍且只同步 max 不同步 min —— 这类漂移就是
   "档位消失"的温床。

### 修法
- 缩小档**只认设备上报的 minZoom**（一位小数）：能到 0.6 显示 0.6x，只能
  到 0.7 就显示 0.7x，不能缩小就不出档（宁可不画，不画假档）。
- 档位条条件放宽为"能放大**或**能缩小"。
- **换镜头才是 0.6x 的真身**：后置 ≥2 颗时档位条上方出「镜头N」按钮，
  在**后置之间**循环（`switchCamera()` 是全部镜头循环，会切到前置，不能
  用）。文案不写"广角"——副摄是广角还是长焦由硬件决定，猜错就是把人往
  更窄的画面上引。
- 能力同步收口 `_syncCameraState`（开相机/换镜头/换画幅共用一份）。
- 相机设置面板写**本机镜头能力**：几颗后置 + 变焦范围；没有可换广角时
  明说原因并给下一步（后退取景 / 系统相机广角拍完走相册导入）。功能
  缺失可以，**静默缺失不行**。
- 每次开控制器落日志：`lens名 + 变焦范围 + 后置镜头数` —— 下次"为什么
  没有 0.6x"可直接判定是硬件不支持还是入口没给。

### 测试
变焦档位 6 条（0.6/0.7/0.5/0.62/0.95 不给档/只能缩不能放）+ 后置镜头
轮换 6 条（主→副、副→主、三颗顺序、前置回后置、只有一颗→-1、无后置→-1）。
全量 **430 条**全绿；analyze No issues found；架构 PASS。

## 产品库性能优化方案（实测）—— outputs/产品库性能优化方案.md

老板反馈「系统卡顿、响应慢」。**没有猜，先把真实库只读备份到临时目录跑了基准**
（真实库一律 `mode=ro` + backup API 做副本，写入只在临时副本；缩略图基准输出也写临时目录）。

### 实测基线（可复用）
- 库仅 **4.9MB**：photos 2738 / ocr_tokens 17874 / checklist_rows 1113 / links 1041 / products 786。
- **列表查询 0.9ms（首页）/ 17.1ms（OFFSET 2600）**；接口本身不慢。
- `photos` **没有 taken_at 索引** → 每次 `ORDER BY taken_at` 全表扫描 + 临时排序树。
  加 `CREATE INDEX idx_photos_taken` 后 **0.4 / 0.5ms（末页 32.9x）**，**建索引只需 8ms**，
  taken_at 无 NULL（0/2738）。**性价比最高的一条。**
- `synchronous=FULL` → 提交 1.30ms/次；改 **NORMAL → 0.04ms（37.1x）**（OFF 无额外收益）。
  ✅ 但别夸大：2738 张才省 3.5s，相对治理是 0.05%，价值是**降写抖动**不是提速治理。
- 冷缩略图 54–72ms/张；加 `Image.draft()` 只到 **1.3–1.4x**（不是数量级），
  且 2356/2738 已预热（缺 382）→ **不是主因**。
- 列表已分页(limit=60)、缩略图已落盘缓存、视觉已压缩+关 thinking(32s→2.5s)、
  `_photo_out` 无 N+1 —— 这些都是对的，**别当优化目标改坏**。

### 结论
**数据库不是瓶颈**（4.9MB/0.9ms），**不要换 DuckDB/Postgres**（呼应之前那次替代方案讨论）。
根因判断：**治理用进程内 `threading.Thread` 跑**（govern.py:51-54），
OCR 2.8s/张 × 2738 ≈ 2.1h 占满 CPU/GIL → 治理期间页面被饿死 = 用户感知的「卡顿」。

### 收益最大的一条：视觉分类没缓存
`govern_one`(pipeline.py:138) **每张无条件调视觉 HTTP**，而 OCR 有 `_ocr_cache`
（注释自述「治理必然反复调，不缓存每次付 12 分钟」）—— 这判断只覆盖了 OCR。
且 `_call` 已设 `temperature=0`、结果稳定，天然可缓存。
按 `file+模型+prompt版本` 缓存即可，Key 必带模型/prompt 版本否则换模型后是静默错误。

### 其余
- `save_ocr_cache()` 每 25 张对全量做 sorted + `json.dump(indent=1)` → O(缓存总量) 重复 ~110 次。建议迁 SQLite 增量写。
- 每张一次的 `UPDATE govern_state='running'` 无消费者，纯浪费写。
- `/thumb/` 无 Cache-Control（no-store 中间件只管 /static/）→ 回访重拉 60 张图。
- `foreign_keys=0`（schema 写了 ON 但 connect 没设）—— 正确性项，非性能。

### 未做/受限
端到端治理基准**不能碰**：会写真实库 + 消耗视觉 API 额度。方案里已标清
「实测 / 代码内既有实测 / 静态推断 / 架构级推断（需验证）」四类可信度。

## 实施性能优化方案（老板一句「实施」，方案已回填 outputs/产品库性能优化方案.md）

**6 条低/中风险的都做了，唯独最高档那条(P0-A)没动。**

### 已实施 + 验证（全部隔离在 PL_HOME 临时目录，真实库没碰）
- **视觉分类缓存（最高价值）**：`classify` 每张都发视觉 HTTP，OCR 有缓存它却从来没有。
  key = `路径 + 模型 + prompt内容哈希 + 文件(体积,mtime)`。
- `photos(taken_at)` 索引（写进 SCHEMA，`IF NOT EXISTS`）：存量库自动建出 7→8 个，
  执行计划去掉 `USE TEMP B-TREE FOR ORDER BY`，**末页 18.8→0.7ms（28.8x）**，
  二次连接仍只有 1 个索引 → 幂等。
- `PRAGMA synchronous=NORMAL`：读回 = 1。
- 治理改 25 张一批提交 + 删掉每张的 `UPDATE govern_state='running'`
  （动手前 grep 确认全库无读取方，只有 `_GOVERN` 那个内存状态字典同名）。
- OCR 缓存去 `indent=1` 与 `sorted()`（迁 SQLite 增量写留后续）。
- 缩略图 `Image.draft()` + `/thumb/` 加 `Cache-Control: max-age=2592000`。
- **回归**：20 个专项测试 + units 全过；server 正常装载（84 路由）。

### 🔴 两条通用教训（别处也会踩）
1. **prompt 版本要用「内容哈希」**：`hashlib.sha1(CLASSIFY_PROMPT)`，
   别手写 `'v1'` 常量 —— 手写迟早「改了 prompt 忘了 bump」，那就是用错还不报错。
   也**不能用内置 `hash()`**：对 str 每次进程随机（PYTHONHASHSEED），
   key 每次都不同 → 缓存永远不命中。已实测两次独立进程算同一 key 完全一致。
   同理**换模型必须进 key**，否则换模型后静默沿用旧结果。
2. **工作区有并发会话**：打开就看到 `app/pubspec.yaml` + organize_page.dart /
   project_console_page.dart + CHANGELOG.md 已被人改了（Flutter v0.17.2 那边的）。
   全程没碰，也**没有提交** —— 提交必须按路径限定（`git add tools/productlib/…`），
   别用 `git add -A` 把别人的成果吞进去（RELEASE.md 早就警告过这条）。

## v0.17.4 半按对焦（现场快拍）—— 真机反馈「拍照时需要能够快速对焦」

### 核心：把 AF 提前到"手指按下→抬起"这段白等的时间里
CameraX 在快门后自己会跑一次 AF 再出片，暗处/低对比（外包装、木箱、唛头）
要几百毫秒；按下→抬起本来就白等 → `prepareFocus()` 在**按下瞬间**触发一次
AF（复用上次点过的对焦点，否则中心），抬手即拍。不动曝光（按下瞬间明暗跳
一下很吓人）、不画框（焦点不是用户主动选的）、350ms 节流（连拍每 400ms
一张，重复触发只会让 AF 反复重启更慢）。

### 🔴 铁律：预对焦回调必须走 Listener，不能走 GestureDetector.onTapDown
快门同时认单击/长按/横滑 → 它们进**手势竞技场**分胜负，手指落下那一刻胜负
未定，`onTapDown` 会被压到竞技场结束（即抬手）才回调 —— 那正好把想抢的时间
原样浪费掉。**Listener 拿原始 pointer 事件、不进竞技场、不消费事件**，落下
即时回调；子 GestureDetector 照旧判单击/长按/横滑。
（这条是**测试抓出来的**：一开始写在 onTapDown 里，widget 测试 `startGesture
+ pump` 后 prepared=0 —— 静态检查与肉眼都看不出来。）

### 其余改动
- 换镜头/换画幅/切前后摄后**清空 `_focusPoint`** 并显式 `setFocusMode(auto)`
  —— 否则镜头一直盯着上一件货的位置，换一件还得再点一次屏幕。
- 对焦框黄（对焦中）→ 白（已合焦）：暗处/低对比光靠看画面判断不出有没有合上焦。
- 相机设置面板写明对焦行为（连续追焦 + 半按 + 点屏指定）。

### 验证

- **探针**：把 Listener 的 onPointerDown 改 null →「按下即预对焦」「连拍第一下」
  2 条红、禁用态仍绿 → 理由正确才恢复。

## v0.18.0 拍照链路体检（对标系统相机，整体改造）

不是"对焦慢"这一件事 —— 通读后发现整条链路有系统性缺陷。

### 🔴 核心：拍照流水线（连拍丢照片 + 每按一下顿一下）
原来 `_shoot` 是一条完整 await 链：取帧 → 写 4~8MB → 入库，`_capturing`
全程占着。两个现场后果：
- **连拍静默丢张**：`burst()` 固定 400ms 发起下一张，上一张常没落完 → 走
  `skipIfBusy` 丢弃。按 20 下实际十几张，顶部张数照涨，看不出来。
- **主 isolate 卡**：`writeRaw` 在主线程 writeAsBytes+flush。

改法：`_capturing` 只覆盖取帧；`writeRaw` 搬到 `Isolate.run`（写盘同步、
后台 isolate —— 铁律 13 的落点）；落盘+入库进新 `core/serial_queue.dart`
（串行保 seq 顺序，错误不掐断链，`drain()` 前置防丢图）。
`endSession`/`dispose` 都必须 `await _sink.drain()`，否则最后几张在关批次后
才落库 → 文件在、库里没有 = 交付缺口。

### 其余改动
- 连拍锁焦（点过对焦点才锁）：一批一组=同一件货，连拍中途追焦只会拍糊。
  顶部显示「连拍中 · 锁焦」，不藏起来。
- 快门黑闪（14%/120ms）：戴手套单手靠"咔嚓+画面一暗"判断拍没拍上。
- `CaptureService.errorStream` + `CaptureError.hint`（文案住 domain，UI/日志
  共用一份）：保存失败→停采集+查存储；没拍成→再按一次；连拍丢张→报 N 张。
- 结束采集时如实说「正在保存 N 张…」。

### 教训
- ⚠️ `File.writeAsBytesSync` 返回 **void**（不是 File，那是异步版）→ analyze
  报 use_of_void_result 才暴露。
- 长按连拍**没调速**：拿掉的是卡在磁盘的时间，不是加快节奏 —— 节奏太快会糊片。

### 验证
新增 serial_queue_test 10 条；全量 **448 绿**、analyze 绿、架构 PASS。

## 两个新需求：建柜记住上次输入 + 选图看大图/自动策略

### 需求① 建柜预填（客户 / Inspector / Location）
**不新增表、不新增配置文件、不落 localStorage** ——「上次输入」= 最近一次建柜
那条记录的取值（containers 表本来就有这些列）。再存一份 = 两份真源必然漂移
（用户事后改了柜信息，默认值还停在旧值）。跟着 data\ 走，换浏览器/换机器都不丢。
- `GET /api/containers/form-defaults` → `{last, recent, from_container}`。
  🔴 **路由顺序**：必须声明在 `/api/containers/{cid}` **之前**否则被 `{cid}` 吃掉。
- 只带 client_name/inspector/location；**柜号/封条号/到离柜时间绝不带**
  （这三个每次必变，自动带入就是替用户猜）。
- 提示语**只列真正填上的字段** —— 说「已带入客户/Inspector/Location」
  而实际只带了客户，是句假话。
- `recent` 给历史取值下拉（去重、最近优先）：客户/地点常在几个固定值间切换，
  只记「上一次」不够用。
- 顺带把 `modal.js` 脏值判定从「非空即脏」改成**与初值快照比对** —— 否则预填后
  用户一个字没改、点取消也被拦「有未保存内容」，那是噪音（老板不吃噪音）。

### 🔴 新踩的坑：created_at 只精确到秒
三个柜在**同一秒内**创建 → `created_at` 完全相同 → `ORDER BY created_at DESC`
结果**不确定**，实测「上次输入」取到了**最早**建的那个柜。
**修法：`ORDER BY created_at DESC, rowid DESC`**（rowid 单调递增，同秒内后插入的更大）。
通用结论：凡是按 `now_iso(timespec='seconds')` 这类**秒级**时间戳取「最近一条」，
都必须有第二排序键兜底。

### 需求② 选图：看大图 + 自动策略
- 看大图复用 `drawer.js` 的 `openViewer`（与照片页同一份实现，自带拍照时间）。
  🔴 **它本来就在文件末尾 `export {...}` 列表里**（第 499 行），我在定义处又写了
  一个 `export` → **Duplicate export**，会让整个模块图挂掉、全站白屏。
  是 `checks/esm_syntax.py` 抓出来的（PASS 16/FAIL 1 → 修完 17/17）。
  修正我此前的记录：**重复导出**静态检查查得出；查不出的是
  「import 了一个没导出的名字」——后者才只有 CDP 走查能抓。
  教训：改导出前**先 grep 一眼文件末尾有没有 export {} 列表**。
- 策略 `strategy`：`balanced`(默认) / `std` / `latest` / `hd` / `near_std`。
  🔴 用「**主次序 rank + 原打分兜底**」，不能只调权重 —— 打分末尾有
  `min(0.99, score)` 封顶，权重一大全塌成 0.99 平局，「优先 X」反而失效。
