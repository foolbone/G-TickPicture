## 无感升级：把升级集成进启动脚本（v0.4.2）

- 用户：能否把升级集成到启动脚本，实现无感升级、提升体验。
- 关键发现：`store.connect()` 每次打开库**已经在静默跑 `_migrate`**（store.py
  64-66，受 `_schema_initialized` 进程内缓存保护），但迁移前**不备份、不核对
  行数、不冒烟** —— 等于带着用户数据做无备份的库结构变更。所以「无感」其实
  已部分发生，但要补的是**安全外壳**，不是新行为。
- 做法：server.main 正常启动分支在起服务前调 `upgrade.auto_upgrade(data)`：
  - `store.needs_migration(db)`（新增，与 `_migrate` 添加的列/表/索引一一对应）
    判 False → 完全静默跳过（不备份、不塞磁盘）；True → 先备份（迁移前快照）
    → 强制跑幂等迁移 → 逐表核对 → 冒烟。失败返回 failed，main **拒绝启动**。
  - auto_upgrade 的升级改用显式 `executescript(SCHEMA)+store._migrate`，不依赖
    store.connect 的 `_schema_initialized` 缓存（否则同进程内第二次 connect 会
    跳过迁移，auto_upgrade 白跑）。
  - explicit `--upgrade` / `升级助手.cmd` 已最新库时改为跳过备份（不再每次
    重跑都造时间戳副本）。
  - 启动方式：用户只需「解压新包→拷 data\\→双击 启动产品库.cmd」，exe 内部
    自动升级；升级助手.cmd 降为手动可选。
- 🔴 顺手抓出并修了一个**真实遗留 bug**：`schema.SCHEMA` 的 photos 表后来直接
  带了 photo_usage/carton_no 列，导致 `_migrate` 里 `if 'photo_usage' not in
  pcols` 恒为 False、`idx_photos_usage`/`idx_photos_carton` 两索引**新库老库都没
  建出来**（按用途/箱号筛选退化成全表扫描）。改成 `_has_index` 保证存在。
  这 bug 是 `needs_migration` 的检查（全新库返回 True）逼出来的——正好印证
  「加检查能抓出隐性 bug」。
- 测试：新增 `tests/auto_upgrade.py`（全新库静默跳过 / 缺列旧库自动补回 / 备份

## 排查「OCR 识别出编码、大模型没识别出来」是否合理（只读，未改代码）

- 统计口径：开发库 2738 张照片 / 2561 已治理，ocr_tokens 里的文字用真实
  `pipeline._match_token`（CodeIndex）判是否精确命中产品码，再与 photos.vision_codes
  比对。**别用 normalize 直等 code_norm 代替**（口径比 _match_token 宽，会多算）。
- 结论分层：
  - 装箱单 packing_list 99 张 OCR 有码、视觉无码 → **故意**：`NO_LINK_KINDS` 不
    关联产品，且 describe 不对它调用（省 API）。不是漏。
  - 标识卡 label 234 张 OCR 有码，其中 212 张视觉也有、22 张视觉漏读（约 9%）
    → 正常互补，**22 张全部由 OCR 兜住自动关联**，零损失。
  - 产品/包装 product|packaging 6 张 OCR 有码、视觉无码 → 视觉 `expect_codes=False`
    （防脑补，合理）；但 OCR 码也没用上，**4 张未关联 = 真漏**。
- 🔴 真漏根因（时序）：`OCR_WORTHY_KINDS=('packing_list','label','unknown')`，
  product/packaging 治理时**不跑 OCR** → 无 hits；而唯一能用已落库 token 补关联的
  `relink_due_to_checklist` **只在清单导入时触发**。这 4 张的 govern_at
  (10-07 03:19~03:21) 晚于最后一次清单导入 (02:52) → 之后再没触发 → 永久漏。
  token 是早期治理遗留（那时跑过 OCR）。
- 证据：真实 `_match_token` 对这 4 张的 OCR 码精确命中，分 0.928/0.942/0.980/0.948
  （阈值仅 0.70）。**DB 副本**干跑 relink：scanned 917 / written 5，4 张全部补回。
  真库未动。
- 待用户决策的修复方向：①治理收尾自动跑一次 relink（零额外算力，推荐）
  ②把 product/packaging 加进 OCR_WORTHY_KINDS（更全，代价是全量 OCR 变慢，
  2700 张约 2h）③不动，界面上已有「补关联」按钮可手动点（products.js /

## v0.20.0 方案：两个真机反馈的根因定位（2026-10-12）

老板 REDMI Turbo 4 两条反馈 + 总要求「对标原生相机」。已定位，方案文档：
`拍照体验改进方案_2026-10-12.md`（仓库根）。

1. **取景≠成片（成片视角更宽）**：`_buildPreview` 用 `FittedBox(BoxFit.cover)` +
   手工交换宽高 SizedBox 把 4:3 预览流无脑铺满 20:9 屏幕（横向裁约 1/3），
   而成片 `ResolutionPreset.max` 是 4:3 全幅不裁 → 差的就是裁掉的部分。
   画幅设置也只映射了成片 preset，预览侧不按画幅裁。**修复=预览容器按画幅
   比例（AspectRatio 3:4/9:16）+ 流在容器内 cover + UI 排黑边区**——已推导
   4:3 与 16:9 两档裁剪同向同量（16:9 时横向各裁 25%），严格所见即所得，
   且与流的实际比例无关（机型差异被容器吸收）。附 preview/capture 尺寸诊断日志。
2. **相册导入日期选择无效**：两层根因。语义层：日期选择是「滚动定位」
   （`_locateToDate`）不是过滤，其他日期无照片时定位回顶部=9/24 纹丝不动
   且无提示；能力层：`queryGalleryImages` 没有日期过滤参数。
   修复=原生加 dayStartMs/dayEndMs（`COALESCE(NULLIF(datetaken,0),date_modified)`
   归日，与 bucket 可叠加）+ `queryGalleryDays` + showDatePicker 的
   selectableDayPredicate 置灰无照片日期 + 过滤模式/日期 chip/明确空态。
3. 顺带 P1：回看 InteractiveViewer 双指放大、手动 EV 滑块 UI（服务 API 早有）、
   微信导入同款日期过滤。音量键快门 P2（需原生拦按键）。
