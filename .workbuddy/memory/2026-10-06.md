## 修「报告生成失败 Permission denied」（09:45）

老板报错：`[Errno 13] Permission denied: ...\LOADING REPORT-CNTR#EMCU9914616-6th_Oct_2026.docx`。
根因：报告文件名按「柜号+日期」固定，同日重复生成就是覆盖同名文件；老板把上一版
拖进 Word 看着，Windows 锁住目标 → `doc.save()` 抛 PermissionError，**20 秒生成
全白跑**。诊断小技巧：文件「可读但 os.replace 失败」= 被 Word 占用。

修法（report_gen._save_report）：
1. 先写 `*.docx.tmp`（不会被锁）→ `os.replace` 原子替换（要么全成要么原样不动）
2. 被锁 → 自动加时分秒另存（`...-094419.docx`），返回 renamed=True + note
3. 路由用**实际落盘**的文件名拼下载链接（否则会指向被占用的旧名）
4. 前端如实显示「同名文件被占用，已自动另存（关掉 Word 里那份再生成可覆盖原名）」
5. `_report_files()` 顺手清 >1h 的残留 `.docx.tmp`
6. 兜底：真写不进去才 500，提示"关闭占用它的程序或检查磁盘/目录权限"

R37 钉住（测试里真持一个文件句柄模拟占用）。实测：拿老板正开着的那个文件跑
→ 自动另存 18.4MB、下载 200、界面提示到位、④列出两份。回归 44 项 + 三项静态
检查全绿。教训：**任何"按固定名覆盖"的产物生成，都要有 .tmp+replace+改名兜底** ——
Windows 上"文档正开着"是日常，不是异常。

## 修「其他电脑运行提示端口被占用」（15:10~15:25）

老板在别的电脑跑绿色包 → 「提示端口被占用」。根因与三条真修法：

**🔴 根因1：避让逻辑放错地方。** 第一版把端口探测写在 `启动产品库.ps1` 里，
但老板**最常见的用法是直接双击 exe**，那条路根本不经过脚本 —— 探测等于没做。
已搬进 `server._pick_port()`（exe 自己会避让），并把 .ps1 里重复的探测删掉
（两处各探一套必然不一致：脚本说 8766、exe 实际 8767）。
新增 `tools/productlib/tests/port_pick.py` 8 项（V1 空闲不换/V2 识别占用/
V3 顺延/V5 连占跳过/V6 全满返 None/V7 _say flush/V8 提示给 exe 名）。

**🔴 根因2：报错不可操作。** 原来是 uvicorn 的英文 `[Errno 98] Address already
in use`。现在三个层次都是中文且给动作：
[WARN] 端口 8765 被占用了（多半不是产品库），已自动改用 8766
[ .. ] 浏览器会打开下面这个地址；旧地址打不开是正常的。
[FAIL] 端口 X~X 都被占用 → 三条办法（关占用软件 / --port 9000 / 改默认值）。
并捕获探测与真正 bind 之间的竞态 OSError，给同风格提示。

**🔴 根因3：启动日志看不到（假死）。** stdout 在管道/重定向时是**块缓冲**，
`print` 不 flush → 黑窗口里要等缓冲区满才出现，老板看到「双击后一片空白以为没反应」，
而端口其实早换好了。加 `_say()` 统一 `print(msg, flush=True)`，容忍窗口被关。

另加 `GET /api/ping` 身份核验（返回 app/version/data_dir/mode）：端口被别人占时
老板浏览器还开着旧地址，看到的是**那个软件的页面**，现象是「产品库打不开」、
真实原因是他没看新地址。有 ping 才能程序化确认「这个端口后面站的是谁」。

**实测（本机 8765 真被占，WinError 10048）**：打包版 exe 直接双击 → 自动改用 8766

## 补充：治理期数据库锁的实测结论（16:56）

老板看到「数据库被占用」提示，问会不会因为治理时做其他操作导致。**实测：不 会。**

模拟 govern_all（每张一次 UPDATE + commit）并发读写同一库：
- 治理线程 700 次写入，**锁错误 0 次**
- 并发读 50 次：平均 **18ms**（WAL 允许读写并行）
- 并发写 20 次：**全部成功**，0 失败

机制已有：`connect()` 里 `journal_mode=WAL` + `busy_timeout=30000` + `timeout=30`。

**真实成因是「同时开着第二个产品库进程」**：造一个长事务不提交的场景，
另一个连接写要干等 **32.9 秒** 才报 `database is locked`（busy_timeout 用满）。
所以「另一个进程在写」这个文案太模糊 —— 已改成
`数据库被另一个产品库进程占用` + 明确解法（关掉多余的黑窗口；
绿色包和源码版别同时开 / 浏览器留的旧窗口也关掉），
并加一句「治理本身不会造成这个 —— 它每张照片就提交一次，锁的时间极短」。
使用说明里也加了同一条 + 「别把产品库开两份：同一个 data\ 只能被一个进程写」。
真实库里 0 条锁错误历史记录，说明老板看到的是我昨天加的失败分类文案，
不是真发生了锁 —— 但文案误导是实打实的（指向错误方向）。

**通用教训**：WAL + busy_timeout 已足够支撑「一个长任务 + 页面查询」的模式。
真出 `database is locked` 基本只有两种成因：①另一个进程在写同一文件
②长事务不提交（begin 后忘了 commit）。排查先看这两个，别怀疑 SQLite 性能。

## 升级方案：如何不丢数据（17:05~17:25）

老板问「如何不影响之前数据进行升级更新」。查出**升级本身是安全的**，并做了一键工具。

**先查清破坏性风险**（这是回答这个问题的前提）：
- `grep -i "DROP TABLE|DROP COLUMN|TRUNCATE"` → **零命中**。所有 DELETE 都在
  业务函数里（重跑治理/删关联），不在迁移路径上。
- `_migrate` 的 DDL 全是 `ADD COLUMN`（12 处，每处都有 `_has_col` 幂等探针），
  schema 全是 `CREATE TABLE IF NOT EXISTS`。
- 迁移里唯一的**数据写入**是两处幂等回填：`INSERT OR IGNORE INTO product_batch
  SELECT ... FROM products`（从老列 source_batch 搬）+ `_migrate_containers`
  （按 container_no 建柜 + 只补 `container_id IS NULL` 的行）。
- **迁移幂等实测**：清 `_schema_initialized` 强制重跑 3 次，12 张表行数完全不变。

**新工具 `tools/productlib/upgrade.py`**（备份→升级→自检→冒烟）：
- 备份**整个 data 目录**（不只 .db —— 缩略图/标准图/报告/vision.json 都在里面）。
- 自检逐表比对行数，掉行就报错并打印还原步骤。
- `--dry-run` 只报告不动手；`--no-backup` 存在但明确警告。
- `main(argv=None)` 改成可传参 —— 让 `集刻产品库.exe --upgrade` 能调它
  （绿色包里没有 Python，升级流程必须能由 exe 自己跑）。
- server.main 加 `--upgrade` / `--dry-run` 分支（在选端口之前就 return，不启服务）。
- spec hiddenimports 加 `tools.productlib.upgrade`；post_build 把 upgrade.py 拷到
  exe 同级成「升级助手.py」。

**实测（真实库副本 + 打包版 exe，各一次，两次都零掉行）**：
升级前 12 表/25002 行 → 备份 114.6MB/8s → 升级 0.2~0.27s →
逐表核对全 OK（checklist_rows 1003、ocr_tokens 17377、photos 2738、links 1017…）
→ 冒烟能读 785 产品/2738 照片/3 柜。
拍照路径抽查在**新机器上 0/20 存在** —— upgrade.py 如实 WARN 并给出解法
（这正是"原地引用"的必然结果，产品/清单/报告/Key 不受影响）。

指南落 `doc/产品库升级指南.md`（含数据目录解剖、三步、为什么安全、
还原步骤、五个常见误区、命令速查）。

**踩过的坑**：造"旧版本库"做对照时我用 `DROP TABLE` 删掉了新表，
却拿**新版表的行数**当基线快照，误判成"丢了 1003 行 checklist_rows"。
对比升级前后必须用**同一个库的同一次快照**，不是"新表应有多少"。
另外 test 里把 `batches.container_no` 全清空，模拟出"全部批次挂未分柜"，
那是我的造数据方式造成的，不是升级缺陷 —— 说明这类试验很容易自证误导。

## 「读取向导进度失败：Not Found」排查（23:11）

老板报向导弹这个错。**不是代码问题，是服务进程是旧的**（老坑第三次踩到）：

- 当前源码里 `['GET'] /api/containers/{cid}/progress` **已注册**（routes/__init__.py
  在 containers 之后 include progress），用干净端口起新进程实测**正常返回 JSON**。
- 但在跑的 8766（data_dir = D:/G-TickPicture/productlib/data，源码模式）实测
  `/api/containers/{cid}/progress` → **404**。它是在 progress.py 加进去之前起的。
- ⚠️ 8765 上那个进程 `/api/ping` 返回 Not Found，我一度判成「别家的程序」，
  **这个判断不准** —— 它更可能是**更老的产品库**（/api/ping 是后来才加的端点）。
  重起后产品库照样落在 8765。以后判「这个端口后面站的是谁」不能只靠 ping 404。

**根因就是那条铁律**：路由在进程启动时加载、静态文件每请求现读 →
「界面是新的、接口 404」。改完后端必须重启，别指望前端能看到新端点。

**本次顺手加固（wizard.js）**
1. 404/Not Found 单独识别，提示直接说「服务进程还是旧的 → 重启产品库服务即可」，
   不再只甩一句 Not Found。
2. 读失败渲染成**错误态 + 重试按钮**，不再卡在「读取中…」
   （「还没查完」≠「没问题」，卡在读取中等于把故障伪装成等待）。
   `loadProgress` 新增 `_loadErr`；空 = 没失败。
3. playwright 用 `page.route` 拦截 progress 强制 404 复现，6 项断言全过。

**重启命令**（源码模式，端口被占会自动往后找并打印实际地址）：
`python -m tools.productlib.server --port 8765`
