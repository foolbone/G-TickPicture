## 旧版「照片治理」抽屉打开后关不掉（老板报障，本轮）

### 根因（实测定案）
治理抽屉 `#wizGovWrap` = `position:fixed; right:0; width:min(560px,94vw); z-index:70`，
**它自己把唯一的关闭入口盖住了**：开关按钮 `#gGovToggle` 被 `.wstat-inline{margin-left:auto}`
推到向导卡片标题行最右缘，正好落在抽屉覆盖区下面 —— 真实鼠标点击命中的是抽屉内部
元素（实测坐标 1304,177 命中 `#gBatch`，`hitInGov:true`），不是按钮。
抽屉内又没有 ×、没有 Esc、没有点外面关闭 ⇒ 三条关闭路径全断。
新版 Vue 端用 `el-drawer`（自带 × + 遮罩 + Esc），无此问题。

### 修法
- `web/index.html`：`#govPanel` **外面**加顶栏（`.gov-drawer-hint`）+ `#gGovClose`
  「✕ 关闭」按钮。⚠️ 不能塞进 `.foldbody`（display 由 batches.js 管）。
  app.css 里 `.gov-drawer-hint` 样式上一轮就预置但从未启用，本轮首次用上。
- `web/static/js/wizard.js`：
  - 抽屉状态存**模块级 `_govOpen`**（不能用 `style.display` 表达状态）——
    `bindStep` 每次重绘都跑，无条件 `display='none'` 会让用户刚开的抽屉在下一次
    刷新（loadProgress / 治理轮询）后自己消失。
  - 新增 `openGovDrawer/closeGovDrawer/govDrawerIsOpen`。
  - 文件末尾模块级绑定（一次性，不随重绘丢失）：`#gGovClose.onclick`、
    `onEscape(..., prio 5)`（低于批次抽屉 10，保证批次开着时 Esc 先关批次）、
    `document mousedown` 点外面关闭（`#wizGovWrap` 外且不在 `_GOV_KEEP_OPEN` 白名单里）。
- `web/static/js/batches.js`：**层级冲突** —— `#bOpen`（照片批次）就在治理面板内，
  但 `#bDrawer` z-index 60 < 治理抽屉 70 ⇒ 从治理面板呼出的批次抽屉整块被压住、

  遮罩 `#bMask` 保持 55 不提（提上去会把治理抽屉整块压暗，治理抽屉自己的
  「点外面关闭」已能兜底）。

## App 端 v0.24.11：渐进式收图 + 进度提示（老板「拍照后要等很久才看到照片」）

### 链路改造（原生 SystemCameraBridge.kt）
- **渐进式收图**：`collectNewImages(progressive=true)` 拆「首批 + 兜底
  sweep」。首批 = 文件集合与大小**连续 2 轮（800ms）稳定**即交回（原来
  要 3 轮全稳定一整批）；ingest 串在首批后面立刻开搬。sweep 线程 400ms
  轮询最多 15s：新路径 → `changed:false` 推送补收；已交回路径**大小变了**
  → `changed:true` 推送修复（Dart `recopyPhoto` 重拷覆盖 + 重算派生），
  渐进式唯一的数据风险（首批交早了）由此闭环。
- **会话代号防重叠**（`sessionGen`，每次 launchSession 自增）：旧 sweep
  收尾发现 `myGen != sessionGen` → **不推 isFinal、不清原生上下文**

  （相册里有）。collecting 结局正常返回 → 断点在「推送→Dart」一环。
- **根因**：`pushLateShots` 在 sweep/收图后台线程直接
  `MethodChannel.invokeMethod` → FlutterJNI.`dispatchPlatformMessage`
  第一行 `ensureRunningOnMainThread()` 抛 RuntimeException → 被 catch
  吞掉只剩一行 log。首批/晚到/收尾 final 三类推送全灭，Dart 永远停在
  collecting。v0.24.11 首批同步走 launchSession 结果所以能进（晚到推送
  同根源早就在丢，只是罕见没暴露）；v0.24.12 把首批也搬上推送 → 全灭。
  代码注释「invokeMethod 线程安全」是错的，没有实测背书。
- **修复**：`pushLateShots` 统一 `activity.runOnUiThread` 包裹（FIFO 保
  序）再 invoke。一行级改动，`compileReleaseKotlin` EXIT=0。
- 查证方法：直接读 Flutter 3.29.0 tag 的 DartMessenger.java /
  FlutterJNI.java 源码（send 只是 @UiThread 约定无检查，dispatchPlatform
  Message 是硬断言）——文档性结论必须落到引擎源码，不能凭印象。
- 事故照片的补收：原生 syscam_pending 已被 sweep finally 清掉、恢复链路
  无上下文 → 老照片只能从「从相册导入」手动补。
- 发版 v0.24.13（+49），`-AllowDirty -CommitPaths 'app,CHANGELOG.md'`
  （工作区躺着 productlib 会话的未提交成果，不能被 release commit 吞）。

## v0.24.14：首批推送被误报「晚到」（真机验收反馈）
- 现象：拍 5 张 → 「又收下 5 张」→ 收尾又「又收下 5 张晚到的照片」，
  用户以为收了两遍。
- 根因：v0.24.12 起「返回即回 App」后**首批也走推送**，但照片页进度层
  （runSystemCameraWithProgress 的 lateSubLocal）与采集页 HUD
  （_onSystemShutter）的晚到记账还是 v0.24.11 口径「凡推送皆晚到」——
  第一批推送被当晚到弹提示 + 计数，收尾再报一遍。
- 修复：第一次推送按首批对待（不弹「又收下」、不计晚到）；收尾无真
  晚到时给「已收下 N 张」确认；修复批（changed=true）全程静默。采集页
  对账改 batchPushed + lateIngested 分开累计（total/stored 差额判断不变）。
- 教训：**把交付通道从「同步返回」搬到「推送」时，所有按推送语义记账
  的下游（提示/对账/计数）都要跟着过一遍**——首批的定义变了。
- 新钉子：首批推送不当「晚到」（debugPushLateShots 驱动进度层真实流）。
- 发版 v0.24.14（+50），脚本内三门禁全绿（analyze / test 251s / 构建）。
