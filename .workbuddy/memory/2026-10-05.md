## 检索页缺口文案混淆（真缺口 vs 被批次挡住的假缺口）

**老板报**：检索页勾批次后检索编码，结果写「编码在库但所选批次内无照片」，
但标准产品页明明能看到照片 —— 像是数据丢了。

**根因**：`store.report_lookup` 只算一份结果（先按批次过滤、再按标准图过滤），
空了统一报「所选批次内无照片」。两种完全不同的情况被合成一句话：
- A 真缺口：全库都没有关联照片
- B 假缺口：照片在，只是不在所选批次

产品页从不按批次过滤，所以 B 在产品页看得到 → 观感就是"数据丢了"。

**改法**：`base`（全库，不受批次限制）与 `scoped`（加批次）分开算。
- `base` 空 → `编码在库但没有关联照片`（不提批次，不甩锅）
- `base` 有、`scoped` 空 → `所选批次内无照片（其他 N 个批次共 M 张）`
  + 返回 `other_batches: [{id,name,n}]` / `other_count`
前端：缺口卡片加 `.rp-why` 行（批次名+张数）+ 「加选并重检 / 不限批次重检」按钮，
顶部 rpgap 提示区分「其中 N 个只是照片不在所选批次」。

**实测**（只选最新批次 UETV8107553 检索 80 个编码）：79 缺口 = 17 假 + 62 真。
真实库 1000000119 → "其他 2 个批次共 5 张"（PIDU9352234 3 张 / MRSU2065286 2 张）。

**踩坑**：写测试时 `products.code_norm` 写成小写 `'c1'`，而 `BL.normalize('C1')`
**保留大写**（= 'C1'），links JOIN 全空 → 测试假红。测试数据必须按 normalize 后的形态写。

**验证**：新增 `tests/report_gap.py`（11 项 ALL PASS：A/B 分开、B 给批次名与张数、
std_only 组合、不勾批次兼容）、`checks/cdp_ui1005.py`（真实浏览器 12 项 ALL PASS，
含点「加选并重检」后假缺口真变命中 miss→5 张图、无 JS 异常）。

## 🔴 v0.15.0 砖化事故：App 完全打不开（duplicate column name: content_hash）

**老板报障**：装 v0.15.0 后打开 App，项目列表页整屏错误卡片
```
⚠ 加载项目失败 (code 1)
duplicate column name: content_hash, SQL logic error (code 1)
Causing statement: ALTER TABLE "photos" ADD COLUMN "content_hash" TEXT NULL;
```
点多少次重试都不会好 —— **永久性卡死**，只能清数据。

**根因（读 drift 2.31 源码逐行确认，不是猜）**：
- `onUpgrade` **不在事务里** —— `db_base.dart:131-135` 的 `beforeOpen` 直接
  `await _resolvedMigration.onUpgrade(...)`，无 `transaction()` 包裹。
- `user_version` 是在 `beforeOpen` 返回**之后**才写 —— `engines.dart` `_runMigrations`
  注释原话 "We only update the schema version after migrations ran"。
- 两者叠加 → **致命中间态：DDL 已落盘、版本号还是旧的**。迁移执行到一半被中断
  （杀进程/系统回收/崩溃/后一步 createIndex 抛错）就留下它，下次启动重跑同一 ALTER。

**第二个 bug（被第一个掩盖）**：`Index(entityName, stmt)` 第二参是**完整的
CREATE INDEX 语句**，v0.15.0 误传裸列名 `content_hash`，drift 当整条 SQL 执行 →
`near "content_hash": syntax error`。列幂等之后才暴露出来。两处一并修。

**修法**（`app/lib/data/db/database.dart`）：`_hasColumn`（`PRAGMA table_info`）+
`_hasIndex`（`sqlite_master`）+ `_addColumnIfMissing` 幂等包装，5 处历史 addColumn
与 1 处 createIndex 全改造 → 半迁移库重开时自动补齐并把版本写到 4，
**用户装 0.15.1 无需清数据即可恢复**。

**测试**（`app/test/migration_idempotency_test.dart`，9 条）——
**写这类测试的头号陷阱**：`beforeOpen` 是在**第一次 customStatement/查询**时触发的，
所以「打开库看一眼现状」这个动作本身就是一次迁移。
- 造种子（手工 DDL）必须用 `NativeDatabase(f, enableMigrations: false)` 裸连接；
- 探查现状（`userVersion()`/`columnsOf()`）同样必须用裸连接 ——
  否则断言函数自己就是被测行为的触发者，断言拿到的是迁移后的值；
- 我因此被坑了两轮：探针一度红在**种子上**（手工 ADD COLUMN 撞上迁移刚加的列），
  红的理由看着像产品有 bug，其实是测试自己把迁移触发了。
- Dart 局部函数**不能前向引用**：探查函数必须排在 seed 函数之前，否则编译失败。

**探针证据**（拆掉 `_addColumnIfMissing` 的探测）：`+3 -6`，6 条变红，报错逐字复现
真机现场 `Causing statement: ALTER TABLE "photos" ADD COLUMN "content_hash" TEXT NULL;`
→ 证明测试真在守护该缺陷。

**验证**：analyze `No issues found!`；全量 **392 条全绿**（基线 383 + 新增 9，EXIT=0）；
架构三条 `RESULT: PASS`。

## 查重提示具体化 + 跨组逐张选（老板追加需求）

**需求**（原话）：「重复提示要更具体明确的告诉用户，并且当跨组重复时，
让用户选择删除哪个组里的哪张。」

**改法三层**：
1. **数据层**：`findDuplicates` 改 `LEFT JOIN photo_groups` 取 `seq`。
   之前只查 `group_id` → UI 拿不到次序，只能写「出现在 2 个组」，
   用户不知道该动哪张。**必须 LEFT**：游离照片 group_id 为 NULL 也要查出来。
   组被删后残留 group_id → `groupSeq` 为 null 但 `isFloating` 仍 false
   （**不能谎称「未分组」**，group_id 还在，只是查不到次序）。
2. **模型层**：新增 `DuplicatePhoto`（id/groupId/groupSeq/seq/thumbPath +
   `groupLabel`）与 `DuplicateSetWithGroups.groupSummary()`（按次序升序拼
   `第2组 ↔ 第5组`，超 3 个折叠成「等 N 个组」）+
   `soleGroupSeq`、`crossGroupCount`/`withinGroupCount`/`floatingDuplicateCount`。
3. **UI 层**：每张缩略图下方写「第 N 组 / 未分组」；跨组**默认不预勾**——
   跨组意味着分组出问题，哪张该留是业务判断，机器按"最早"猜**猜错就是删掉有用的那张**。
   同组内保留一键删冗余（早/晚无业务含义）。按钮未选时禁用**且写清下一步**。

**顺手修的 4 个真缺陷**：
- 判「处理完」原用 `failed == 0` —— 用户只勾一部分删时 failed 也是 0，
  剩下照片**仍彼此重复**却被标成「已处理完」，与提示「还剩 N 张重复待处理」
  **自相矛盾**。改判据：删完这组是否还剩 ≥2 张。
- `deletePhoto` 的 `catch (_)` **空捕获**：删 2 张只成 1 张时现场只看得到
  「1 张失败」，无从自查。改为记录第一条异常带进提示（截 40 字）。
- 缩略图溢出 3px：选中态 `Border.all(width: 2)` 画在内容**之外**，
  Stack 62→66 高于外层 SizedBox 4px → Column 溢出（真机表现为文字被切）。
  改 `Positioned.fill` 约束在框内。
- SnackBar 把「只剩 1 张」也说成「还剩 1 张重复待处理」—— 剩 1 张
  **根本不重复**（判定需 ≥2 张），是句假话。改「这一组已清干净」。

**widget 测试纪律（本次栽了三次，代价 4 轮跑）**：
- **点完真删/真写库后不能用 `pumpAndSettle`**，要 `runAsync` + `pump` 交替。
  只 pump 帧**推不动 drift 事务** —— 表现是"删了 1 张（第一张恰好在同步段完成）、
  第二张卡住不动"，我据此**误判过一次「第二次 deletePhoto 抛异常」**，其实只是没等够。
- 删除后会 invalidate 四个 provider（openGroups/supervisionPhotos/
  projectPhotoCount/duplicateReport），**不 override 就 `pumpAndSettle timed out`**。
- `showDuplicateSheet` 要 **WidgetRef**（不是 container）→ 按钮必须长在
  `ConsumerWidget` 里，`Builder` 给不了。
- ⚠️ **测试前提写错，断言就是一根永远绿的拐杖**：我第一版用
  「2 张删 1 张」测「还没删干净」，但剩 1 张本就不重复 —— 测的是个不存在的情况。
  改 3 张删 1 张（剩 2 张仍重复）才是真场景。

**探针**（把 `groupLabel` 改成 `第 ? 组`）：`+37 -8`，红的 8 条全是
「说清组归属」与「逐张选删」相关 —— 理由正确。

**验证**：查重测试 29 → **45 条全绿**；analyze `No issues found!`。

## 候选照片「标记为无关联」（14:5x，productlib）

老板原话：「可能的照片关联时，经用户查看确认没有关联的，可以标记为无关联，
不在可能关联的图片显示」。

### 核心判断：候选是「算出来的」，所以标记必须落库 + 挡四处
候选每次刷新都由 `cand_code_map` 重算。**只在前端 `display:none` 等于没标记**
（刷新一次就回来）。落 `cand_reject(code_norm, photo_id)` 表之后，
标记会在**四个地方复活**，每一处都必须单独挡：

| 复活路径 | 挡在哪 |
|---|---|
| 详情读码候选（刷新重算）| `cand_code_map` 收尾减（`cand_counts` 读码部分也吃它 → 一处减两处生效）|
| 详情同组候选（另一条 SQL）| `product_group_siblings` 减 |
| 列表「待确认」角标（独立 SQL + 60s 缓存）| `cand_counts` 的同组部分 + **`_cand_stamp` 必须计入 `cand_reject` 行数** |
| 自动关联（清单重导跑 relink，用同一批 token 重匹配）| `apply_auto_links` 跳过 |

⚠️ 最后一条最容易漏：`relink_due_to_checklist` 会 `replay_hits` 重跑一遍匹配，
命中的是**同一批已落库 token**，标记会被无声吞掉 → 标记成了摆设。
人的判断必须优先于机器，所以闸门加在 `apply_auto_links`（两处调用点共用）。

### 粒度：`(code_norm, photo_id)` 不是 `photo_id`
一张照片上可能读出多个码 → 它同时是 A、B 两个产品的候选。
老板说「它不是 A 的」**不能顺带抹掉 B 的候选** —— 那是替他做了范围更大的决定。
测试专门造了 `p_two`（同进 A、B 候选），否 A 后验 B 仍在。

### 三态互斥 + 反悔路径
每对只有三态：已关联(links) / 已否决(cand_reject) / 待确认(两处都没有)。
- 人工 `link()` 时清同对否决 —— 改主意了能关联回来；
- `unlink()` 也清 —— 否则「否决→关联→解除」后照片**不回候选**，
  最常见的操作变成单向门（这条是写测试时才发现的，实现时没想到）。

### 验证

- **探针**：四处 `rejected_pairs` 全换成 `set()` → **11 条红**，且理由逐条正确。
