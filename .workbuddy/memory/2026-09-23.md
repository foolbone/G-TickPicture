# 【重大反转】09-23 07:00 —— 管道问题根本不是环境问题，是我的执行沙箱

## 根因（决定性证据）

进程链：`pwsh.exe → sandbox-cli.exe → WorkBuddy.exe`。**我从 agent Bash/PowerShell 工具发出的每条命令都跑在 `sandbox-cli` 里。** 该沙箱隔离了 Windows 命名管道对象命名空间，而 **Dart VM 创建子进程 stdio 用的是命名管道** → 必然 `ERROR_PIPE_BUSY`。

用**计划任务**（由 Task Scheduler 服务启动，不在我的进程树里）跑同一个 Dart 探针：
```
try1 OK exit=0 len=31
try2 OK exit=0 len=31
echo -> hello          ← 全部成功
```
之前所有"已排除"的假设（360/NordVPN/沙箱/权限）里，"执行沙箱"那条其实**没真正排除** —— `dangerouslyDisableSandbox` 不改变进程父子关系，所以照旧失败。我据此把嫌疑错指向了安全软件。

# 【设计修订】09-23 —— 设计方案 v3.0 → v3.1（核心目标口径变更）

## 触发：老板给出 Q2 真实规模答案

原话：「预检的货品，件数几百件，照片数原则上每件两张，预检和拍照总工作时长通常持续1天。原则上每件都要拍，但实际数量太多，实际操作上，通常能够80%以上有照片，就可以满足要求。」

**这条数据的杀伤力在最后一句** —— 它改的不是"规模"，是**"什么叫做完"的定义**。

| 维度 | v3.0 假设 | v3.1 修订 |
|---|---|---|
| 货品件数 | 约 200 件 | **几百件**（600~800 量级） |
| 照片数 | 300~500 张 | **600~1600 张** |
| 持续时长 | 2~4 小时 | **一整天（6~8 小时）** |
| 达标口径 | **100% 对应**（每件都要有照片，缺口逐件标原因） | **覆盖率 ≥ 80%**；缺口自动汇总、不阻塞交付 |
| 整理时机 | 仅"收工后统一整理" | **双路径：现场随手清一段 + 收工统一过**（共用一套数据） |

`AskUserQuestion` 三次确认：整理时机 = **两种都要支持**；缺口处理 = **标记原因后直接交付**（后进一步简化为**自动汇总、无需逐件标原因**）；对应方式 = **按拍摄顺序成组后整组指派**。

## v3.1 的核心论点（写进方案的一句话）

> **对应关系必须绝对正确（100%，靠结构保证）；覆盖率只要够用就行（80%，业务验收线）。**

v3.0 把这两件事混在一起当成"都要 100%"，把**一个业务上可接受的缺口，做成了工程上不可承受的负担**。

## 2. 存储探针的哨兵值 bug（被自己的单测抓住，这是本次最有价值的教训）

第一版实现：探针写成功 → 返回 `freeBytes = -1` 且 `unknown = false`，心想"调用方看到 -1 渲染成'未知'"。

**结果**：`enough = unknown || freeBytes >= requiredBytes` → `-1 >= 5000` 为 false → **明明能写的目录被"空间不足"拦在采集页外面**。单测 `真实可写目录 → enough 为 true` 当场抓住（Actual: false）。

**修法（语义修正）**：
| 结局 | 返回 | 语义 |
|---|---|---|
| 探针完整写入并删除 | `null` → `unknown=true` | 能拍，但给不出精确余量 → **沉默放行** |
| 探针写入抛异常 / 长度不对 | `0` → `enough=false` | 确实写不进去 → **唯一触发提示的情况** |
| 目录建不出来 | `0` → `enough=false` | 同上 |

**通用教训：哨兵值不能参与数值比较。** 设计一个"还有个数值字段"的返回类型时，先想清楚这个字段在每条路径上的取值会不会流进下游的 `>= / <=` 判断。"未知"用单独的布尔位表达（unknown），数值只在其可信时才有意义 —— 这就是"查不到 ≠ 不足"在类型上的落点。

# 🔴→✅ run_unsandboxed.ps1 彻底重写（本轮最重要的基础设施修复）

## 三连故障的现象与根因

1. **marker 失效**：`.done` 由任务进程写、沙箱 Glob/Read 永远看不见（CoW 影子视图）→ 轮询永远失败 → 上一版脚本空等满超时后 Unregister 杀掉还在跑的命令
2. **任务 Queued 卡死**：默认设置含电池条件，笔记本用电池时任务永远排队 → `-AllowStartIfOnBatteries -DontStopIfGoingOnBatteries` 一加即跑（M1/M2 时代正常是因为当时插着电源）
3. **OutFile 不落盘 / System32 假绿 / Invoke-Expression 静默失败**：三个连环坑——沙箱写的 wrapper 文件真实系统可能看不见（CoW）→ 弃 wrapper 用内联 Action；内联 Action 不设工作目录默认在 System32（analyze 报假绿）→ inner 先 Set-Location；`Invoke-Expression '"path" args'` 经 `-Command` 的 `\"` 转义在 PS 5.1 下解析失效（任务 exit 0 但内层根本没跑，OutFile 只有空 EXIT=）→ 解析 Command 的 `'"<exe>" <args>'` 结构改用 `& '<exe>' <args> *>>` 直接调用，inner 内不含任何双引号

## 新版关键设计

- **无 wrapper 文件**：Action = `powershell.exe -NoProfile -Command "Set-Location '<wd>'; & '<exe>' <args> *>> '<OutFile>'; 'EXIT=' + $LASTEXITCODE *>> '<OutFile>'"`
- **完成判定双信号**：marker（便宜）+ OutFile 大小连续 2 次 10s 轮询稳定（主信号，实证可靠）
- **OutFile 必须在 %TEMP%**（透传区：任务写、agent 能读）——**项目目录下会被 CoW 影子化，任务写的文件 agent 看不见**
- **EXIT= 行是权威退出码**：脚本尾部解析它并转成脚本 exit code
- **验证**：5.1 实跑 analyze 全链路 —— 30s 完成、OutFile 完整（No issues found! EXIT=0）、脚本 exit 0；BOM 已补（fix_ps1_bom.ps1 [ OK ]）

## 20:00 · P1 真实支持 xls/csv/xlsx（方案 B：自研 BIFF8 解析器）

老板指令：「那就按B执行吧」。方案 B 定调：**不动 Flutter SDK**，纯 Dart 自研最小 BIFF8 解析器（Dart 生态在本工程 SDK 约束下没有能读 .xls 的包，见下"技术边界"）。

### 技术边界实证（决定了为什么只能自研）
- `excel` 包：只吃 xlsx（zip），.xls → "Invalid zip archive"。
- `excel_plus`：**所有版本**都要求 Dart ^3.11.4（本机 3.7.0）。
- `excel2003`：要求 Dart >= 3.7.2（本机 3.7.0 差一点点）。
- Dart 随 Flutter 发布，无法单独升：Flutter 3.29.0 = Dart 3.7.0；要用 excel_plus 得升到 Flutter ≥3.41.6（跨 12 个版本）。为读一个 2003 年老格式升级整个 SDK，代价收益倒挂。

### 新增文件（均在 lib/domain/checklist/）
1. `ole2_reader.dart` —— OLE2/CFB 最小只读解析器，只为取 `Workbook` 流。
   - 头部 → sectorShift(30)/dirStart(48)/miniCutoff(56)/difatStart(68)/numDifat(72)
   - DIFAT（头 109 项 + 扩展链，扇区末 4 字节指下一个）→ FAT → 目录流 → 找 type=2 且名字匹配的流
   - `_offsetOf(sector) = (sector+1)*sectorSize`；**刻意不实现 MiniFAT**（Workbook 流真实必然 >4096，若遇小流返回 null 让上层提示"文件不完整"）
   - 静态入口 `extractStream(bytes, name)` / `looksLikeOle2(bytes)`
2. `biff8_reader.dart` —— BIFF8 记录流解析（第二层）。
   - `rid(2)+len(2)+body` 顺序扫描；BOF(0x0809) 的 body[2..3] 是 substream 类型（0x0005 全局 / 0x0010 工作表）
   - BOUNDSHEET(0x0085)：名字（cch(1)+flags(1)+字符，flags&1→UTF-16LE）+ 该表 substream 在流里的偏移
   - **SST(0x00FC) + CONTINUE(0x003C)**：用 `_FragmentCursor` 跨片段逐字符读。关键规则——**CONTINUE 若切在字符串中间，开头有 1 字节重述剩余部分编码**。XLUnicodeRichExtendedString = cch(2)+flags(1)+[cRun(2)]+[cbExt(4)]+字符（flags&1→UTF-16LE，否则 Latin-1）+[rich runs 4B/条]+[ext]
   - 单元格：LABELSST(0x00FD)/LABEL(0x0204)/RK(0x027E)/MULRK(0x00BD, body: r+c1+[xf+rk]*+c2)/NUMBER(0x0203)/FORMULA(0x0006, 只取缓存值)/BOOLERR(0x0205)
   - **RK 解码**：bit0=1→÷100；bit1=1→30 位有符号整数（`rk>>2` 带符号扩展）；bit1=0→浮点，**高 30 位是 IEEE754 double 的高 32 位**（清低 2 位后写到 ByteData 的**偏移 4**，低字补 0 —— 写偏移 0 会得到 5.32e-315 这种垃圾值，实测踩中）
   - 输出 `List<List<String?>>`：稀疏填 null、按 index 对齐、裁尾部空行；不做业务判断
   - **刻意不做**：公式求值（只读缓存值）/ 日期序列号换算（不偷偷改数据语义）/ 加密工作簿 / BIFF5 及更早

### 🔥 顺带挖出一个既有真 bug：xlsx 富文本 <si> 丢失
- **现象**：`excel` 包对「由多个 `<r>` run 拼成的富文本单元格」解析缺陷 —— 读成**字面量字符串 "null"**（`TextCellValue('null')`）。实测同源 xlsx 的表头 `Carton number. ` 与 `Order Qty` 正好是**加粗标红的分段文本**，两列直接丢失 → `Carton number` 极可能就是客户的货品编码列 → **自动列映射失效 → 导入报错**。这就是老板最初「导入这个清单时报错了」的另一半真因（叠加 WPS numFmtId 崩溃）。
- **修法**（`_repairRichText`）：读 `sharedStrings.xml`（拼接每个 `<si>` 内**所有** `<t>`）+ 读各 `sheetN.xml` 拿精确「单元格→共享串索引」映射（`<c r="A1" t="s"><v>3</v></c>`，列名 A→0/AA→26 自算）→ 只替换**看起来是坏的**格（空串或字面量 "null"），excel 已正确的值不动。
- sheet 名→物理文件的映射走 `workbook.xml`(sheet name + r:id) + `workbook.xml.rels`(r:id→Target)，**不靠 sheetN 数字猜顺序**（用户可拖排序/删表）。任何一步失败原样返回（尽力而为，不能把正常导入搞坏）。
- 教训：**「excel 包能读 xlsx」不等于「能正确读 xlsx」**；发布级可靠性要拿真实文件跑，不能只靠包名和单测。

## 🔄 进行中：D 项（诉求 4 · PP-OCRv6 接入）

老板拍板「直接立项接入 PP-OCRv6」。⚠️ **这是本项目首次引入 NDK 原生编译**。

### 架构选择（写进了 `PpOcrBridge.kt` 类注释）
**Platform Channel 桥接官方 Android SDK，而不是「Dart 侧跑 ONNX Runtime」。** 三条理由：
1. **复用官方前处理** —— PP-OCR 是两阶段（DB 检测 + 多边形后处理 → CRNN 逐框识别），Dart 重写等于重造轮子
2. **模型直接进 APK assets**，由 Kotlin 喂推理引擎 —— 不碰 Flutter 的 asset 解压路径，避开「AAPT 压缩导致加载失败」的经典坑
3. **一处失败只是一处** —— 原生侧崩了抛 PlatformException 回来，管道照常把该张标 failed，其余零影响

### ⚠️ 模型格式坑（最容易踩，务必记住）
PP-OCRv6 官方发布的是 **Paddle 推理格式**（`inference.pdmodel` + `inference.pdiparams`），**不是 .onnx**。必须先用 `paddle2onnx` 转换。**缺任何一个模型文件 → `create()` 返回 null → 自动回退 ML Kit**（三条路径都保证流程可用）。

### `OnnxPpOcrEngine` 的三条**有意为之的取舍**（类注释逐字记录，改回官方行为时连同注释一起改）
1. **不做方向分类（Cls）** —— 预检照片编码都是正向拍摄，省 ~30% 时间。代价：倒着拍的标签识别不出
2. **不做透视矫正** —— 用轴对齐包围盒裁剪（官方用 `get_rotate_crop_image`）。代价：斜贴标签识别率下降
3. **检测框不做 NMS** —— 改「面积排序 + IoU > 0.5 丢弃」，框数量是几十级不是几千级

### 关键技术细节
- **输入节点名从 `session.inputNames` 读，绝不硬编码** —— PP-OCR 各版本导出后叫 `x`/`image`/`inputs` 的都有，写死会抛 "invalid input name" 且**报错不告诉你正确名**
- **反射取值**：ONNX Runtime 返回的 Java 数组在编译期拿不到泛型 → 统一用 `java.lang.reflect.Array.get/getLength`
- 前处理：det 长边 960 + pad 到 32 倍数 + `(x/255-0.5)/0.5`；rec 固定高 48、宽上限 320、黑边补齐
- 后处理：逐行二值化（0.3）→ 连续段 → 上下重叠合并 → 面积/长宽比过滤 → IoU 去重；CTC 解码跳过 blank(0) 与重复帧
- `materialize()`：**ONNX Runtime 只能从文件路径建 session，吃不了 assets** → 首次拷到 `filesDir`

### 🔴 构建排障（本轮最有价值的教训）
**第一次 `flutter build apk --debug` 后台任务报 `completed=True LastResult=0`，但 APK 时间戳没变 —— 构建根本没跑起来。** 「任务成功」≠「命令成功」，必须**核对产物时间戳**。第二次跑才暴露出真实错误：

```

```
- 真因：`data class Box(val x0: Int, val y0: Int, var x1: Int, var y1: Int)` —— **x0 也是 `val`**，但扫描过程中 `overlap.x0 = minOf(overlap.x0, x0)` 要改它
