## App 端 v0.24.7：拍完必须「等一下返回」照片才进 App
- 老板反馈：拍照后要等一下再返回，照片才能进 App；立刻返回只在相册里有。
  **现象本身就是答案**：相机 App 是**在用户按下返回之后**才把最后一张写完
  盘的（4~8MB 原图 + 低端机 1~3 秒），「等一下」恰好等它写完 → 能进。
- v0.24.6 的两个硬伤：①文件系统扫描只在窗口末尾**执行一次**；②`size<=0`
  的文件被直接跳过（正在写）。立刻返回时文件还没创建/还没写完 → 必然漏。
- v0.24.7 改法：文件系统**轮询到稳定**（文件集合 + 每个文件 size 连续 3 轮
  ≈1.5s 不变才算写完），`size=0` 的候选也进签名（用来判「还在写」）；
  空窗口自适应 —— 媒体库有结果或相机停留 ≥2.5s（SHOOT_DWELL_MS）→ 最多等
  8s 落盘，否则 2s 收场；总上限 15s。扫描目录扩到**所有存储卷**的
  DCIM/Pictures（相机存储设 SD 卡的机型也能收）。
- 采集页 HUD：3 秒还没进 ingest 就显示「正在收照片，请稍候…（相机可能还在
  保存）」，别让用户以为卡死。
- 教训：**「等一个固定时长」永远不如「等状态稳定」**。收图/落盘/索引这类
  异步外部过程，判据要用「集合与大小不再变化」，不是 sleep 一个猜的秒数。
- Kotlin 小坑：`map[key]?["k"]` 非法（Map 没有安全索引），要 `.get()`；
  `val x = try { if (c) continue } catch { continue }` 报「if 缺 else」（try 被当表达式）。
- 门禁：dart analyze 0 → Kotlin compileReleaseKotlin SUCCESSFUL（1 warning:
  getExternalMediaDirs deprecated，可用）→ test 556 绿 → tag v0.24.7 →
  aapt versionCode=43/0.24.7 + pubspec 在包。

## 抽屉大图 ↔ 文件名之间的大空白（已修，两端同步）
- 现象：竖构图照片下方，文件名/柜号/箱号那行离图片很远，中间空一大段。
- 根因（CDP 实测钉死，非猜）：`.dw-imgwrap` 是 flex 容器，撑高时取的是 img
  **「未限高」的 hypothetical cross size**（498 宽→664 高），而 img 本身被
  `max-height` 压到 504；img 又 `align-items:flex-start` 顶对齐 → 容器底部
  裂开 160px 空白，`.dw-src` 紧跟容器底 → 图底到文件名 168px。
  帮凶：`max-height: min(56vh, 100%)` 里那个 `100%` 挂在 **auto 高度的父容器**上，
  属循环依赖，computed value 看着正常但 used value 不可靠。
- 修法：wrap 改 `display:block; line-height:0`，img `margin:0 auto` 水平居中，
  `max-height` 去掉 `100%` 只留 `56vh`。容器高度直接由图片给出，不再让 flex 去猜。
  - 新端 `frontend/src/components/PhotoDrawer.vue`（scoped CSS）
  - 旧端 `web/static/app.css` 405-412（`.dw-left .dw-imgwrap`）——**旧端同一处同款 bug**，
    注意它双类选择器优先级高于文件后面 452 行的通用 `.dw-imgwrap`。
- 验证：新写 `checks/cdp_vue_dw_gap.py`（造 900x1200 竖图复现，逐层量盒模型）。
  slackInWrap 160→**0**，gapImgToSrc 168→**8**（只剩 margin），
  wrap.h == img.h == 504。旧端 `cdp_drawer_layout.py` 与新端
  `cdp_vue_drawer_layout.py` 均 `FAIL 0`（大图限高、首屏不滚动、参考块 8+3 未受影响）。
- 遗留（有意不动）：`slackInLeft` ≈285px = 左栏内容少时底部空白。这是 `.dw-left`
  sticky 撑满高度的必然代价，不在「图↔文件名」之间，不算 bug。

## 选图（④）里同一张图并排出现两次（2026-10-20 老板反馈）
- 现象：报告④选图页同一个编码下成对出现同一张图；照片库看不到（按组折叠）。
- 🔴 **根因：同一张照片被两个来源各导入一次，都关联了同一编码**。实测
  `f6ed36f7571d` = `IMG_20260927_113549.jpg`（相机原图 4.0MB，历史图片批次 2c66f42e3313）
  vs `p_e6a536b7e7f83697` = `20260927_113549_00447.jpg`（0.9MB，**标准产品库导入**时
  `store.import_standard_folder` 造的 `p_`+md5 虚拟 id），两者同为 11:35:49。
  **不是渲染 bug**：`links` 无重复对、`report_lookup` 返回的 `photo_id` 也无重复
  （446 编码查过 0 个）。
- 修法：`store._dedup_same_shot()`，在 `report_lookup` 的 **base 最外层**去重
  （让 scoped / photo_count / in_container / container_n 全部同源）。
- 🔴 **判据不能只看文件名**：第一版「剥掉末尾连拍序号再比」把 App 自己的真实连拍
  `..._00447` 与 `..._00448` 合并了（单元测试当场抓到）。最终判据 =
  **同目录 + 拍摄时刻到秒 + 一组有相机原图（IMG_/P_/DSC_）、另一组有 App 版**：
  只有这种「同秒里既有原图又有 App 版」才认定是同一快门的两种副本，留原图（bytes 大）。
  App 连拍、相机连拍、跨目录、差 1 秒 —— 一律不动（5 个场景单元测试全过）。
- 实测该编码 8 张 → 6 张；微信命名 3 张原样保留。
- picks 存在 localStorage `{code_norm: [photo_id]}`：被合并掉的 id 仍指向真实照片，
  报告取图不受影响，只是列表里不再显示勾选 —— 安全，不处理。
