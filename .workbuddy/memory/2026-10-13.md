## v0.21.1 热修：相册导入日期过滤 0 行（老板截图反馈）

- 症状：选择照片 → 过滤 2026/10/12 → 「这一天没有照片」，实际有照片。
- 取证：日期清单（日历置灰）走**内存归日** → 通；日期过滤走
  **selection 里的 COALESCE/NULLIF 表达式** → 查询成功返回但 0 行
  （UI 显示空态而非报错框，排除抛错路径）。
- 根因：Turbo 4 的 MediaProvider 对 selection 表达式/参数绑定行为
  不可信（第 4 击：此前 LIMIT 被拒、GROUP BY 被拒、列名严查）。
  v0.20.0 把表达式拼进 selection = 违反项目自己的「不做 ROM 兼容性
  赌博」铁律，核对方案时抓了 SQL 单位/时区坑，却没抓"表达式本身
  就不该出现在 selection"这层。
- 修复：selection 只留裸列比较；按天筛选挪进 queryGalleryImagesOnce
  的 cursor 循环（内存做，offset 语义=过滤后集合内偏移，与 Dart 分页
  口径一致）；新增排障锚点日志（过滤 0 行时打 range + 首样本原始
  taken/added 值）。
- 过程坑：排障日志在 use{} 闭包外读不到闭包内声明的计数器 →
  Kotlin 编译失败一次（Unresolved reference），计数器提升到闭包外。
- 🔴 新铁律候选：**MediaStore selection 里禁止 SQL 表达式/函数**，
  只允许「裸列 =/? AND」；任何过滤/归一逻辑一律内存做。

## v0.21.2 热修：日期清单与照片列表口径不一致（推翻 v0.21.1 的根因判断）

老板确认「已是 v0.21.1 最新包」仍复现 → 我的 ROM selection 表达式判断
不成立（v0.21.1 里过滤与日历已是同一套内存逻辑，不可能打架）。
**重新取证定位到真根因（与 ROM 无关）**：
- `_days = await svc.queryDays()` **不带相册**；`queryImages(bucket: _bucket)`
  **带相册** → 两个数据集不一致：日历按全部相册算「哪天有照片」，
  列表只在记住的相册里找 → 选 9/29 空态。
- `_bucket` 由 `gallery.last_bucket` 恢复（`_init` 160 行）→ **换台手机
  表现不同**（别的手机没选过相册 → 不复现），正好解释老板说的
  「其他手机可以，我手机不行」。
- 修复：queryDays 带 bucket；切相册时 _init 同步刷新清单；空态写明
  「「X」相册在 YYYY/MM/DD 这一天没有照片」+ 两个一键退路
  （查看全部日期 / 查看全部相册）。
- 🔴 教训（方法论）：**两个 UI 元素声称同一件事时，先查它们是不是查的
  同一批数据**；ROM 差异是最诱人但最易误判的解释，先排「口径不同源」
  这种与设备无关的原因。另：v0.21.1 的 SQL→内存改动保留（无害且降风险）。
