## productlib 三处修复（老板报障 + 布局推翻重来）

### 1. 大图查看器被抽屉遮挡（老板截图报障）
根因：`#mask` z-index 50 < `#drawer` 55。抽屉开着点照片看大图，

header 30 / 遮罩 55 / 抽屉 bdrawer·pdrawer 60 / **照片详情 #drawer 65** /
大图 #mask 70 / stdEd 80 / **#toast 90**。

### 2. 已关联照片不再显示「建议关联」
drawer.js：`links.length>0` 时区块不渲染，且**连 /candidates 请求都不发**。
要改关联 → 先在「已关联产品」解除 → 候选自然回来。
⚠️ `dwLink`/`dwCode` 绑定必须加存在性保护（区块可能不渲染），
`if(!$('#dwCands')) return;` 提前退出，别去请求候选。

### 3. 产品库布局：左右/上下都被推翻 → 全宽表格 + 大抽屉
老板：两个方案「似乎都不是最优」。左右 = 表格压到 36% 宽；
上下 = 点一下要滚到屏幕另一头。
最终方案：**列表面板全宽（实测 1239px）+ 点行滑出 1150px 大抽屉**，
关掉回到列表原位（翻页/搜索/滚动位置不丢）。
- 删 `#pLayout` 按钮与 `.stack` 样式（切换已无意义）
- `#pDetail` 移出 section 变成 fixed 抽屉（模式复用照片批次抽屉）
- `openProduct` 先 `openProductDrawer()` 再取数（体感快）
- 删除产品后 `closeProductDrawer()`
- Esc 关闭走 `onEscape`（products.js 要补 import onEscape）

## 照片查重功能收尾（Flutter 侧，接续上文未提交的改动）

需求：老板「同一组间照片和不同分组间的照片，原则上不能重复，
请向用户在合适位置、显眼位置提示」。三项拍板：判定口径=字节级一致 /
提示位置=顶部橙色横幅 / 处理方式=列出来+一键删冗余（保留最早一张）。

### 实现要点（详见 CHANGELOG 0.15.0）
- `photos.content_hash` 列（schema **3→4**，**只加列不回填**）+ `@TableIndex`。
  回填交给 `backfillHashes` 进页时后台分批（batchSize=20、一次原生往返、
  **有失败就停**防死循环）—— 老项目上千张，迁移时同步算会卡死升级。
- 指纹 = 「文件大小 + 前 64KB 的 SHA-256 前 8 字节」，**不全文件读**
  （1200 张 × 2.4MB = 2.9GB IO，现场等不起）。原生 `PerfBridge.hashFiles`。
- 拍照路径 `unawaited`（不拖住下一张快门）；导入路径 `await` 整批
  （已在进度对话框内，且"导完就知道有没有重复"是刚需）。
- **NULL = "还没算过"不是"不重复"**：判重 SQL 必须带
  `content_hash IS NOT NULL`，否则上千张老照片会被误报成彼此重复。
- 监装部类下不显示横幅（监装墙是流水，不存在"重复"这个业务概念）。
- **刻意不自动删**：同组内重复可能是故意拍两张存档，机器分不清，只列出来。

### 写测试时发现并修掉的真缺陷
1. **横幅首帧显示橙色「发现 0 张重复照片」** —— provider 首次加载期间
   `duplicateCount` 还是 0，旧逻辑照直渲染成"发现 0 张"。还没查就宣布"没有"，
   比不提示更糟，用户还会以为已经查过了。改：`pending = scanning || (!hasDup && loading)`，
   loading 态渲染灰色「正在核查照片重复…」。
   ⚠️ 注意这个 bug 只在 `pumpAndSettle` 的 widget 测试里撞见过 —— 纯
   `DuplicateReport` 单测测不出来，因为 `loading` 是 UI 侧的独立入参。

2. **加新 provider 打破既有 widget 测试**：`console_tabs_test.dart` 4 条
   全挂在 `pumpAndSettle timed out`（一条挂 8 秒共 32 秒，很像 flaky）。
   根因：脚手架只覆写自己关心的 provider，新 provider 真去跑
   `backfillHashes` 走原生通道，而 loading 态 `CircularProgressIndicator`
   永转 → 帧永不静止。修法：补 `duplicateReportProvider.overrideWith`。
   **教训：改页面结构前先 `grep -rln "providers.dart" test/` 一次补齐。**

3. **探针改错行 = 假探针**：验证 NULL 过滤时我把 PROBE 注释加在
   `GROUP BY` 行（真正的 `IS NOT NULL` 在上一行 WHERE），探针跑完仍
   `All tests passed` —— 等于什么都没验证。改对行后 `+27 -2` 立刻红。
   **判据：探针必须出现 `-N` 且失败用例名正是预期那条。**

### 验证结果
- `duplicate_photos_test.dart` 29 条（判重不漏报/不误报、NULL 语义、跨组 vs 同组、
  `photosMissingHash` 顺序与 limit、`backfillHashes` 分批与失败即停、横幅三形态）。
- 探针 2 次：① 回退横幅修复 → `+27 -1`；② 去掉 SQL `IS NOT NULL` → `+27 -2`。
- analyze `No issues found` / 架构 3 条 `RESULT: PASS`。
- flutter test 全量首次 `+379 -4`（即上面第 2 点），补 override 后重跑待确认。

## 标准产品页四项（老板报障：待关对不上 / 切换 / 保存 / 噪音提示）

### 1. 表格「1 待关」但详情一张没有 —— 口径两处各写一份
根因：列表 `list_products` 的 `cand_count` 是裸 SQL（只排 `is_dup`），
详情 `product_candidates` 额外排除了 `NO_LINK_KINDS + scene`。
**装箱单（packing_list）上印着整箱所有编码**，被列表算成候选，进详情又被滤掉。
实测 127 个产品 cand>0、其中 **45 个详情为空**。
修法：抽 `store._cand_filter_sql(alias='')`，**两边共用同一条过滤**。
结果：cand>0 127→**4**，详情为空 45→**0**。
⚠️ 不把装箱单照放出来是刻意的 —— 拿它关联会把一件货连到几十个产品上
（铁律 15：错关联比没关联危险）。
⚠️ A/B 实测 600 条时 OLD 5.04s / NEW 5.64s，只慢 12%，不是退化；
前端只用 limit=50（0.54s）。

### 2. 抽屉快速切换产品
头部加「← 上一个 / 下一个 →」+ `#pPos`（第 n / 596 条），
键盘 `↑↓←→`（焦点在 input 时不抢）。
模块内维护 `pCodes/pSel/pTotal/pPages`：`gotoProduct(delta)` 走到页边界
自动翻页，列表选中行 `.sel` 跟随 + `scrollIntoView({block:'nearest'})`。
⚠️ `onEscape` 是 `fn()` 无参调用，所以 `closeProductDrawer(force)` 不会
被 event 误当 force —— 但自己加 `document.addEventListener('keydown')` 时要注意。

### 3. 字段编辑改显式保存（原来失焦即存）
`pDraft` 快照比对 → 「保存修改 / 还原」按钮（未改时 disabled），
`peMsg` 显示「有未保存的修改」。回车 = 保存。保存后 `loadProducts(false)`
同步列表品名（不重置页码）。
**有未保存改动时离开必须 confirm**（`confirmLeave()`，关闭/遮罩/Esc/切产品
全走它），删除产品用 `closeProductDrawer(true)` 强制关。

### 4. 移除「N 个批次未拍到」提示
标题 tag 与底部 `.bmiss` 块全删（后端仍返回 `missing_batches`，前端不用）。
老板口径：这是噪音。

列表待关行 → 详情确有候选 / 上下切换 + 列表跟随 + 位置更新 + 键盘 ↓ /

## 再修两个遮挡/Esc（老板：产品抽屉里点照片详情被盖住）

### 1. 照片详情抽屉被产品抽屉盖住
`#drawer` z-index **55 < `.pdrawer` 60** → 从产品详情点照片，详情弹出来却压在
产品抽屉下面（和 10-04 第一个 bug 是同一类，只是这次是抽屉压抽屉，不是 mask）。
把 `#drawer` 提到 **65**（> 产品/批次抽屉 60，< 大图 `#mask` 70）。
顺手把 `#toast` 60 → **90**（提示必须压过所有浮层，否则详情里保存完看不见反馈）。

**z-index 全表（记牢）**：header 30 / 遮罩 55 / 抽屉 bdrawer·pdrawer 60 /
**照片详情 #drawer 65** / 大图 #mask 70 / 标准图编辑器 #stdEd 80 / **#toast 90**。

### 2. Esc 一次关两层（连带缺陷，老板没报，验遮挡时撞见）
`core.js` 的 `ESC_HANDLERS` 是**正序全跑**，而 drawer.js 注册的处理器是
「一把全关」（drawer + mask + stdEd 一起 remove），products.js 又注册了关产品抽屉
→ 一次 Esc 把照片详情和产品详情都关了。
修法两条：① `ESC_HANDLERS` **逆序执行**，处理器 `return true` = 消费掉这次按键，
后面的层不再关；② drawer.js 改成**逐层关**（mask → stdEd → drawer，关一层就 return true）；
products/batches 只在自己开着时关并返回 true。
⚠️ 关 mask 必须调 `resetViewer()`（重置缩放），只 remove('on') 会留下缩放态。
⚠️ **第一版只做「逆序执行」是错的**：`photos.js ↔ drawer.js` 互相 import，
   模块实际执行顺序 ≠ main.js 里的 import 书写顺序，实测 drawer 的钩子排到了
   products **前面**，逆序后 products 先关产品抽屉并 return true，照片详情留在屏幕上。
   改成 `onEscape(fn, prio)` **显式优先级**（drawer 50 > 产品/批次抽屉 10），
   按 prio 降序执行。**教训：有循环依赖时，注册顺序不可信 —— 层级必须显式声明。**

## 同组连拍改按拍照时间分组（老板：「同组连拍照片，要实现拍照时间」）

### 决策过程（两次问老板，都是拿实测数据问的）
1. 老板选「分组按时间，去掉 12 张硬切」。
2. 试算发现问题：纯按 45 秒间隔 → **197 组变 92 组，最大组 412 张**。
   原因：主力那批（2026-09-16 App 采集，515 张）是 **0~2 秒一张的连续流**
   （p50=0s / p90=2s / p99=4s），整段只有 2 个 >45s 的断点。
   → 同组待确认会一次列出 400 张候选，等于报废。
3. 拿「间隔 45s + 上限 12/20/30/50/无」的对照数字再问 → 老板选 **上限 30**。

### 最终口径
- 主规则 = 拍照时间间隔 > `GROUP_GAP_SEC`(45s) 才切；
- 张数上限 12 → **30**，**只作安全阀**（不是主规则，别再写回去）；
- 时间缺失的照片**各自单独成组，不猜**；
- 组的真实标识仍是 **(batch_id, group_idx)**，跨批次不混。
- 结果：1678 张 / 7 批次，**197 → 128 组，最大组 30 张**（中位 7 张）。

### 实现
- `tools/build_library.py`：scan_photos 分组逻辑（常量 + 报告文案同步）。
- `store.regroup_photos_by_time(batch_id, dry_run, gap_sec, max_per_group)`：
  **只改 photos.group_idx**，不动 links / 文件 / 识别结果；支持 dry_run。
- 入口：`cli regroup [--dry-run --gap N --max N --batch ID]`、
  `POST /api/photos/regroup?dry_run=1`。
- 真实库已重算，写库前备份 `productlib.db.bak-regroup-081656`（字节数校验一致）。
  ⚠️ 重算后 `links` 363 条里多的 4 条是老板 21:17-21:19 在界面上点的
  （`manual`/`created_by=web`），**不是重算写的** —— 别误判，先查 source/created_by。

### 验证
`tests/regroup.py` **13 项 ALL_PASS**：30 张连拍 → **1 组**（老口径 3 组）、
35 张 → [30,5]、间隔 100s 切开、无时间各自成组、dry_run 不写库、不动 links。
units + relink 仍 ALL_PASS；新端点 dry_run `changed=0`（幂等）。

### 教训
**改分组口径前必须先 dry-run 看组规模分布** —— 「按时间分组」在连续流数据上
会退化成「整个批次一组」。数字（最大组张数）比概念更能说明可行与否。
