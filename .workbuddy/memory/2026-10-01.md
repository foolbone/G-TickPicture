### 两个真机 bug（重要）

1. **分卷后分享面板没有微信** —— 根因在 share_plus-10.1.4 `Share.kt` 的 `shareFiles`：
   **1 个文件 → `ACTION_SEND`；≥2 个 → `ACTION_SEND_MULTIPLE`**，而微信只注册了 ACTION_SEND。
   修法不是"别分卷"，而是**逐卷发送**（每卷单文件 ACTION_SEND）。
   抽 `domain/export/delivery_share.dart::DeliverySharer`（注入 `ShareFiles` 函数），
   使"每次只传 1 个文件"可单测。UI：每卷一行 + 已发送标记 + 一次全发（注明不含微信）。
2. **自动分卷被挂在压缩画质下** —— 耦合是反的：关压缩走原图更容易破 1GB，更需要分卷。
   domain 层本来就独立（只有 UI 用 `if (compressPhotos)` 包着），提为顶层即可。
3. 顺手修潜伏 bug：`photoConfirmed - photoUnassigned` —— 两者是**互斥的 photos.state**，
   相减无意义且会出负数 → 改相加。

### 发版 flaky 排查（v0.14.0 第一次 release 失败的真因）

release 门禁报「353 过 / 1 挂」，且失败计数 `+251 -1` 出现在 export 压测窗口（01:48），
单跑 project_list_test 又全绿 —— 极易误判成 project_list 的 widget flaky。
**真相在 `%TEMP%\gt_release_test.txt`（release.ps1 留下的完整测试日志，UTF-16LE）**：
挂的是 `photo_exif_test.dart` ——
① tearDown 的 `tmp.delete(recursive: true)` 在 Windows 上偶发 errno 32
（刚写的文件被句柄/杀软短暂占用），PathAccessException 直接红；
② 全量时 1000 张压测吃满 CPU，30 秒默认超时被饿穿。
修法（都在测试侧）：tearDown 改 5×200ms 重试 + 最终放弃（systemTemp 系统回收）；
文件级 `@Timeout(Duration(minutes: 2))`。

**排查方法论**：flutter test 输出里失败用例名可能与实际失败的测试**错位**
（`-1` 计数挂在你没在跑的测试名下）；别信摘要行，去完整日志里找 `[E]` 和异常原文。

**二次踩坑**：`@Timeout` 挂在 `main()` 上报 `invalid_annotation_target` ——
它只能标 **library / group / test**，库级写法是文件顶部 `@Timeout(...) library;`。
