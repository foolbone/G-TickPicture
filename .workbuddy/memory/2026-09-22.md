## 预检拍照 APP 设计方案 v1.0

- 需求：仓库预检人员用的手机 APP（拍照取证 → 归货 → 打包 → 微信发给后端报告制作人员）。9 条原始需求整理为 11 章完整设计实现方案。
- 技术路线（老板确认）：**仅 Android** + **Flutter 3.x** + **通用 WebDAV 协议**（兼容坚果云/Nextcloud/群晖）。免登录、离线优先。
- 核心设计决策：
  1. **照片—货品绑定三级策略** —— 一级「显式上下文」（点货品进拍照页，照片自动归属，100% 可靠）为主；二级「OCR 静默校验」（非阻断黄色角标）；三级「OCR 自动归档」+ 待认领池兜底。明确不让 OCR 做唯一决策者。
  2. **文件名自带归属信息**（`{项目}_{序号}_{编码}_{序号}.jpg`），数据库之外做冗余。
  3. 以「项目（预检任务）」为顶层容器；导出同时给 ZIP 原图包 + **PDF 联系表**（微信可直发、可预览）。
  4. Google ML Kit 离线 OCR，跑在常驻 isolate 的缩略图上（非预览帧），分档阈值 0.90 / 0.60，需灰度数据校准。
  5. 明确**不申请 MANAGE_EXTERNAL_STORAGE**，用 App 私有外置目录 + 分享/SAF 导出。
- 排期：7 周 1 人（6 个里程碑），**M2 结束即可灰度试用**。
- 交付物：`D:\G-TickPicture\预检拍照APP_设计方案.html`（单文件 HTML，深海军蓝 + 朱砂点缀，scroll-spy 导航，可打印）。
- 待老板确认的开放问题 Q1~Q7，最关键的是 **Q2 货品编码长什么样**（直接决定 OCR 正则与归一化规则）。建议下一步先拿 20~30 张真实标签照片做 OCR POC。

## 方案修订 v1.0 → v2.0（老板指出的方向性错误）

**老板原话**：清单中货品众多、现场货品也很多，无法做到先选货品再从现场找对应货品；只能是**先拍照，再与清单比对**。并且要支持上传手机中已有的照片。

**问题定性**：v1.0 把"清单选货 → 进拍照页"当主路径，等于把"找货"成本强加给最忙的人。现场真实动线是**跟着货走**的。

**v2.0 核心改动**：
1. **主路径反转**：随手拍 → OCR 识别编码 → 自动归档。OCR 从"校验器"升为**主路径引擎**。
2. **新增「连续拍摄分组」（Capture Session）**：45s 内连拍聚为一组，组内互相印证 + 继承归属。**废弃 v1.0 的"清单顺序邻近"先验，改为拍摄时序聚类**（v1.0 那个先验基于错误假设）。
3. **新增四态归属模型**：已确认 / 待确认（有归属带黄标）/ 冲突 / 待认领。解决"OCR 当主角必然出错"的核心矛盾——错误显性化，不静默流入报告（PDF 打黄标 + 附待核对清单）。
4. **导航重构**：拍照页成为默认首页；新增"核对"Tab（带红色角标，唯一行为驱动）；清单页从拍摄入口降级为进度看板 + 补拍定向入口。
5. **新增相册批量导入流程**：多选 → 全量 OCR → 分组预览 → 批量确认。相册照片无时序可信度，不启用分组继承，自动归档线提到 0.95。
6. **新增 AssignDecision 一等领域对象**：每次归属记录命中 token/权重/是否歧义，可追溯可复盘。
7. **排期调整**：新增 M0（3~4 天 OCR POC，必须在 M1 前跑通），OCR 从 M3 提前到 M2。总周期 7 → 7.5~8 周。
8. 新增处理：清单外货品、现场未见货品、一照多货、拆分组。

**经验教训**：做现场作业类工具设计时，**必须先还原真实动线**（几点做什么、手上拿着什么、注意力在哪），再设计流程。v1.0 的失误在于用"数据关系的逻辑"替代了"人在现场的物理逻辑"。

**下一步关键依赖**：老板提供 20~30 张真实标签照片 + 2 份真实清单 Excel → 做 M0 OCR POC → 用实测数据定阈值与规则。

## 方案修订 v2.0 → v3.0（OCR 降级为智能辅助）

**老板原话**：「按项目走的思路是对的，但是 OCR 要定位为智能辅助，给出建议，不能替代人，遵循的原则是**先批量整体拍照，然后统一对应货品，最后打包输出分享**。」

**问题定性**：v2.0 让 OCR 当了"主路径引擎"——快门按下后 300ms 由机器决定照片归属。这本质上是在**赌 OCR 精度**，一旦静默归错就流进交付物；而且它把"整理"切碎塞进了拍摄那一刻，系统复杂度全压在现场最不该复杂的那一秒。

**v3.0 核心改动**：
1. **三段式主路径**：① 批量采集（现场，零智能）→ ② 统一对应（坐下，人决策）→ ③ 打包交付。三阶段物理隔离。
2. **OCR 降为建议者**：归属（`photo.item_id` / `group.item_id`）**只能由 `AssignService` 写入且必须带 `confirmed_by`/`confirmed_at`**；OCR 结果只落 `photo_group.suggested_item_id` + `ocr_tokens`，物理隔离。置信度**不再做"自动归档线"**，只用于排序与标冲突。OCR 可在设置里一键全关。
3. **采集期三条禁令**（lint 强制）：禁 OCR（`domain/capture/` 不得 import `domain/suggest/`）、禁网络、禁弹窗。
4. **整理效率成为新的核心工程问题**（因为全人确认）。七个提速手段：时序分组、组代表图、建议置于组头、相似建议合并成块、一键确认高置信、只显示缺口、候选前缀检索。
5. **新增「清单缺口视图」**：反向列出"清单里有、但没有照片"的货品 + 「现场未见」标记。这是唯一能回答"我漏拍了哪件"的地方，且**不依赖 OCR 成功**——v2.0 完全缺失。
6. **数据模型新增**：`capture_session` / `photo_group` / `ocr_tokens` / `assignments`（决策记录，含 suggested_item_id 用于算采纳率）/ `deliveries` / `upload_tasks`。`photo.item_id` 与 `group.item_id` 是"人的领地"。
7. **关键不变式**：`confirmGroup` 事务里**先写决策记录、再改归属**——保证不存在"有归属但无记录"的状态。交付前有强制校验 SQL 断言（必须返回 0）。
8. **原始文件永不改名**；交付命名只在打包时生成副本 → 改归属零文件操作，交付包可反复重新生成。
9. **验收指标换口径**：① 归属完整性 **100%**（结构性保证，非概率）② 整理耗时 ≤12min ③ OCR 建议采纳率 ≥80% ④ 一键确认覆盖率 ≥60% ⑤ 采集零弹窗零网络。
10. **排期调整**：OCR 不再是阻塞项，POC 挪到 M0 并行。M3（约第 5.5 周）纯手动模式即可灰度，**主干不被 OCR 进度绑架**。灰度纪律：第 1 轮必须纯手动、第 2 轮才开 OCR（否则出问题分不清是整理页设计还是 OCR 建议）。

**这次调整最本质的一句话**：v2.0 问的是「怎么让机器不出错」（没有确定答案）；v3.0 问的是「怎么让人觉得对一遍很便宜」（工程可解）。**风险从不可控的精度风险，换成了可控的效率风险。**

**关键实现决策（后续勿改）**：

5. `AssignService.confirmGroup` 事务顺序：**先写 assignments 记录、再改 itemId** —— 这是 v3.0 正确性的落点
6. 环境探测必须 `Test-Path` 验证目录，不能只看环境变量

## 修复：.ps1 编码崩溃 → setup_flutter.ps1 可执行（并连带修正架构校验器）

**老板反馈**：跑 `setup_flutter.ps1` 报一屏 ParserError（"表达式或语句中包含意外的标记"），报错行号 89/134/207/209… 与实际代码对不上。

**根因（两层，第二层才是关键）**：
1. 由 Write 工具写出的 `.ps1` 是**无 BOM 的 UTF-8**，而 Windows PowerShell **5.1 按 ANSI(GBK 936) 解码** → 中文全乱码（`需要` → `闇€瑕?`）。
2. 某些 UTF-8 三字节序列的第 3 个字节被当成 GBK 前导字节，**连同后面的换行符一起被吃掉** → 报错行号整体漂移（报 89 行，实际 96 行）。所以"按报错行号去看那行，发现没问题"是正常现象。
3. **我之前的自检全绿是假绿**：我的验证环境是 PowerShell 7.6（默认 UTF-8），老板跑的是 5.1。用 pwsh 验 5.1 的东西 = 假绿。

**修复动作**：
- 三个脚本全部改写为 **UTF-8 with BOM**；改用 `powershell.exe`(5.1) 实测验证（解析 + 实跑），不再用 pwsh。
- 清掉代码页 936 表示不了的符号（`✅` `▸`），统一 `[ OK ] [SKIP] [WARN] [FAIL]`。
- 新增 `tools/fix_ps1_bom.ps1`：**纯 ASCII**（所以即使全部脚本都坏了它也能跑），幂等，只改编码不动内容，非合法 UTF-8 拒绝处理。已实跑自测（给自己补上 BOM、跳过其余 3 个）。
- 顺手修掉并行编辑导致的静默丢失（JAVA_HOME 段、sdkmanager 许可喂法、WithEmulator 选项被互相覆盖）—— **同一文件并行编辑会互相覆盖，工具仍报 success**，后续改成整文件重写。

**脚本改进**：新增 `-WithEmulator` 开关（默认不装模拟器，省 1.2 GB）；自动把 `JAVA_HOME` 指向 Android Studio 的 jbr；许可改用**逐行**管道喂 `'y'`（拼长字符串时部分 .bat 只读第一行）；`init_project.ps1` 删 lib 前先校验备份完整性（不过就 throw，一个文件都不动）；失败计数非 0 时 `exit 1`。

**连带修掉一个真实分层违规**：`check_architecture.ps1` 的规则 2 原本字面禁止非 data 层 import `data/db/database.dart`，与设计自相矛盾（`AssignService` 必须持有 DB 句柄才能保证事务），且把中文注释里的引用文字当违规 → 校验器永远红灯、没人会再看它。按"数据访问收口"的真实含义重写：**UI 层不得 import `lib/data/`；domain 层持有 AppDatabase 合法**；规则 1/3 也加入注释行豁免。重写后立刻抓出一处**真违规**：`project_console_page.dart` 为了拿类型名直接 import 了 data 层 → 把 `DeliveryReadiness` DTO 从 `data/db/integrity_checks.dart` 迁到 `domain/model/delivery_readiness.dart`（4 处引用同步更新）。

**验证证据（PowerShell 5.1 实跑，非 pwsh）**：
- 4 个脚本全部 `BOM=True` 且解析 0 error（tokens 829 / 406 / 634 / 1552）
- 脚本头部中文按 5.1 读出正常
- `check_architecture.ps1` → **exit code 0 / RESULT: PASS**（规则 1 扫 1 个 capture 文件；规则 2 扫 26 个非 data 文件含 4 个 UI 文件；规则 3 扫 26 个文件）
- `ui/` 下 import `data/` 的文件数 = 0
- 三个脚本 GBK 不可表示字符 = none

**教训**：验证脚本必须用**用户实际会用的那个运行时**，并且自检脚本本身要写成纯 ASCII，否则它自己在 5.1 下就崩。
