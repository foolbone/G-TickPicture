## 相册导入时间修复（老板报 BUG：「相册导入显示导入时间不是拍摄时间」「相差几秒分两组」）

### 根因（证据链闭合）
1. **相册导入时间错误**：`runGalleryImport` 走 `file_picker`（SAF），只回传**缓存副本路径** —— 副本 mtime = 复制那一刻（导入时刻）。落库链 `override(相册传 null) → PhotoExif（仅 JPEG，微信保存图/截图/HEIC 无 EXIF → null）→ mtime` 整批退化成导入时刻。
2. **「相差几秒却分两组」**：两个机制叠加 ——
   - 整批时间戳挤在几秒内 → 相册批次可信度检查（跨度 ≤2s 或全同 → 不可信）→ 每张独立成组；
   - 相册导入每次 `startSession(source: album)` **自成一批**，聚类按 sessionId 分桶 —— 分两次导入的照片即使时间相邻也永不同组（组表 sessionId 外键）。09-27 只给 camera 加了续接，album 被明确排除（当时的注释「来源隔离是聚类正确性的前提」把两件事混了：隔离=不跨来源混桶，≠同来源不续批）。

### 修复清单
- **原生** `GalleryBridge.kt` 加 `queryDateTakenByNames`：按 `display_name + size` 回查 MediaStore Images 表（file_picker 的 PlatformFile.name/size 是媒体库原始值），DATE_TAKEN>0 优先否则 DATE_ADDED*1000，多行命中取 max，`is_pending=0` 过滤，单条失败记日志继续；返回与请求对齐的毫秒数组，查不到=0。

- **UI** `import_actions.dart`：`pickImages()` 返回 `List<AlbumPick>`（记录类型 path/name/sizeBytes）；`runGalleryImport` 回查后作 `takenAts` 传入 `importPaths`；新增 await 后补 `context.mounted` 检查（use_build_context_synchronously）。

- 注释同步：`camera_capture_service` 时间戳优先级链（①覆盖值=微信 DATE_TAKEN / 相册回查值）。

## 相册选择器真机空态修复（老板截图：「没有可选择的照片（可能没有相册读取权限）」）

### 诊断（三个爆炸点 + 一个静默路径）
截图 = `_photos.isEmpty` 的空态文案，但 `_init` 只有 `finally` 没有 `catch` —— 任何原生异常都被吞成同一句话。排查出：
1. **`queryGalleryBuckets` 用「sortOrder 塞 GROUP BY」hack**：拼出 `ORDER BY bucket GROUP BY bucket ORDER BY cnt` 非法 SQL，AOSP 靠 SQLite 容错侥幸能跑，部分 ROM 直接 SQLiteException → 整页空。
2. **`is_pending` / `BUCKET_DISPLAY_NAME` 都是 API 29+ 列**，Android 8/9（minSdk 26~28）上 `no such column` → 空态。原注释「列全是 API 1 起就有」是错的。
3. **Android 14「仅允许选中的照片」部分授权**：查询不报错但只回用户勾选过的行 —— 若旧副本已按指引删光且没勾选任何图，0 行空态，无任何异常。permission_handler 对 VISUAL_USER_SELECTED 的判定与 MediaStore 实际口径不一致。
4. 附带发现：AppBar 6 个 action 把标题挤成「选...」。

### 修复
- **原生** `GalleryBridge.kt`：①新增 `galleryStatus`（sdkInt/granted/fullAccess，partial=granted&&!full，granted 含 VISUAL_USER_SELECTED）；②`queryGalleryImages` 版本分支（Q+ 带 is_pending/BUCKET 列，8/9 用 DATA 路径推桶名 + LIKE 桶过滤）；③`queryGalleryBuckets` 改**单列查询+内存计数**，弃 GROUP BY hack（几千行毫秒级）。
- **模型/服务**：`NativeGalleryStatus`（domain/model）；`NativeGalleryService.galleryStatus()`。
- **权限口径**：`requestGalleryPermission(ref)` 以原生状态兜底（部分授权时 permission_handler 报未授予但原生算已授权）。
- **页面**：`_init` 加 catch + galleryStatus 前置闸 —— 无权限→`_BrokenStateBox`（去授权/去系统设置两个按钮）；查询异常→原样露出 + 重试；部分授权→橙色横幅 + 去改授权；桶内空→提示切回全部相册。AppBar 6 action 收敛为 3（连选/相册过滤/更多菜单），标题不再截断。

## 空态修复第二击（老板截图：`PlatformException(QUERY_ERROR, Invalid token date_taken)`）

### 意义
上一轮的错误可视化立刻回本 —— 空态页面直接报出了异常原文，一轮截图就锁死根因，不用再猜。

### 根因（真凶，低级但隐蔽）
`MediaStore.Images.Media.DATE_TAKEN` 的**底层列名是 `datetaken`（无下划线）**。我在排序子句里裸写了 `"COALESCE(date_taken, date_added * 1000) DESC LIMIT ... OFFSET ..."` —— AOSP 上是 `no such column`，这台 vivo 的魔改 MediaProvider 则报 `Invalid token date_taken`（自定义解析器）。之前 `queryWeChatImages` / `queryDateTakenByNames` 都没踩坑，因为它们只用 SDK 常量，从未手写 `date_taken`。

### 修复
- 排序子句改用 **SDK 常量拼列名**（`"${MediaStore.Images.Media.DATE_TAKEN}"` → `datetaken`），绝不手写。
- 加**排序降级梯度**：①`COALESCE(datetaken, date_added*1000)`（修正列）→ ②裸 `datetaken`（个别 ROM 不认 COALESCE）→ ③裸 `date_added`（最终兜底）。逐级 try/catch + Log.w，总有一条能跑；查询逻辑抽成 `queryGalleryImagesOnce` 复用。
- 纪律：**SQL 片段（selection/sortOrder）里的列名一律用 SDK 常量拼，绝不手写字符串** —— 常量值和底层列名未必长得一样（DATE_TAKEN→datetaken 就是反例）。

### 验证
- 仅 Kotlin 改动，Dart 零变化（analyze/test/arch 无需重跑，Dart 测试面不变）；Kotlin 编译由 gradle 构建兜底。

## 空态修复第三击（老板截图：`Invalid token LIMIT`）

### 排查链（错误可视化三连击的价值）
1. 第一击 `Invalid token date_taken` → 列名裸写错误（datetaken 无下划线）。
2. 第二击修复列名后 → `Invalid token LIMIT` → **这台 ROM 的 MediaProvider 解析器只认「列 + 方向」，排序子句里 LIMIT/OFFSET 关键字都不放行**。反推：COALESCE(datetaken, date_added*1000) DESC 已通过解析器（错误报在 LIMIT 上）。

### 修复
- 排序子句**彻底去掉 LIMIT/OFFSET**，只留「COALESCE 修正列 + 方向」（含三级降级梯度）。
- 分页改 **cursor 端窗口**：无 LIMIT 全量排序查询 + 跳过 offset 行、收满 limit 行即止。SQL OFFSET 本来也是扫到 offset 处才取，复杂度同级；`queryGalleryImagesOnce` 加 limit/offset 参数，`while (c.moveToNext())` 里先 skip 后收、满即 break。
- 微信导入/分桶查询本来就不带 LIMIT 关键字，无需动。

### 验证
- 仅 Kotlin；build EXIT=0 + 时间戳核对 + dex 解包验证（OFFSET 关键字 0 次、COALESCE 在包）。
- **经验**：魔改 ROM 的 MediaProvider 是「白名单解析器」不是 SQLite 直通 —— 排序子句应按「最朴素的 列+方向」设计，分页逻辑放 cursor 端，别赌 ROM 放行 SQL 语法。

## 位置记忆修复（老板反馈：「重新导入时自动定位到上次最后的选择位置，好像没有实现」）

## 位置记忆第三击（老板真机反馈：「虽然有提示已回到上次浏览位置，但是实际上不是上次浏览位置」）

### 根因（两个 bug 叠加出「假成功」）
1. **主犯：恢复翻页后 GridView 不知道列表变长了**。`_restore` 翻页循环只调 `_loadMorePage()`（改 `_photos` 数据），从不 setState —— GridView 的 itemCount / maxScrollExtent 停在首帧 121 格规模。找到目标 id 后 `_jumpToIndex` 算出目标 offset（如 15k px），当前 maxScrollExtent 只有 ~5.2k → **被 clamp 截断在半路**，SnackBar 照弹成功。正常滚动的翻页能工作是因为 `_onScroll` 的 then 里有 setState —— 恢复循环里漏了。
2. **从犯：`_indexOfDateNotLaterThan` 找不到时假装找到**。目标位置太深（超 30 页上限）时返回已加载列表**最后一张**而不是 -1 → 跳到错误位置 + 提示成功。

### 修复（全在 gallery_picker_page.dart）
- 两个翻页循环每页后 `setState`（GridView 认账，maxScrollExtent 随 itemCount 增长）。
- `_restore` 跳转改**闭环**：等 maxScrollExtent 真正覆盖目标行再 jumpTo；跳完核对落点，没到位等帧重试（上限 8 次）；真跳到目标才说「已回到上次浏览位置」，否则「已回到上次浏览位置附近」。
- `_indexOfDateNotLaterThan` 加 `fallbackToEnd` 参数：时间轴定位 true（兜底最旧合理），位置恢复 false（返回 -1 走「上次浏览的照片已不在」诚实提示）。
- `_jumpToIndex` 注释明确：只用于「目标必在已加载范围」的时间轴场景，恢复路径禁用（clamp 会咬）。

### 核心教训
**数据加载 ≠ UI 认账**：改列表数据后 GridView 不 setState 就不知道；maxScrollExtent 是按 itemCount 估算的，不是按已构建格数。凡是「加载后跳转」的路径，跳转前必须确认可滚范围真的覆盖目标——**clamp 是防炸手段，不是正常路径**，静默 clamp = 静默失败。

## 位置记忆第四击 + 日期选择修复（老板真机反馈：「相册回到上次浏览位置附近，这个问题还没有解决，并且选择照片的日期选择也没有起作用」）

### 第四击根因（「附近」提示 = 跳转闭环重试 8 次仍没跳成 → 根本没跳，停在顶部）
- **目标行处于列表最后几屏时，物理上无法让行顶对齐视口顶**（maxScrollExtent = 内容高 − 视口高，目标行贴尾时 target > max 恒成立）。触发链：上次浏览位置较深 → 之后新拍照片插入列表头部 → 同一照片 idx 后移 → 目标行落入尾屏 → 上一版闭环只傻等 8 帧（setState+waitFrame），**max 明明能靠继续翻页加载增长却没加载** → 永远等不到覆盖 → jumped=false → 停在顶部弹「附近」。
- 修复：闭环里 max 不够时**继续 `_loadMorePage()`**（max 随 itemCount 增长）；翻到 `_hasMore=false` 仍覆盖不了 → **jumpTo(maxScrollExtent) 兜底**——目标行在最后一屏内滚到最深处让它可见，这是物理上最准的恢复。

### 日期选择不起作用的根因（两个）
1. `_locateToDate` 在**新→旧**列表里找「第一张不早于 day」——最新照片永远不早于任何过去的日期 → **永远命中第一张、永远跳回顶部**。
2. 选已加载范围外的老日期时**不翻页**，定位不到。
- 修复：语义改为「跳到时间不晚于当天末尾的第一张」（`endMs = 次日00:00 - 1ms`，与滑杆 `_scrollToDate` 同一条路）；目标比已加载范围更老时按时间翻页（上限 30 页）加载到该日期再跳。

- analyze **No issues found** EXIT=0（15.5s）；架构 **RESULT: PASS**。
- release APK **86,072,253 字节 @ 20:49:25**，EXIT=0，指纹 4/4 + 时间戳新鲜。

### 核心教训（滚动定位类功能）
1. **maxScrollExtent 是「内容高 − 视口高」**：尾部一屏内的行永远无法顶对齐视口顶——任何「跳到某行」的功能都必须处理这个物理边界（继续加载 or 滚到底让目标可见），否则就是静默失败。
2. **倒序列表里「第一张不早于 X」永远是最新的那张**：时间定位语义必须写清「不晚于 X」还是「不早于 X」，配一个 DESC 列表脑子里的方向箭头。

## 位置记忆第五击（真修复）· 退出再进回不到上次位置（老板反馈：「从相册选择照片后退出，再次进入相册选择无法定位到上次位置」）

### 三个独立 bug，缺一个就表现为「回到顶部」
1. **保存侧：退出那一刻 offset 已经读不到了。** 原来只在 dispose / 导入前按 `ScrollController.offset` 反算；路由拆除时 controller 常常已 detach（`hasClients=false`）→ offset 取 0 → 存下**列表第一张**（诊断实锤：`savedId=1`）。修复：滚动过程中 `_captureTop()` 实时把「顶部那张」的 id 记在字段里，dispose 只落盘（`_savePosition(resample: false)`，绝不再按失效的 offset 重算）；`_exit()`/导入前页面还活着时才 resample。
