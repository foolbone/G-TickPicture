## 修复：先导照片、后导清单 → 关联全丢（老板报的现象）

### 根因（三步，缺一不可）
1. 自动关联靠 `CodeIndex`，索引建自 **products 表**（`pipeline.govern_all`）。
   照片先导时 products 空 → `index.best()` 全 None → 零关联。
2. **但识别结果没丢**：`ocr_tokens`（逐条文本+置信度）和 `photos.vision_codes` 都已落库。
3. 清单后导后照片 `govern_state` 已是 `done`，`govern_all` 的
   `WHERE govern_state='pending'` 永远扫不到它们 → 关联永久丢，界面无任何入口能修。

实测损失：9780 条 OCR token 只命中 271 条；**656 张照片有识别产出但零关联**。

### 修法：补关联（不重跑识别、不花 API 钱）
- `pipeline._build_index(con)`：抽出的索引构造，治理与补关联共用。
- `pipeline._match_token()`：抽出单 token 判定，**govern_one 也改用它** ——
  「首次治理」和「事后补关联」必须走同一套口径，各写一份必然漂移。
- `pipeline.replay_hits()`：用已落库 token + vision_codes 重匹配。
- `pipeline.relink_due_to_checklist()`：只补**没有 auto 关联**的 done 照片
  （已有的人工关联永不动，副本靠 inherit_duplicates）。
- 接入：清单导入后自动触发（`routes/products.py`，失败不阻断导入，
  错误回带给前端）；`POST /api/products/relink` 手动兜底；`cli.py relink`；
  产品页工具栏加「补关联」按钮（index.html + products.js）。

links 324→358，**有照片产品 246→269（+23）**，人工关联 9 条未动。

### 🔴 踩坑：`written` 必须报**净增**而不是写入次数
同库两份清单的 `1000000119` 与 `1000000119.0` 归一后是同一 code_norm，
同一照片会命中两次，`INSERT OR REPLACE` 覆盖而不新增 → 报 36 实际只 +34。
已改为 before/after 集合差算净增，另返回 `replaced` 字段。

### 顺带挖出并修的两个真 bug（都早于本次改动）
1. **`upsert_products` 新增分支缺 `continue`** —— 掉进 merge 分支读
   `exist[k]` → `TypeError: 'NoneType' object is not subscriptable`。
   走 `import_checklist_file` 时 INSERT 后不 commit 就 return，
   所以这条路径**一直没被触发**，只有直接调 `upsert_products`（测试）会崩。
   **`tests/units.py` 从 09-28 起就是红的**，这次首次跑就撞上。
2. **`connect()` 的 `_schema_initialized` 是进程级 bool** —— 进程内先后连
   两个不同库（临时测试库 + 真实库）时，第二个库跳过建表 →
   `no such table: products`。改成按库绝对路径记的 set。

### 🔴 顺带挖出第 3 个真 bug：数字型编码的文本形态匹配不上
验证归一化时发现 `1000000119.0`（照片 OCR 出的**文本**）匹配不上清单里的
`1000000119`。根因：`_SEP_RE = [\s\-_·．。,，、/\\.]` **含小数点**，
`normalize('1000000119.0')` 直接压成 `10000001190`（尾部多一个 0）。

`_cell()` 文档里早就写了这个陷阱，但**只在读 Excel 时处理**（那时是 float），
照片 OCR 出来的是文本，没人管 → 首次治理和补关联**都**漏这一类。

修法（`build_library.py`）：
1. `_strip_numeric_tail(raw)`：**必须在 normalize 之前**调用（normalize 后小数点
   已被删，来不及了）。只在 `_NUM_TEXT_RE` 整串纯数字时才动，
   `1.20→1.2`、`100.→100`、混合串 `A1000000119.0B` 不动。不用 int()（2^53 精度）。
2. `variants()` 把去尾零形态作为**独立变体追加**（不替换 basic ——
   清单里可能真有编码叫 `1000000119.0`，原样必须先试）。
3. `CodeIndex.__init__` **两种形态都建键**（否则反向漏：清单 `.0` + token 整型
   只到 edit1 0.817 分）。⚠️ 两侧都要改才是双向对称。
4. 清单里两种形态并存时各归各的不串（`setdefault` 先到先得）。

⚠️ **这批真实数据上恰好零收益**（36 与修前一致）—— 这批清单编码都是文本型。
它是独立的潜在缺口，不是本次的收益来源，别当成"修了就多 36 条"。
