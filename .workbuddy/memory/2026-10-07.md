## 产品库顶栏「设置」换行修复（老板截图，纯前端）

**现象**：顶栏导航「设置」掉到第二行、压在底边框上（截图窗口 ≈1488px 宽）。CDP 实测：

## 需求①照片按「已关联 / 未关联」分组展示

**后端**：`GET /api/photos` 加**可选**查询参数 `linked=1`
（`AND p.id IN (SELECT photo_id FROM links)`）。它与既有 `unlinked=1` 是**两把独立的筛子**，
不是同一开关的两态 —— 分组视图要各发一次请求拿各自的总数，一把开关给不出「两组各多少张」。

🔴 **口径故意不对称，别当 bug 修**：`unlinked` 沿用既有写法（未关联 **且** `is_dup=0`），
`linked` 只看「在 links 表里」不排重复 —— 重复照片若被关联过就是一条有效关联。
副作用：两组之和 ≤ 该范围总数（实测 1034 + 1692 = 2726，全库 2738，差 12 张即被排除的重复照片），
所以前端文案写「共 a+b 张（已关联 a · 未关联 b）」，**不声称等于全部**。

**前端**：照片浏览工具条新增第 4 个视图「关联」（`#shotView [data-v=link]`），
向导③筛选条新增「按关联分组」复选框，两者**共用同一份** `photos.js` 的
`loadLinkGroups(boxSel, baseQs, st, reset, onInfo)` —— 两处各写一套分页口径必然漂。

- `linkSecHtml` 段头 = 色点 + 名称 + `已显示 / 总数 张` + 该组自己的「加载更多」；
- 🔴 **两组必须各发一次请求、各自独立分页**。不能「取一页再在内存里分」：
  一屏 60 张可能全是已关联，未关联组就被渲染成 0 张，看着像「没有未关联的」其实是没取到
  （铁律 17 的具体形态）。总数取自后端 COUNT，不是已取到的条数。

老板要「监装图片的监装细分，在治理中由大模型分类识别，用户可以确认修改」。
原先 `schema.py` 有一条明确的设计否决（「版位语义只能由人给」），本次推翻。

**零额外成本**：细分挂在治理**已有的那次** `vision.classify` 上（同一次视觉请求
多问一句），不新增 API 调用。提示词补了 4 组易混对照（空柜vs装柜过程 /
空柜vs柜侧 / 封条vs锁门 / 卡车头vs柜侧）+「判不准就归 other，别高置信度猜错」。

**🔴 核心设计：AI 建议绝不自动生效，分两列**
- `supervision_tag` = 人工确认值（**报告唯一依据**）
- `sup_tag_ai/_conf/_reason` = 模型建议 + 置信度 + 依据（待确认）
- `sup_tag_confirmed` = 人工是否已表态（**防重跑治理冲掉人工结果**）

理由：报告区块④的 4 张柜况代表图从 `supervision_tag` 挑，一张贴错的图会
**直接印进交给客户的正式报告**，比留空危害大得多。「还没确认」≠「没问题」。
新增 `sup_tag_pending_count` 给 UI 提示「待确认 N」。

**其它口径**：枚举外/自造值一律丢弃且置信度+理由一起清空（不许「编的值+0.9
高分」）；用途非监装不给细分，采用时再挡一次；三件套同生共死。

### 踩坑（都是实测撞出来的）

1. 🔴 **路由顺序吃掉字面量端点**：`/api/photos/{pid}` 注册在前，把
   `'supervision-tags'` 当 pid 吞了 —— 端点写对、`checks/routes.py` 也绿，
   但 GET 返回的是**照片详情的形状**。已把字面量路由移到 `{pid}` 之前，
   并在 `tests/sup_tag.py` 写死顺序断言（**routes.py 只校验端点存在，
   抓不到顺序错位**）。
2. **筛建议/造数据必须用 `paths.db_path()`**，别自己拼路径（应用真正用的那个库）。
3. 服务端会清掉 `path` 指向文件已不存在的照片 → 造 UI 数据必须**真的生成 jpg**，
   否则缩略图 404、照片卡不渲染，抽屉打不开，后面每条断言都假失败。

## 产品库改名 + 柜号筛选「全部柜号」覆盖不全（commit 2f43f6b）

老板报「筛选的『全部柜号』没有所有的柜号」。

### 根因：柜号解析散在三处，且都只认**已废弃的冗余列**

`list_products` / `count_products` / `product_containers` 各写一份 SQL，
三份都 JOIN `batches.container_no` —— 那列 v3 就降级成「冗余只读列」
（schema 注释原话），早停更了。真实库实测（改之前）：

- 22 个批次里 **13 个 container_no IS NULL** → 产品整批漏在统计外；
- 未分柜只统计到 **524**，真值 **781**（NULL 那 634 行一条没进来）；
- 三档之和 **1051 ≠ 不筛选总数 786**，互相重叠且对不上全库。

修法：新增 `_container_filter_sql` / `_container_list_sql` 作**唯一真源**，
三处共用。口径 ①container_id→containers（权威）②batches.container_no
直接相等（**老库兜底**，没挂 container_id 的批次不能凭空消失）。
`product_containers` 现在**列出柜实体表每一个柜，含 0 件的空柜**（否则用户
想查「这柜为什么一件都没有」时下拉里选不到它）。两路命中同一柜号取 max
**不能相加**（相加重复计数）。

改后：未分柜 524→781；并集 786 == 总数 786，零产品隐形。

### ⚠️ 别写错断言：「各柜之和 == 总数」是**错的**

同一产品可以出现在多个柜的清单里（真实库 EMCU 447 + 未分柜 785，并集 786），
逐档相加天然 > 总数，那是**正常重叠不是 bug**。真正的不变量是
**「并集 == 总数 - 无归属产品数」**。我第一版就写错了断言，改对。
