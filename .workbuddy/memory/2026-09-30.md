### 经验教训
1. **analyze 门禁字面匹配 `No issues found`** —— 死代码 / 未用 import 都
   会 fail 发版。删 OCR 类必须**整类删干净**，不能留死代码「等以后用」。

3. **`unawaited` 在测试场景下是定时炸弹** —— 凡是测试会 await 的入口

## v0.8.1 真机反馈修复（同日）

老板装 v0.8.0 后反馈「从相册导入后组内缩略图还是显示不出来」。

**根因**：v0.8.0 的 backfill 只挂在 `OrganizePage.initState`，
但 `OrganizePage` 是 `IndexedStack` 子页 —— **进项目那一刻就 initState**，
此时项目里还没刚导入的照片，backfill 找不到 missing；等用户点「从相册
导入」完成后，initState 不会再触发，新照片 `thumbPath` 永远 null，UI
显示空图标。

**修法**：在 `import_paths.dart` 的 `importPaths` 尾段（导入落库后、
SnackBar 之前）`unawaited` 启动 `backfillThumbnails`，补完
`ref.invalidate(openGroups/assignedGroups/supervisionPhotos)` 让
整理页三个流重读新 thumbPath。用 unawaited 而非 await：
①不阻塞 SnackBar 反馈；②不在测试场景（测试调 svc.importFromGallery
不调本函数），无 path_provider channel race。try/catch 兜底 widget
dispose 后 invalidate 抛错。

**经验教训 5**：IndexedStack 子页的 initState 时机 ≠ 用户实际操作
时机。IndexedStack 进项目就构建所有 tab，initState 在那一刻全跑完。
任何「进页跑一次」逻辑对「进页后才产生的数据」无效 —— 必须把这类
逻辑挂到「数据产生的动作」上（如导入按钮回调），而非挂到页面的
initState。

发版门禁全过：analyze 5.3s / test 337 / 架构 PASS / build OK。
pubspec 0.8.0+7 → 0.8.1+8（versionCode 7→8）。

## 14:20 修复「打交付包 APP 直接崩溃退出」+ 移除 PDF 联系表 → v0.10.1

**现象**：老板真机验收 v0.10.0 —— 1000+ 张 / 70+ 组打交付包，**APP 直接崩溃退出**
（不是卡死，是被系统杀进程 = OOM）。v0.10.0 的流式 ZIP 修复无效。

**根因（真凶 = PDF 联系表，不是 ZIP）**：
- `ExportOptions.includePdf` **默认 true** → 人人打交付包都会生成 PDF。
- `_writeContactSheet` 把 1000+ 张图的 JPEG 字节全攒进 `List<PdfTile>`；
  缩略图缺失时**退到读原图**（2-4MB/张）→ 2-4GB 常驻。
- `buildContactSheetPdf` 用 `List<int>[...head, ...jpegBytes, ...tail]`
  把每张图**展开复制**（`List<int>` 是 boxed，内存放大 8-10 倍），
  `_assemble` 的 `BytesBuilder` 再一份、`toBytes()` 又一份。
- 三者叠加 → 必 OOM。**ZIP 那条线经源码核实确是流式的**
  （`InputFileStream` 1MB 分块 + `output.writeInputStream`），不是问题。

**教训：定位性能崩溃要看「谁把全部数据攒进内存」，别只盯最后一步。**
上一轮只盯 92%（ZIP），漏掉了 78%-90% 的 PDF 阶段才是炸弹。

**处置（老板 09-30：「不需要 PDF 联系表」）**：
- 删 `pdf_contact_sheet.dart`（整模块）+ `_writeContactSheet` + 相关测试；
  `ExportOptions` 去掉 `includePdf`/`litePdf`、`ExportEstimate` 去掉 `pdfBytes`、
  `DeliveryResult` 去掉 `pdfPath`；交付页去掉 PDF 勾选框。
- `deliveries.pdf_path` DB 列**保留不动**（避免 schema 迁移）。
- 交付包现在 = 预检/监装 照片 + `_对照表.csv` + `_清单缺口.txt` + `manifest.json` + ZIP。
- 加防回归断言：交付包根目录不含 `联系表.pdf`。

## 17:20 交付包去掉对照表/清单缺口 + 打成「打包卡死」真根因 → v0.11.0

**A. 交付包精简（老板 09-30：「对照表、清单缺口这些都可以不要」）**
- 包内不再产出 `_对照表.csv` / `_清单缺口.txt`；交付包 = 预检/监装 照片 + `_未使用/`(可选) + `manifest.json` + ZIP。
- 删 `DeliveryPlan.buildCrossReferenceCsv()` / `buildGapReport()` 及 `_csv`/`_fmtTime`；UI 文案、注释、测试断言同步清理（测试改为断言这两个文件**不出现**）。
- 缺口/未对应信息仍全在 `manifest.json` 里，报告员直接翻照片。

**B. 打包卡死真根因（第三轮排查终于打中）**
- v0.10.0（流式 ZIP）、v0.10.1（去 PDF）都没打中。这轮靠**插桩 + 分阶段基准**才看到：
  **整条链路每个文件一次 `await`** —— `await File(src).exists()`（而且跑在**主 isolate** 上）/ `await File.copy()` /
  `await ZipFileEncoder.addFile()`（内部 `await stream.close()`）。
- 实测：每次「发起异步 IO → 等事件循环回投完成事件」的往返 ~100–184ms，**与字节数无关**。
  1000×64KB：异步复制 184s，同步复制 9–21s。**慢的不是吞吐，是那一次 await。**
  `openRead()` 纯读只要 1.1ms/文件（读不慢）；`IOSink.addStream` 最慢（42–104ms/文件）。
- 修复三处：①打包链路**全同步**（`copySync` / `writeAsStringSync` / 同步 `ZipEncoder.addFile` +
  `InputFileStream`/`OutputFileStream`；`ZipFileEncoder.addFile` 是 async 不能用）；
  ②整条重 IO 搬**后台 isolate**（UI 全程不阻塞，进度节流 ~100 条，取消会清半成品 zip）；
  ③汇总清单与自检去 await（`existsSync()`；自检改用复制清单长度，不再 `list(recursive:true)`）。
- 压力测试从「5 分钟硬超时」→ 通过（本机 205–230s；但 **Windows+Defender 同代码波动 2–8 倍**，
  绝对值不可跨机比较）。测试超时放宽到 10 分钟防假红。
- 并行 worker 实测只快 ~1.8×（单条 ZIP 输出流无法并行）→ 不做，保持简单。

## v0.12.0（同日下午）：微信 1GB 限制 → 压缩 + 分卷

- 老板拍板：**压缩画质（不能丢关键信息：标签/箱号必须可读）+ 超限自动分卷**；分卷是**可选开关**（默认开，关掉出单包走网盘）；单卷上限 **500MB**。
- 实现：
  - 原生 `PerfBridge.compressPhotos`（ARGB_8888 + inSampleSize + JPEG **2560px/q85**；原图长边不超目标 → `skipped=true` **原图直出**；单张失败 → Dart 侧回退 `copySync` 原图，**压缩失败绝不丢照片**）。原生**串行**（12MP 位图 48MB，并发顶爆低配机），Dart 按 8 张/块调通道、回进度。
  - `volume_planner.dart` 纯函数 `planVolumes(sizes, limit)`：贪心保序、绝不拆文件、单文件超限独占一卷。测试独立成 `volume_planner_test.dart`。
  - `_packEntry`：分卷后每卷都含 manifest.json（修复：此前 ZIP 里根本没有 manifest）；卷名 `…_第NN卷-共MM卷.zip`；取消清理改为按前缀删全部半成品卷。
  - `ExportOptions` 加 `compressPhotos` / `splitVolumes`（默认 true）+ `volumeLimitBytes`（默认 500MB，测试可传小值驱动多卷路径）。DB 两列不迁移：zipPath 存第一卷、bytes 存总和；`DeliveryResult.volumes` 才是全量。
- **三个测试教训**：
  1. **mock 通道写 dst 前目录必须已存在** —— compress 阶段（主 isolate）在包内子目录创建之前跑，mock `writeAsBytes` 抛异常被 PerfBridge 吞成空列表 → 全部回退原图。修法：目录创建提前到 compress 之前（build 里同步建，目录数≈箱号数+2 与照片数无关）。真实原生会自行 mkdirs，但替身不会 —— mock 逼出了这个真实顺序缺陷。
  2. **进度必须单调钳制** —— 压缩段与复制段分段算浮点比例，交界处 1e-16 回退（0.6000000000000001→0.6）。修法：build 的 tick 包装里 `_lastRatio` 钳制。且 copyFrom 由 `compressAttempted`（开关）决定而非 flags（全回退时进度不能跳回 0.05）。
  3. 全量测试里「压缩开」的失败只在**有 binding 的环境下暴露**（setUp ensureInitialized 全局生效）——单文件隔离跑不出来，全量跑必跑。
- 压力测试（compressPhotos:false）232s / RSS +23MB 依旧稳。
