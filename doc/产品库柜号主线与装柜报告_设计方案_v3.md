## 一、总原则：柜是一等实体，流程有闸门

### 1.1 现状问题

柜号目前只是 `batches` 上的一个**可空文本字段**，四处导入 API（清单导入 /
照片目录 / 自动探测 / 文件上传）都收 `container_no` 但**不强制**——
不填柜号照样导，流程"顺"但数据是散的：批次列表里柜号有无随缘、
检索按批次勾而不是按柜、报告生成时才发现柜号对不齐。

### 1.2 目标流程（五步，柜是第一步也是唯一入口）

```
┌─ ① 建柜 ────┬─ ② 导清单 ────┬─ ③ 导照片 ────┬─ ④ 治理/关联 ──┬─ ⑤ 出报告 ─┐
│ 柜号(必填)  │ 挂到柜下      │ 挂到柜下      │ 按柜过滤      │ 按柜出docx │
│ 封条号(后补)│ 行快照落库    │ 自动提箱号    │ 打用途/标签   │ 8区块      │
└─────────────┴───────────────┴───────────────┴───────────────┴────────────┘
       ↑ 无柜号 = 四个导入 API 一律 400「请先选择柜」——闸门在后端，不只在前端
```

柜详情页是 ②③④⑤ 的聚合面板；批次页降级为柜详情里的列表区块。

## 二、数据模型改造

### 2.1 新表 `containers`（柜，一等实体）

```sql
CREATE TABLE IF NOT EXISTS containers (
    id            TEXT PRIMARY KEY,     -- uuid
    container_no  TEXT NOT NULL UNIQUE, -- 柜号（ISO 6346，如 EMCU9914616）
    seal_no       TEXT,                 -- 封条号
    arrival_at    TEXT,                 -- 到柜时间
    departure_at  TEXT,                 -- 离柜时间
    inspector     TEXT,                 -- Inspector（报告②区块）
    location      TEXT,                 -- Inspection Location
    remark        TEXT,                 -- REMARKS（报告③区块）
    client_name   TEXT,                 -- Client Name（报告②区块）
    product_name  TEXT,                 -- Product Name（报告②区块）
    created_at    TEXT NOT NULL,
    updated_at    TEXT NOT NULL
);
```

柜元数据直接住 containers（v2 放 batches 上是错的：一个柜有清单批次 + 照片批次
多个批次，柜级字段放批次上就得选"写哪个批次"，必然漂移）。

### 2.2 `batches` 挂柜（列改造）

```sql
ALTER TABLE batches ADD COLUMN container_id TEXT REFERENCES containers(id);
CREATE INDEX IF NOT EXISTS idx_batches_ctn ON batches(container_id);
```

- 旧列 `batches.container_no` **保留不删**（读兼容），但写入路径统一改为
  `container_id`，`container_no` 由 store 同步冗余（一个真相源 = containers 表）。
- **迁移**（`_migrate` 里跑，一次性）：按现存 `batches.container_no` 分组自动建柜；
  空柜号的老批次挂进一个自动建的兜底柜（container_no = `_UNCATEGORIZED`，
  UI 显示为「未分柜（N 批）」并提示补柜号后可改挂）。

### 2.3 照片挂柜（经批次）+ 监装标签

照片已有 `batch_id`，柜归属经批次传导，**photos 不加 container_id 列**——
多一列冗余就多一个失同步的机会，查询经 join 一次到位。

```sql
ALTER TABLE photos ADD COLUMN supervision_tag TEXT;
-- empty_container / container_side / container_seal /
-- container_lock / truck_head / loading_process / other
CREATE INDEX IF NOT EXISTS idx_photos_suptag ON photos(supervision_tag);
```

柜况 4 图（报告④区块）= tag 定候选 + 每类一张代表图（默认该 tag 最新一张，
柜详情页可换）。**不建槽位表**：tag 已表达"这张照片是什么"，
槽位表只会造出第二个真相源。

### 2.4 新表 `checklist_rows`（清单行快照，报告⑤区块的数据源）

```sql
CREATE TABLE IF NOT EXISTS checklist_rows (
    batch_id     TEXT NOT NULL,       -- 清单批次（batches.id, kind='checklist'）
    seq          INTEGER NOT NULL,    -- 清单内行序（同码多行各自占一 seq）
    code         TEXT NOT NULL,       -- 原始编码（照抄）
    code_norm    TEXT NOT NULL,
    name         TEXT,                -- DESCRIPTION
    spec         TEXT,
    package_no   TEXT,                -- Package Number（向下填充后的值）
    order_qty    TEXT,                -- 存文本照抄（12 / 12.0 / "12 PCS" 都有）
    loading_qty  TEXT,
    check_import TEXT,                -- 清单预填的 Quantity Check result（客户的值）
    check_result TEXT,                -- 人工核对结论；NULL = 沿用 check_import
    taken_at     TEXT, taken_by TEXT, -- 核对留痕
    PRIMARY KEY (batch_id, seq)
);
CREATE INDEX IF NOT EXISTS idx_clrows_norm ON checklist_rows(code_norm);
```

`parse_checklist` 同步扩展：`qty` 单列识别拆成 `order_qty` / `loading_qty`
两套 hints（`orderqty` / `loadingqty` 精确词优先，旧 `qty` 兜底归 order_qty），
新增 `check_result` hints（`quantitycheck` / `checkresult`）。
重复导入同柜清单 → 整批替换该 batch 的行快照（清单是权威快照）。

### 2.5 闸门 API 改造（后端强制）

| API | 改造 |
|---|---|
| `POST /api/checklist/import` | `container_id` 必填，缺失 400「请先选择柜」 |
| `POST /api/photos/import` / `import-auto` / `upload`（共 4 处） | 同上 |
| 新增柜 CRUD：`GET/POST /api/containers`、`GET /api/containers/{id}`（详情聚合）、`PUT`（改元数据/换代表图）、`POST /api/containers/{id}/reassign`（未分柜批次改挂） | 柜先行的入口 |

前端把批次页升级为柜页，但**闸门在后端**——前端拦得住误操作，拦不住脚本。

## 三、照片尺寸与排版方向：在哪处理（老板问题②的正面回答）

### 3.1 决策表（先给结论）

| 问题 | 处理环节 | 机制 | 为什么 |
|---|---|---|---|
| **EXIF 方向自动矫正** | **报告生成**（读取时） | PIL `exif_transpose` 后再算宽高比 | 不改原图文件；EXIF Orientation 存在与否都正确摆正 |
| **版位尺寸适配**（横/竖/方图进同一网格） | **报告生成** | 固定格宽 + 高按宽高比 + 上限钳制（3.3 节） | 版式是**模板的属性**不是数据的属性；换模板不重跑治理 |
| **嵌入分辨率**（压缩档） | **报告生成** | 按版位宽 × 300DPI 算，统一 1200px 档 | 原图不动；3.2" 格宽 @300DPI ≈ 960px，1200px 已超配 |
| **人工修图**（照片歪了/方向错/要裁） | **治理环节** | `standard_images`（**已有机制**：人工裁剪成标准资产） | 修图是人工决策，产物是独立资产，原图仍不动 |
| **报告用哪个版本的照片** | **报告生成** | 有标准图 → 用标准图；无 → 回退原图 | 复用「导出标准库」既有先例，零新概念 |

**一句话原则：治理环节只产生元数据（kind / tag / 关联 / 标准图），永远不碰像素；
报告生成环节负责一切"为了版面"的处理（方向矫正 / 缩放 / 适配）。**

### 3.2 为什么不在治理环节处理尺寸/方向

1. **证据保全**：项目铁律「原始文件是证据，任何改写都是篡改风险」。
   治理管道写像素 = 治理失败时原图已丢。
2. **一图多消费者**：同一张照片要出素材包（1600px）、标准库（裁剪版）、
   装柜报告（版位适配）——三个消费者三套尺寸，在治理时固化一个尺寸是错误抽象。
3. **版式迭代成本**：报告模板改版位（2 列 → 3 列、A4 → 横版）只改生成器参数；
   尺寸若在治理定死，每次改版式要重跑全量治理管道。
4. **治理已有正确的"修图"落点**：standard_images 正是"人觉得这张图该修"的产物，
   报告优先用它——职责边界清晰：**机器适配版位，人修内容**。

### 3.3 版位适配规则（docx 生成器内置，实现时的唯一真相）

样例报告全部照片版位都是 **2 列网格**（柜况 4 图 / Quantity check / Truck picture）：

```
格宽 W = 3.2 英寸（正文宽 6.4" 平分，A4 纵向）
每张照片：
  1. 取图（标准图优先，否则原图）→ exif_transpose → 得 (w, h)
  2. 目标宽 = W；目标高 = W × h / w
  3. 若目标高 > H_max(4.2")：改为 高 = H_max，宽 = H_max × w / h（必然 ≤ W）
  4. 按 min(1200px, 原图长边) 重采样后嵌入
效果：横图按宽铺满；极端竖图（9:16）不会撑爆页面；图注永远在照片下方同宽
```

- 压缩档固定 `long_edge=1200`（比 v2 的 1600 再省约 25% 体积：
  438 图 × ~90KB ≈ 40MB docx，可接受；要更小降质量档，版位规则不变）。
- **压缩产物只进 docx，不落盘不回写**——治理管道看到的永远是原图。

## 四、报告生成（继承 v2 骨架，数据源改为按柜取）

### 4.1 模块布局

```
tools/productlib/
├── report_gen.py            # 【新增】纯生成器：dict → .docx（不碰 db，单测直接断言）
├── routes/report.py         # 【扩展】POST /api/report/loading-docx {container_id, ...}
├── store.py                 # 【扩展】loading_report_data(con, container_id) 一次查全
└── web/static/js/report.js  # 【扩展】装柜报告区块
```

`loading_report_data` 是数字同源点：报告页的「93 行 · 4 行无照片 · 12 行未核对」
提示与生成器吃同一份数据（铁律 23：各写一份 SQL 必然漂移）。

### 4.2 区块 → 数据源映射

| 报告区块 | 数据来源 | 口径 |
|---|---|---|
| ① 抬头 | `data/report_templates/<名>.json` | 默认内置 SZAE |
| ② 项目信息 | `containers.product_name / client_name / inspector / location` + 生成日 | 柜详情页可编辑 |
| ③ 柜汇总 | 本柜 `checklist_rows` 汇总（Order/Loading 求和）+ `containers.remark` | 单柜文件一行 |
| ④ General Information | 柜元数据 + 4 个 tag 代表图 | 缺图 → `Not provided`，**不阻断** |
| ⑤ Packing list | `checklist_rows` 按 seq | **原行不合并**；TOTAL 行；check = `check_result ?? check_import ?? ''` |
| ⑥ Quantity check | 本柜照片批次内 `photo_usage='预检'` 且 links 到本柜清单编码的照片 | 图注 `{code}-{name}-{carton_no}`（无箱号省第三段）；2 列；**倒序**（可参数）；每个编码**默认取 1 张代表图**，沿用素材导出的 `picks` 机制人工指定 |
| ⑦ Truck picture | `photo_usage='监装'` 且 tag ∈ {truck_head, loading_process, other} | 按 taken_at 升序；图注 = tag 固定英文文案 |
| ⑧ 结尾 | 常量 | — |

⑥与⑤行数天然不等（有照片的件 ≠ 全部件），与样例一致，**不造数补齐**。

### 4.3 照片导入的箱号提取（App 零改动的配套）

`add_photos` 增强：路径含 `/预检/<目录>/` 段时自动提取 `<目录>` 写 `carton_no`
（与 `carton_map` 并集，人工映射优先）。App 交付包不用改一个字节。

## 五、UI 改造

### 5.1 柜页（新导航项「柜」，替代批次页成为入口）

```
柜列表：柜号 · 封条号 · 清单行数 · 照片数 · 关联完成度 · 报告状态
  [ + 新建柜 ]   ← 唯一必填：柜号
  未分柜（3 批）  ← 迁移产生的兜底柜，提示补柜号后改挂
```

### 5.2 柜详情页（聚合面板，五步流程的 ②③④⑤ 全在这）

```
柜 EMCU9914616                          [编辑柜信息]
①元数据：封条/到离柜/Inspector/Location/Product/Client/REMARKS
②清单：MIEU2012616.xlsx（93 行 · 12 行未核对）[导入/重导] [核对清单]
③照片批次：3 个（预检 812 · 监装 66）       [导入照片]
④治理：待治理 N · 关联缺口 M · 监装标签待打 K [去治理] [打标签]
⑤柜况图：空柜[缩略图▾] 柜侧[▾] 封条[▾] 锁门[▾]
[ 生成装柜报告 ]
```

- 「导入清单」「导入照片」按钮都在柜详情页 —— **选择柜的动作先于导入表单**，
  container_id 从上下文带，用户没有"忘了填柜号"的机会。
- 治理/检索页的批次筛选加柜维度（批次列表显示所属柜）。

### 5.3 监装打标签（照片页，photo_usage=监装 筛选下）

7 类 chip（空柜/柜侧/封条/锁门/卡车头/装柜过程/其他），支持多选批量打
（监装是连拍流，逐张点会点断手）。默认 other。

### 5.4 报告页

选柜（containers 下拉）→ 选项 → 告知不拦截（柜况图缺几张 / 未核行数 / 体积预估）→
生成 → 下载。产物存 `data/reports/`，命名
`LOADING REPORT-CNTR#<柜号>-<日期>.docx`。

## 八、既有纪律对照

- **store.py 唯一写入口**：containers / checklist_rows / 标签写入全走 store，Web 层禁直接 INSERT。
- **数字同源**：报告页提示与生成器共用 `loading_report_data`（铁律 23）。
- **CDP 验收门槛**：UI 改动按 `checks/cdp_*.py` 模式实跑（铁律 24：前置闸门/干净端口 8790/`textContent`）。
- **测试双轨**：`tests/`（解析/行快照/数据组装/生成器）+ `checks/`（CDP 实跑）。
- **措辞**：缺口/未核对不许渲染成 PASS/无问题（铁律 17）。
- **App 零改动**：不碰 `app/`；App 交付包结构（`预检/{箱号}/`、`监装/`）是输入契约。
- **迁移安全**：`_migrate` 幂等（PRAGMA 探测），老库无损升级，改挂未分柜批次可反悔。
