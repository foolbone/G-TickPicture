## 一、方法：桌面预演

真机验证之前，先在 PC 上用 onnxruntime（Python）**逐行复刻** `OnnxPpOcrEngine.kt` 的前/后处理（det 按像素缩放 + BGR/ImageNet 归一化 + DBPostProcess；rec 48×320 + 中灰补边 + CTC 解码 + 字典反查），对 249 张真实照片全量跑通。**跑通 = Kotlin 逻辑同构验证**（PC 与 Kotlin 的差异只剩运行时）。

工具（可复现）：
- `tools/pc_ocr_probe.py` —— 单张/抽样，含四方向实验（`--four-dir`）
- `tools/pc_ocr_eval.py` —— 全量 249 张 + 清单编码匹配统计
- 明细 JSON：`%TEMP%\gt_ocr_eval_out.json`（每张照片的框数 / 文本 / 置信度 / 命中编码）

## 二、探针抓到的 bug（真机验证前修掉）

| # | 问题 | 后果（若上真机） | 修复 |
|---|---|---|---|
| 1 | det 输入尺寸必须 **32 对齐**（U-Net 跳连 Add 节点要求，61×62 直接广播崩） | 每一张照片 run() 抛异常 → 引擎静默回退 ML Kit，用户永远看不到"增强识别"生效，**且不报错** | Kotlin `detResize` 已有 round32（此前写对），探针同步修正 |
| 2 | det 误检框无上限：塑料袋反光让一张装箱单出 **300+ 框**，逐框 rec 在 PC 上 16s | 手机单张几十秒，整理流程卡死 | `MAX_REC_CROPS=40`（det 框已按面积降序，文字行永远比反光块大） |
| 3 | **倒贴的标识卡**：det 对倒置文字完全无感（照样出框），rec 0° 全是乱码 | 现场标识卡经常倒贴/侧贴，这类照片识别率 = 0 | rec **四方向兜底**：0° 置信度 < 0.85 才试 180/90/270。实测倒置卡 180° 后表头字段全部 0.97~1.00 |
| 4 | 探针自身：概率图→原图坐标写反（除法应为乘法）、normalize 通道序多转一次 | —（Kotlin 端本来就是对的） | 探针修正，Kotlin 未动 |

另确认两件**不需要改**的事：det 归一化的"PaddleOCR 怪癖"（mean[0]=0.485 直接施加在 B 通道）与官方一致；det 输出是真概率（0~1），不需要补 sigmoid。

## 四、四个关键判断（数据支撑）

1. **低命中率的真实原因是"照片内容没有编码可读"，不是引擎不行。** 249 张里大部分是集装箱外观/人物/空箱（本来就无文字）；提高 det 像素预算实验（70 万 → 200 万 → 400 万）在"有文字但未命中"的 8 张上命中数全部为 0 —— **70 万像素已到收益平台，维持不变**。
2. **装箱单近拍是高效路径**：一张照片 = 一整箱十几行编码的归属证据，命中质量 0.94+。这应成为「整理页 OCR 建议」的主推场景（拍照引导：凑近拍装箱单，比逐件拍标识卡效率高一个数量级）。
3. **手写编码是硬边界**：标识卡上的物料代码/型号是手写（且常涂改），PP-OCRv6 是印刷体模型，认不出是预期行为。归属判断仍由报告员肉眼完成，OCR 建议缺位不阻塞流程（v3.1 架构本来就这样设计）。
4. **倒置标签已被四方向兜底覆盖**（打印体 0° 直通零开销；倒置卡 180° 满分救回）。
