## 二、信息架构：从「工具页」到「四步向导」

改造后一个页面 = 一条报告生产流水线，每步都带编号与状态：

```
① 选柜          选柜 → 检查就绪度（行数/未核对/核对照/柜况图/卡车图 + 缺口清单）
② 取材          按货品编码检索历史照片 → 标记「采用」→（可选）导出素材包
                 ⚠️ 这一步的「采用」会作为报告区块⑥的用图 —— 检索产生的选图
                 直接喂给报告，这是「检索是报告的一个环节」的物理连接
③ 生成          选项（⑥倒序 / 画质）+「⑥用取材选中的照片」→ 生成 docx → 下载
④ 已生成报告    列表（文件名/大小/时间）+ 下载 / 删除 / 重新生成
```

### 为什么这样分

- **① 是唯一入口**：报告永远按柜出，选柜在位（v3 闸门已保证柜是主线）。
- **② 保持原检索全部能力**（编码粘贴/清单加载/范围勾选/推荐理由/标准图优先/
  素材包导出），只改标题与文案，把「检索终点」改成「取材中转」。
- **③ 与④ 分开**：生成是分钟级动作（1000 行 + 250 图 ≈ 20 秒），生成历史是
  独立资产 —— 老板常要「上周那版再发一次」，没有列表就只能重跑一遍。
- 素材包导出留在 ②：它是同一次取材的另一种出口（给人看的照片包 vs 给客户的报告）。

## 三、后端新增（两个小接口，零数据模型改动）

```python
GET    /api/report/loading-list        # 已生成报告：文件名/大小/时间/下载链接/总占用
DELETE /api/report/loading-file?path=  # 删除单个报告（basename 白名单，禁目录穿越）
```

配套：`POST /api/report/loading-docx` 已支持 `picks`（编码 → photo_id），
本次把它接到 ② 的「采用」上 —— 不改协议，只接前端。
