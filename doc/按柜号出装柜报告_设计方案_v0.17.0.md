## 一、样例报告结构解剖

按 `word/document.xml` 顶层块顺序，共 5 张表 + 7 段文字，7 个区块：

| # | 区块 | 内容 | 样例实测 |
|---|---|---|---|
| ① | 抬头页 | `Report of / CARGO LOADING SUPERVISION` + 供应商固定信息块（Supplier / Contract person / Email / Website / Add） | 8 段纯文字，**客户固定文案** |
| ② | 项目信息表 | Product Name / Client Name / Inspection Date / Inspection Location / Inspector | 5 行 × 2 列 |
| ③ | 柜汇总表 | NO. / CONTAINER NO. / SEAL NO. / Q'ty / REMARKS | 样例 1 行（结构支持多柜） |
| ④ | General Information — `<柜号>` | 柜号+封条号 / 订单数量+到货数量 / 到柜时间+离柜时间 + **4 张柜况照**（空柜、柜侧、封条、锁门） | 4 行 × 4 列，内嵌 4 图 |
| ⑤ | Packing list data | Part Number / DESCRIPTION / Package Number / Order Qty / Loading Qty / Quantity Check result + TOTAL 行 | **1005 行** |
| ⑥ | Quantity check | 2 列网格，每格 = 照片 + 图注 `编码-描述-包装号` | **201 行 × 2 = 402 格，398 有图** |
| ⑦ | Truck picture | 2 列网格，每格 = 照片 + 图注（Truck head/Truck no、Container no view、Side of Container View、Empty Container view、Loading container view…） | 36 图，**图注是照片语义分类** |
| ⑧ | 结尾 | `End of the report.` | 1 段 |

**关键发现**

1. **⑤的表头与真实清单完全一致**（`Part Number / DESCRIPTION / Package Number / Order Qty / Loading Qty / Quantity Check result`）——
   `9.13 5x40HQ/MIEU2012616.xlsx` 的 A1:F1 一字不差。**报告的 Packing list 就是客户清单本身**，
   App 已在导入这一列，问题只在于「Order Qty / Loading Qty / Quantity Check」三列 App 只吃了一个 `qty`。
2. **真实清单的文件名就是柜号**：`MIEU2012616` / `MRSU2065286` / `MRSU5224680` / `MRSU6143915` / `MRSU7099822`
   = 5 个柜 = 5 份报告。**「按柜号出报告」在数据源头就成立**，不是 App 硬加的维度。
3. **柜号在 App 里目前完全不存在**。App 只有 `photo_groups.carton`，语义是清单的
   `Package Number`（Cage-M068 / Pallet-M56 / CENTER-M51）—— 那是**箱**，不是柜。
   柜是箱的**上一层**：项目 → 柜 → 箱 → 组 → 照片。
4. ⑥的图注 `213050008059-Hose GH493-...-Cage-M3103/Cage-M3103-1/Cage-M3103-2`
   里的 `-1/-2` 后缀 = **同一包装箱内的第几件**（与 packing list 里同码多行对应）。
   ⑥的排序是**倒序**（首行 = packing list 的第 1003、1002 行）—— 疑似「最后装的先验」，**待确认**。

## 二、与现状的差距（6 条，按严重度排）

| # | 缺口 | 现状 | 报告要什么 | 严重度 |
|---|---|---|---|---|
| G1 | **没有「柜」实体** | 项目 → 箱（`carton`）→ 组 → 照片 | 项目 → **柜** → 箱 → 组 → 照片；一柜一份文件 | 🔴 阻塞 |
| G2 | **监装照片无语义分类** | `supervisionPhotos` 一坨全进 `监装/` | 柜况 4 图（空柜/柜侧/封条/锁门）+ 卡车头 + 装柜过程，**每类有固定图注** | 🔴 阻塞 |
| G3 | **Order/Loading Qty 与 PASS 判定缺失** | `items.qty` 一个数 | `Order Qty` + `Loading Qty`（实装）+ `Quantity Check result`（PASS/FAIL/NOT FOUND） | 🔴 阻塞 |
| G4 | **柜况元数据无处填** | 无 | Seal No. / 到柜时间 / 离柜时间 / 订单数量 / 到货数量 / Inspection Location / Inspector | 🟠 大 |
| G5 | **docx 生成能力为零** | 交付只出 ZIP + manifest | 42MB 级、1000 行表格 + 400 图的 Word 文档 | 🔴 阻塞 |
| G6 | 抬头供应商文案无处配置 | 无 | 每客户一套固定抬头 | 🟡 小 |

> 附带风险：`Deliveries` 表已有 `pdfPath` 字段但 PDF 联系表已于 v0.12 移除（1000+ 张图全攒内存必 OOM）。
> **本方案明确不做 PDF**，docx 走流式落盘（见第五节）。

## 三、数据模型改造

### 3.1 新增 `Containers`（柜）

```dart
class Containers extends Table {
  TextColumn get id => text()();
  TextColumn get projectId => text()().references(Projects, #id)();

  /// 柜号，如 EMCU9914616 —— **报告文件名与 General Information 标题的来源**
  TextColumn get code => text()();

  /// 封条号（区块④）
  TextColumn get sealNo => text().nullable()();

  /// 到柜 / 离柜时间（区块④）。int 毫秒，可空 = 没填
  IntColumn get arrivalAt => integer().nullable()();
  IntColumn get departureAt => integer().nullable()();

  /// 订单数量 / 到货数量（区块④）。可空 = 由 packing list 汇总自动算
  IntColumn get orderQtyOverride => integer().nullable()();
  IntColumn get availableQtyOverride => integer().nullable()();

  /// REMARKS（区块③）
  TextColumn get remark => text().nullable()();

  /// 柜况 4 图对应的照片 id（区块④ 固定槽位）
  TextColumn get photoEmptyContainerId => text().nullable()();   // 空柜
  TextColumn get photoSideId => text().nullable()();             // 柜侧
  TextColumn get photoSealId => text().nullable()();             // 封条
  TextColumn get photoLockId => text().nullable()();             // 锁门

  IntColumn get seq => integer()();
  IntColumn get createdAt => integer()();
  IntColumn get deletedAt => integer().nullable()();

  @override
  Set<Column> get primaryKey => {#id};
  @override
  List<Set<Column>> get uniqueKeys => [ {#projectId, #code} ];  // 同项目柜号唯一
}
```

**4 个柜况槽位是固定列而不是 JSON** —— 它们是报告的固定版位，每次都要填、每次位置都一样，
放 JSON 等于把「报告第几行第几格」藏进字符串，改版时没人找得到。

### 3.2 `Items` 增列

```dart
IntColumn  get loadingQty => integer().nullable();   // 实装数量（Loading Qty）
TextColumn get checkResult => text().nullable();     // PASS / FAIL / NOT_FOUND
TextColumn get containerId => text().nullable()      // 所属柜（导入清单时按文件名绑定）
    .references(Containers, #id)();
```

`checkResult` 存 code（不引 drift TypeConverter，遵守铁律 1）。默认值**留空 = 未核对**，
⛔ 绝不能默认 `PASS`（沿用铁律 17「还没查完 ≠ 没问题」）。

### 3.3 `Photos` 增列（监装语义分类）

```dart
/// 仅 category == 'supervision' 时有意义：
/// container_truck / container_empty / container_side /
/// container_seal / container_lock / loading_process / other
TextColumn get supervisionTag => text().nullable()();

TextColumn get containerId => text().nullable()().references(Containers, #id)();
```

监装照片**必须挂柜** —— 区块⑦是「这个柜的装柜过程」，不挂柜就没有归属。
预检照片的柜号**从它的箱号反查**（箱 → 柜），不单独存，避免两处打架。

### 3.4 迁移纪律（铁律 18，不可跳过）

- 本次 schema 4 → 5，**只加列不加表不改列**。
- 6 处 `addColumn` 全部走 `_addColumnIfMissing`（幂等），`createIndex` 前查 `sqlite_master`。
- 迁移种子测试必须用 `NativeDatabase(f, enableMigrations: false)` 裸连接。
- 补 `migration_idempotency_test.dart` 用例：连跑两次 onUpgrade 不报错、列都在。

## 四、交互设计

### 4.1 柜的建档：随清单导入自动生成

清单导入向导新增一步「**柜信息确认**」：

```
导入 MIEU2012616.xlsx
  → 识别到柜号：MIEU2012616        ← 来自文件名（可手工改）
  → 货品 93 行，其中 Package Number 覆盖 12 个箱
  → [ ] 允许 App 自动创建这个柜
  → 封条号 [__________]  到柜时间 [2026-09-16 08:49]  离柜时间 [2026-09-16 11:27]
```

- 柜号**取自文件名**（真实清单 5/5 命中），取不到时留空手输。
- 一个项目可导入多个清单文件 → 自动建多个柜（5x40HQ 就是 5 柜）。
- 同一柜号重复导入 → 提示「该柜已存在，是覆盖还是跳过」（**不自动合并**，避免静默改数据）。

### 4.2 照片分柜：整理页顶部加柜选择器

现状是「部类 → 箱号 → 组」，改为「**部类 → 柜 → 箱 → 组**」：

- 照片页顶部 Tab 行下方加一条 `柜：▾ EMCU9914616`（与现有 Tab+拍照条同层，不加高）。
- 选中柜后：预检照片的**可选箱号列表收窄到该柜下的箱**；监装照片直接归到该柜。
- ⚠️ 改组箱号时若该箱属于另一个柜，**联动提示**（不自动改，正交原则）。

### 4.3 监装照片打标签：拍完立刻选

监装拍照后弹一个轻量标签条（7 个 chip，不打断连拍）：

```
[柜况] [空柜] [柜侧] [封条] [锁门] [卡车头] [装柜中]
```

- 区块④ 的 4 个固定槽位直接从这 4 类里挑，**指定即绑定**（改选会换掉旧图并留痕）。
- 区块⑦ 取「卡车头 + 装柜中 + other」三类，按时间排。
- ⚠️ 采集中**不弹任何东西**（铁律：采集期零智能）→ 标签在**整理页**打，不在快门后弹。

### 4.4 数量核对：从「有照片」升级到「有结论」

照片页现有缺口入口（`gap_sheet.dart`）扩成核对表：

| 列 | 来源 | 交互 |
|---|---|---|
| Part Number / DESCRIPTION / Package Number | 清单导入 | 只读 |
| Order Qty | `items.qty` | 只读 |
| **Loading Qty** | `items.loadingQty` | 可编辑（数字键盘） |
| **Quantity Check result** | `items.checkResult` | 三态按钮 PASS / FAIL / 未核对 |
| 照片 | 现归属 | 缩略图 + 缺「去补拍」按钮 |

- **`checkResult` 永不自动填**。机器能判的只有「有照片/没照片」，那是**覆盖率**不是**数量核对结论**。
- 汇总：`Order Total` / `Loading Total` 逐行相加（与样例 TOTAL 行一致）。
- ⚠️ 打包/出报告**不因 FAIL 阻断**（沿用铁律：交付不设检查），但报告里如实出 FAIL。

### 4.5 报告生成入口

交付页新增第三个动作「**出装柜报告**」（与「出照片包」并列，不混在一起）：

```
选柜：[EMCU9914616 ▾]        模板：[SZAE 抬头 ▾]
输出：□ PDF（不支持）☑ Word(.docx)   画质：[1600px/q78 ▾]
[ 生成报告 ]
→ 进度：正在压缩照片 128/398 …  正在写入文档 210/398 …
→ 完成 32.4MB  →  分享 / 保存
```

**出报告前的一次性检查**（不是阻断，是让人知道自己要交什么）：

- 柜况 4 图缺 → 「柜况照缺 2 张（空柜、封条），报告里会留空」
- `checkResult` 仍为空的行数 → 「312 行数量未核对，结果列会留空」
- 体积预估 → 「约 32MB，微信可直发」

## 五、技术选型：docx 生成

### 5.1 三个选项的对比

| | A. 纯 Dart 生成 docx | B. App 出中间件 + PC 脚本生成 | C. 生成自包含 HTML |
|---|---|---|---|
| 现场即时出 | ✅ | ❌ 要拷到电脑 | ✅ |
| 客户可直接改 | ✅ Word/WPS | ✅ | ⚠️ 只能打印 |
| 排版还原 5 张表 + 页眉页脚 | ⚠️ 要手写 OOXML | ✅ 随便改 | ✅ |
| 开发量 | OOXML 生成器 ≈ 3 天 | 脚本 ≈ 1 天 + 协议 | ≈ 1.5 天 |
| 42MB 文档的内存风险 | 可控（见 5.2） | 无（不在手机上） | ⚠️ base64 膨胀 33% |
| 模板迭代（客户改抬头） | 改 JSON 模板即可 | 改脚本 | ✅ |

**推荐 A（纯 Dart 直出 docx）**，理由：老板要的是「最终按柜号输出文件类似的报告」，
交付物必须能在现场手机上手里直接出来；B 方案把最后一步甩到 PC，现场还得再搬一次东西。

C 作为**兜底**（docx 生成器出问题时至少有个能看的东西），不做主路径。

### 5.2 A 方案的可行性论证（关键）

docx 本质 = **ZIP + OOXML**，而 `archive: ^3.6.1` **已经是现有依赖**（清单导入与交付打包都在用）。

结构（只需这些 part，够撑起样例的全部版式）：

```
[Content_Types].xml
_rels/.rels
word/document.xml           ← 5 张表 + 段落（StringBuffer 拼，1000 行约 1.5MB 文本）
word/_rels/document.xml.rels← 398+ 图片关系 + styles/header/footer
word/styles.xml             ← 正文/表头/表格边框
word/header1.xml            ← 页眉（样例有）
word/footer1.xml
word/media/imageN.jpg       ← 逐张流入
```

**内存可控的关键：完全复用交付打包的成熟链路**（`_packEntry` 已验证的那套）：

- 走**后台 isolate + 同步 IO**（`ZipEncoder.addFile` + `InputFileStream`），**零 await**。
  铁律 13⑧已经用 1000 张照片验证过：每文件一 await = 184s，同步 = ~2ms/张。
- 图片**先压后写**：复用 `PerfBridge` 的原生压缩通道，报告用 1600px/q78（比交付的 2560/q85 更小）。
  398 张 × ~80KB ≈ 32MB，微信 1GB 上限内绰绰有余。
- 表格 XML 用 `StringBuffer` 增量拼，**不建 DOM 树**（1005 行 × 6 列的 DOM 会吃掉几百 MB）。
- 图片宽高按 A4 正文宽换算成 EMU（1 inch = 914400 EMU），**只改显示尺寸不改像素**，避免二次解码。

**进度与取消**：分两段（压缩 0→0.45 / 写文档 0.45→1.0），取消 = kill isolate + 删半成品
（与现有 `ExportCancelled` 处理一致）。

### 5.3 区块 → 数据源映射表（实现时的唯一真相）

| 报告区块 | 数据来源 | 缺省行为 |
|---|---|---|
| ① 抬头 | `AppSettings` 里的 `report_template`（JSON） | 无模板 → 用内置 SZAE 默认值 |
| ② 项目信息 | `Projects.name` / `.client` / 报告生成日 / 项目 `inspectionLocation` / `AppSettings.inspector` | Inspector 可留空 |
| ③ 柜汇总 | 该柜 + `Packing list` 汇总 Order/Loading | 多柜时列出全部（单柜文件只有一行） |
| ④ General Information | `Containers` 全部字段 + 4 个 photo 槽位 | 照片缺失 → 单元格留「未提供」 |
| ⑤ Packing list | `Items` 按 `seq` 排（**不合并同码行**！与样例一致：同码多行是不同件） | `state=='extra'` 的行单列在末尾并标 EXTRA |
| ⑥ Quantity check | 有照片的 Items，2 列网格，图注 `code-name-carton` | 排序倒序（**待老板确认**） |
| ⑦ Truck picture | `supervisionTag ∈ {truck, loading_process, other}`，2 列网格 + 固定图注文案 | 无照片 → 整块跳过 |
| ⑧ 结尾 | 常量 | — |

> ⚠️ **⑤不合并同码行**是刻意的：`Items` 导入时会把同 `code` 多行**合并成一条**（`sourceLineCount`），
> 而样例报告里 `216070000001` 是**连着 3 行**的。这是「App 的合并模型」与「报告的行模型」的**根本差异**，
> 必须在 `Items` 里保留原始行快照（见 3.2 的补充），否则报告数量对不上清单。

## 八、必须遵守的既有铁律（实现时对照）

- **铁律 1**：UI 禁 import `data/`；报告模型的 UI 可见类型住 `domain/model/`；改 UI 跑 `check_architecture.ps1`。
- **铁律 13⑧**：批量文件 IO 同步 + 后台 isolate，**零 await**（`ZipEncoder.addFile`，不用 `ZipFileEncoder.addFile`）。
- **铁律 17**：`checkResult` 未核对 ≠ PASS；未完成态不许渲染成结论态。
- **铁律 18**：所有 `addColumn` 幂等 + 自愈；迁移种子用裸连接。
- **铁律 7**：报告内照片**只读源文件、永不改名**。
- **原则 13**：措辞禁「现场未见」，缺口一律说「缺口」。
- **铁律 5/6**：`Value.absent()` 跳过列、`Value(null)` 清空；同文件禁并行编辑。
- **不做 PDF**：v0.12 移除 PDF 联系表的教训（1000+ 张图全攒内存必 OOM）不重犯。
