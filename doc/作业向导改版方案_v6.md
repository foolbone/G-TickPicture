# 作业向导改版方案 v6

> 触发：老板 2026-10-06 23:59 的五条反馈
> ① 建柜下要能编辑当前柜信息；
> ② 导入清单要能看清单内容，字段交互与标准产品库一致；
> ③ 导入照片与照片治理**合并为一个**，并能查看照片；
> ④ 把⑤里的「取材」提为第④步并改名；
> ⑤ ⑤里去掉取材。
>
> 前序：`产品库整体流程与界面改造方案_v5.md`（v5 已落地并通过 55 项验收断言）。
> 本次仍是**纯交互层**：不动 schema、不动迁移链、不新增数据表。

## 一、新的五步

| 步 | 名称 | 内容 | 数据来源 |
|---|---|---|---|
| ① | **建柜** | 新建柜 + **编辑当前柜信息**（显式保存） | `PUT /api/containers/{cid}` |
| ② | **导入清单** | 导入 Excel + **查看/编辑清单内容**（品名·规格·箱号·Order·Loading·核对） | `GET .../checklist` + `PATCH /api/products/{code}` + `POST /api/checklist/rows/check` |
| ③ | **照片** | **导入照片 + 跑治理 + 浏览照片**（原③④合并） | `import-auto/upload` + `/api/govern` + `GET /api/photos?container_id=` |
| ④ | **选图**（原⑤的取材） | 为报告的 Quantity check 挑每件货的用图；**可跳过** | `GET .../checklist` + `POST /api/report/lookup` |
| ⑤ | **生成报告** | 只生成，**不再有取材** | `POST /api/report/loading-docx` |

### 步 ↔ 后端 progress 的映射

后端 `steps` 仍是 5 个键，UI 重新映射（④是纯客户端步骤，后端无对应）：

| UI 步 | 后端 steps 键 | done 的判定 |
|---|---|---|
| ① 建柜 | `container` | `container.done` |
| ② 导入清单 | `checklist` | `checklist.done` |
| ③ 照片 | `photos` + `govern` **合并** | `photos.done && govern.done` |
| ④ 选图 | —（客户端） | 有采用标记即算完成；**不参与 ready_pct**（它是可选优化，不是流程必经） |
| ⑤ 生成报告 | `report` | `report.done` |

就绪度百分比仍取后端 `ready_pct`（①20+②15+③照片15+③治理25+⑤25 = 100），
④不计入 —— 否则「跳过选图」会被显示成"没做完"。

## 二、每步的界面结构

沿用 v5 的卡片骨架：**说明 → 本步状态 → 结果详情 → 主操作 → 反向链接**。

### ① 建柜（可编辑）

- 结果详情从"只读表格"改成**可编辑表单**：封条号 / 客户 / Inspector / Location /
  Product / 到柜时间 / 离柜时间 / 备注。
- **柜号只读**（它是身份标识，改了等于换柜）。
- 交互与标准产品库字段编辑**完全一致**：改完点「保存修改」才生效、旁边有「还原」、
  未保存时切步骤会拦一下并提示。
- 空值显示为橙色占位「未填」（这几个字段进报告 General Information，缺了报告不完整）。

### ② 导入清单（可查看 + 可编辑）

- 结果详情换成**清单内容表格**（不是一个批次名的列表）。
- 多批次时顶部有批次下拉（默认最新一批）。
- 列：`# / 编码 / 品名 / 规格 / 箱号 / Order / Loading / 核对`。
  - **品名、规格可编辑** → 保存时 `PATCH /api/products/{code_norm}`，
    即**改标准产品库的主记录**（唯一真源；不写快照，避免两份品名打架）。
    字段交互与标准产品库一致：显式保存 + 还原 + 未保存拦截。
  - **Loading、核对可编辑** → `POST /api/checklist/rows/check`
    （写清单快照的人工核对结论，空 = 未核对，报告沿用清单预填）。
- **1000+ 行必须分页**：每页 50 行，客户端翻页（后端一次返回，前端切片渲染，
  绝不全量塞进 DOM —— 1003 行 × 8 列会明显卡顿）。

### ③ 照片（导入 + 治理 + 浏览，三合一）

- 主操作：`[＋ 导入照片]`（模态，同前）。
- **治理面板整块搬进这一步**（不是复制一份）：`#govPanel` 从照片库页搬到向导里，
  批次选择 / 开始治理 / 重试失败 / 进度条 / 失败七类诊断**全部原样复用**。
- 下方**照片网格**：本柜最近 24 张缩略图，点开进照片详情抽屉（复用 `shotCard`），
  底部给「在照片库查看全部 →」。
- 照片库页原来的治理面板换成一块指引：「治理已并入作业向导③」+ 跳转按钮。

> **为什么搬而不是再写一份**：治理是全站最重的逻辑（进度轮询 + 失败七类诊断）。
> 复制一份必然漂移。搬过去后照片库页通过自定义事件 `wizard:goto` 跳回来，
> 避免 batches.js ↔ wizard.js 循环依赖。

### ④ 选图（原⑤的取材）

- 名字从「取材」改成**「选图」**：老板的动作是"给报告的每件货挑一张图"，
  「取材」太像工厂用语，且和②导入清单的"取"混淆。
- 内容整体搬过来：载入本柜清单编码 / 粘贴解析 / 检索 / 逐张「设为采用」。
- 状态：`已选 N 张`；`未选（可跳过）`；没有清单行时禁用并说明「先完成②」。
- **采用标记按柜存 localStorage**（与报告中心同一口径），刷新/切步骤不丢。

### ⑤ 生成报告（去掉取材）

- 只留：⑥倒序 / 画质 两个选项 + `[生成 docx]` + 结果卡 + 本柜历史报告。
- 结果卡由状态渲染（刷新进度不能把它冲掉）。
- 前置不变：清单 ≥1 行 **且** 照片 ≥1 张，否则按钮禁用并说明缺什么。

## 三、后端改动

**零改动**。逐条对齐复用：

| 需求 | 复用的端点（已存在） |
|---|---|
| ① 编辑柜信息 | `PUT /api/containers/{cid}` |
| ② 看清单内容 | `GET /api/containers/{cid}/checklist?batch=` |
| ② 改品名/规格 | `PATCH /api/products/{code}` |
| ② 改 Loading/核对 | `POST /api/checklist/rows/check` |
| ③ 导入照片 | `POST /api/photos/import-auto` / `/api/photos/upload` |
| ③ 跑治理 | `POST /api/govern` + `GET /api/govern/status`（面板整体搬过来） |
| ③ 浏览照片 | `GET /api/photos?container_id=&limit=` |
| ④ 载入编码 | `GET /api/containers/{cid}/checklist` |
| ④ 检索 | `POST /api/report/lookup` |
| ⑤ 生成 | `POST /api/report/loading-docx` |
| ⑤ 历史报告 | `GET /api/report/loading-list` |

## 五、验收标准

1. 五步顺序 = 建柜 / 导入清单 / 照片 / 选图 / 生成报告，节点数仍 5。
2. ①柜信息可改 → 保存 → 刷新后还在；未保存时切步骤有提示。
3. ②能看到清单行（1003 行的柜分页正常），改品名后保存 → 标准产品库里同步变了。
4. ③能导入、能跑治理（进度条可见）、能看到本柜照片缩略图并点开详情。
5. ④能看到编码池、检索、标记采用；状态显示"已选 N 张"。
6. ⑤里**没有**取材区块；生成后结果卡不被刷新冲掉。
7. 照片库页的治理面板已移除，指引按钮能跳到向导③并展开治理。
8. 静态三检绿 + 16 套后端测试全绿 + 无头走查零 JS 报错。

## 六、风险与取舍

| 风险 | 处置 |
|---|---|
| 治理面板搬家影响照片库页既有用户 | 照片库页保留指引块 + 一键跳转；`govBatch()` 启动治理后自动跳向导③，**保证进度条可见**（进度藏起来等于卡死） |
| 清单 1000+ 行卡顿 | 客户端分页，每页 50；不全量渲染 |
| ②改品名与标准产品库双写 | 只写 products（主记录），快照不动；界面明确标注"改的是标准产品库的产品字段" |
| ④选图状态刷新即丢 | 按柜存 localStorage（与报告中心同一口径） |
| 循环依赖 | 向导需要 batches 的 `loadBatches`，batches 需要跳向导 —— 用 window 事件解耦 |
